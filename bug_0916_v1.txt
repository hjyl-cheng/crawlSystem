问题记录：YouTube 视频返回 Please sign in 时的处理优化
记录日期：2026-09-16
状态：修复已部署，但发现 Feature 事件协议兼容回归，Plan 收尾验收未通过；待补充修复（2026-09-16）。

一、问题范围

涉及全量抓取和增量抓取中的视频详情采集。
典型响应为 LOGIN_REQUIRED / Please sign in，且响应不足以满足当前采集所需字段。
该响应说明本次请求被要求登录，不能单独证明视频私有、已删除或永久不可访问。

二、当前处理方式

1. 视频详情先尝试 WEB，再尝试 IOS；当前不继续尝试 ANDROID。
2. 客户端均未取得所需信息时，抛出 alternate_clients_exhausted，统一归类为
   youtube_challenge，并进入更换身份、线路及断点重试流程。
3. API 兜底启用时，此类网络/风控失败在受管执行中依赖 Rota 业务网络预算耗尽，
   才允许进入官方 Data API 兜底。
4. 增量 API 兜底由 YOUTUBEJS_VIDEO_API_BATCH_FALLBACK 控制；全量需使用
   youtubejs_full_v3。Compose 默认启用两者，但环境覆盖和已有任务契约可能不同。
5. 持续登录提示且未进入 API 兜底时，重试耗尽后本轮抓取失败。
   API 兜底仍失败或信息不足时，全量最终走失败收尾；增量可能将单视频记为
   settled_error，视频域汇总为 partial，后续步骤成功后频道 Run 仍可为 done。

三、存在的问题

1. 将持续登录要求与机器人验证混为 youtube_challenge，错误分类不够准确。
2. 对需要登录权限的访问限制，反复更换匿名客户端或代理无法补足账号权限，
   容易消耗请求、换线和重试预算，并可能对正常代理产生不恰当的风控反馈。
3. 单条无法采集的视频可能阻塞频道其他视频的处理。
4. 增量流程结束状态与数据完整程度不同，单看 done 容易被理解为所有详情均已取得。

四、已确认的优化策略

业务定义：当前匿名采集不支持持续要求登录的视频，将其按策略排除，
不再为该视频反复换线、不调用 Data API、不安排自动重试。
这是主动缩小采集范围，不是认定视频已删除，也不是证明 Data API 无法取得信息。

建议触发条件：
- WEB、IOS 均返回 LOGIN_REQUIRED / Please sign in，且所需信息仍不足。
- 任一客户端取得满足要求的信息，则继续正常采集。
- 任一客户端返回明确私有、删除等原因，则按真实内容状态处理。
- 机器人验证（如 not a bot）、年龄限制、限流和网络故障仍走各自策略，
  不得仅按包含 sign in 的宽泛文本匹配归入本分支。

触发后的目标字段：
  disposition       = terminal_excluded
  reason_code       = login_required
  detail_status     = unavailable
  api_status        = not_needed
  next_attempt_at   = infinity
  retryable         = false

字段语义：
- terminal_excluded：按当前采集策略排除该视频，完成该视频的处理结算。
- detail_status=unavailable：当前采集无法取得所需详情。
- api_status=not_needed：按策略不调用 Data API，不表示 API 已验证该视频不可用。
- next_attempt_at=infinity：不安排自动重试或定期复查，允许人工解除排除后重新采集。

处理结果：
- 不再把本分支当作 youtube_challenge，不处罚代理，不继续消耗换线预算。
- 记录客户端响应、缺失字段及排除原因，保留审计依据。
- 频道继续处理其他视频；该视频本身不导致频道任务失败或进入失败队列。
- 其他必要步骤成功后，频道可以按采集范围完成，并展示
  “采集完成，因登录限制排除 N 个视频”，不能表述为所有视频详情均已取得。
- 若频道其他步骤失败，仍正常进入相应失败流程。

五、数据保护与实现注意事项

1. 区分采集详情状态与视频真实访问状态。
   不得仅因登录提示将已有视频的 access_status 改为已下架或不可用，
   不得删除已有内容、清空已有有效详情或触发不实的下架传播。

2. 排除策略需覆盖全量、增量首次发现、增量已有视频刷新，以及本地、远程执行路径。
   已入库视频还需停止对应的自动刷新调度；只修改候选项可能仍会再次请求。

3. 排除结论需在后续调度、任务恢复及再次发现该视频时保留。
   不能只在当前 Run 中生效，也不能在恢复执行时重新反复尝试 WEB、IOS。
   人工解除排除应能恢复正常调度。

4. 现有 terminal_excluded 并不等于永久不重试。
   videoDisposition.js 中普通排除原因存在七天低频复查逻辑，
   必须为 login_required 保留 infinity，防止后续结算覆盖为有限时间。

5. 增量当前会将部分 terminal_excluded 项的 api_status 写为 unavailable，
   需要针对 login_required 与全量统一为 not_needed。

6. 不能通过伪造 access_status=unavailable 来复用排除逻辑。
   应增加明确的 login_required 排除分支，保证结算不依赖不实的访问状态。

7. 检查 infinity 在数据库、JavaScript、序列化及展示中的兼容性，
   避免日期转换异常或被当作普通待重试时间。

8. 该策略明确放弃登录受限视频可能通过 API 获取的信息，以及未来自动恢复采集的机会。
   排除清单应可查询、可人工解除，频道结果应包含登录受限排除数量。

六、验收建议

1. WEB、IOS 均持续返回目标登录提示且字段不足：视频按上述字段排除，
   不换代理、不调用 API、不进入自动重试，其他视频继续处理。
2. WEB 要求登录、IOS 返回足够数据：正常保存，不排除。
3. 机器人验证、年龄限制、私有、删除、限流及网络错误：保持各自既有分类。
4. 全量、增量及远程路径采用相同排除语义，恢复执行不重复采集已排除视频。
5. 已有有效视频数据不被清空，也不被误标为下架。
6. 下一轮调度及自动修复不再次选中 login_required 排除项；人工解除后可重新采集。
7. 频道正常收尾时能查询排除原因和数量；其他真实失败仍进入失败流程。

十、补充诊断：Run done 但 Plan 未收尾（2026-09-16 12:05 UTC）

此前“已完成线上验收”的结论不充分：只确认了采集 Run 和候选结算，
未覆盖 Feature 事件应用及 Daily Plan 最终完成状态。

固定观察窗口截至 11:59:12.216 UTC 的最近 5 分钟，184 个已完成任务：
- 161 个 Plan=running、Run=done；About 事件已 applied，Video 事件缺失。
- 13 个 Plan=dispatched、Run=done；仅要求 Video，完成事件未应用。
- 10 个 Plan=succeeded、Run=done；仅要求 About。
12:03 UTC 复查时，上述 174 个计划仍未收尾，不是几秒钟的统计缓存延迟。
对应 174 个 Video Outbox 均为 published，但 Feature Inbox 中无对应 Video 事件；
171 个 About 事件均已 applied。

使用线上 Feature 容器的 CrawlerObservationRecorded.from_mapping 对原始持久化
Video 事件进行纯解析（不写库），确定性复现协议错误：
1. discovery.payload.login_required_excluded_count: unexpected field。
2. recent_sampling.payload.login_required_excluded_count: unexpected field。
3. 对实际 login_required 排除项：terminal_excluded disposition requires retry_class，
   新策略的 retry_class=null 被旧校验拒绝。

根因：本次修复增加了生产者事件字段及永久排除语义，却遗漏 Feature 消费者
严格协议和语义解析的兼容修改、跨服务事件验收。
计数字段即使为 0 也会发送，因此影响不仅限于真正出现 Please sign in 的视频。
Outbox published 只代表上游投递完成，不能据此认定 Feature 已接受并应用事件。

Plan 收尾由 Feature 对所需 About/Video/Agent applied 事件聚合决定；
采集 Run.done 并不会直接修改 Plan 为 succeeded。
因此“每分钟队列完成数”不能当作端到端频道完成速度；此前将低速主要解释为
状态滞后的说法不准确，已证实为本次变更引起的下游事件兼容故障。

待修复范围：
- 补齐 Feature 严格契约及语义解析对登录排除计数、永久不重试语义的支持。
- 使用实际生产事件覆盖协议解析、事件应用和 Plan 终态的跨服务回归。
- 修复后按已持久化事件 ID、原顺序与幂等约束恢复事件消费，避免重新抓取。
- 检查失败/拒绝投递的实际存储位置及重放入口，不直接伪造 Plan 成功状态。

本轮仅诊断并记录，未修改运行配置、任务状态或重放事件。
