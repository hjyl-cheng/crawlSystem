# 迁移吞吐与 Finalize 恢复修复方案

日期：2026-09-10。状态：代码已实现，Controller 已分阶段上线，API/Dashboard 推广和持续观测进行中。原方案保留如下；实际实施与验证记录见第 10 节。

目标：让有合格待迁移频道、可用 Worker 和代理容量时，抓取持续获得任务；让 Finalize 与视频 API 兜底及时恢复；限制数据库每轮维护开销，并保留现有完整性、批次控制和发布一致性。

**1. 线上事实与尚待测量的部分**

本次只读诊断的采样窗口主要为 08:57–09:02 UTC，另于 09:12 UTC核对待补数据状态。以下数字是当时快照。

| 观测 | 结果 | 含义 |

| Channel Worker | 40 个容器运行 | 容器数量不等于持续执行数量 |
| 连续队列采样 | active 从 40 降到 22、4、1、0；prioritized 耗空 | 存在任务供给间歇 |

| 调度配置与记录 | 配置 15 秒；最近 tick 记录间隔约 3–5 分钟 | 设置周期没有保证实际周期 |
| 数据库活动 | `finalize-recovery:candidates` 同一查询持续超过 120 秒 | 慢查询处于控制器串行路径 |

已核对源码：`controller.js` 顺序执行迁移管理、API 兜底及 Finalize 恢复；`controllerLifecycle.js` 防止 tick 重入，因此慢 tick 期间不会开始新 tick。`migrationBatchControl.js` 又将准备、终态结算和补队列绑在一个函数中，当前一次选择最多 100 个 pending 频道。

Finalize 查询包含 channels / channel_runs 扫描，以及每个候选 Run 的内容更新时间聚合。`LIMIT 200` 在候选判断和排序之后，不能限制之前的扫描量。已有内容关联索引，不能把问题简单归为“没有索引”。执行计划为 EXPLAIN、未运行 ANALYZE；尚未测出每个查询节点的实际耗时。

尚需在实现前的基线中补齐：各控制器阶段耗时、批次结算持锁时间、进度接口开销、数据库连接等待、API 额度及熔断状态、API 最老可执行请求年龄、代理就绪容量。API 派发受慢 tick 影响已明确，但积压的全部原因仍需逐项确认。

**2. 必须保留的业务条件**

- 恢复候选要求详情 done；活跃频道要求 Agent 完成且存在成功的 basic Agent 记录；休眠频道走现有 registry promotion 和活跃度判断分支。
- 最终完成仍由 `finalizePolicy.js` 的规则决定：存在 open detail / open API 时保持 pending；Agent 未满足要求时保持 pending_agent。现有 ready_partial 表示按当前规则接受的部分完成或休眠，不等于所有字段都齐全，本次不改这个产品语义。
- “需要检查 Finalize”的记录只是一条恢复意图，不代表已经满足 Finalize 条件；检查时、执行时仍使用真实源状态。
- 保留 `finalizeDispatch.js` 的 source revision 任务去重和 `finalizeSourceFence.js` 的提交前源版本复核；旧 Run、旧 revision 不得覆盖新状态。
- 已 Finalize 的频道发生相关数据变化后，必须能够再次检查和收尾。禁止将“已经 Finalize”作为永久跳过条件。
- 批次仍使用冻结清单；pause/stop 提交后不得接纳新的频道，已启动频道继续恢复、收尾和发布。暂停不能变成暂停共享 BullMQ 队列。
- 保留 Run、candidate、批次和派发 generation 的身份检查、既有重试预算与检查点续跑；吞吐修复不改变抓取范围、代理策略、API 额度或失败终态规则。

**3. 第一阶段：拆开调度路径，恢复连续供给**

将控制器内的工作拆为独立、不可重入的循环，每个循环有自己的唤醒、周期、耗时和错误记录：

| 循环 | 职责 | 初始建议 |
| --- | --- | --- |
| 迁移补队列 | 检查批次、读取已准备 pending 项、补足可执行任务 | 每 2 秒检查；低水位时补足目标窗口 |
| API 兜底派发 | 恢复已持久化批次、按现有规则派发可执行 API 请求 | 每 2–5 秒检查 |
| 批次维护 | 准备冻结清单、结算终态、推进 pausing/stopping/completed | 独立周期，按批处理 |
| Finalize 恢复 | 有界扫描或消费待检查记录，复用现有 Finalize 投递 | 独立周期，限制单轮工作量 |
| 其余控制逻辑 | Query、容量控制、Agent 等既有职责 | 保留语义，记录各阶段耗时 |

这些数值是待压测调优的初始配置，不能直接当作线上效果承诺。先在现有单控制器进程内拆分职责，不额外启动第二个完整 Controller。

迁移补队列提取为单独的 Module，隐藏队列计数、pending 选择、快照准备与幂等投递。批次准备完成后才允许补任务；快照读取设定超时和每轮上限。待抓取任务计数要区分“尚未启动的真实迁移任务”与 API 续跑/延迟恢复，后者不能堵住新任务供给窗口。

初始保留 100 个真实新任务的目标窗口，低于约 40 个时补齐，最多增加目标缺口；数据表中的尚未启动项与已有 Job ID 去重，避免每轮把同一窗口无效重投。真实在途数量仍由 Worker 和既有容量控制决定。

拆分时同时缩短批次锁事务：准备大清单在 preparing 状态进行；终态候选可分批计算，写入时按原有锁顺序重新核对批次版本、候选及恢复状态。不得让全量结算计算长期占用 admission 所需的 scheduler/batch 锁。部分结算尚未处理完时，不能提前声明整批已完成。

pause/stop 与补队列存在竞争时，Worker 端原子 admission 是最终屏障：已经排队但尚未启动的 placeholder 不得创建新 candidate 或开始抓取。续跑属于已接纳任务，按原规则继续。

循环拆分也必须处理资源隔离：为补任务和慢速维护提供明确的连接预算，设置用途可识别的 application_name；对恢复查询设置局部 statement_timeout/lock_timeout。复用现有数据库身份校验、writer version 和时区配置。慢查询超时不能标记频道失败，扫描进度不能越过未处理数据。总连接数受 PgBouncer/PostgreSQL 容量限制。

从旧 tick 删除迁移/API/Finalize 对应调用，避免新旧路径双重调度。共享队列启停及容量策略保持单一归属；需要跨循环读取的控制状态使用持久状态或明确版本的快照。停机时先停止全部循环接单，再等待在途调用结束，最后关闭共享连接。

**4. 第一阶段：将 Finalize 全量查询改成有界轮巡**

先实现不依赖全量事件覆盖的修复，作为后续长期核对机制：

1. 使用稳定且有索引的 channel_id 游标，在扫描轮次开始记录本轮上界；每次先取最多 100–200 个频道 ID。先限制扫描页面，再关联 Run、Agent、内容和 finalized 数据。
2. 页面查询用明确的物化阶段或独立语句，验证 PostgreSQL 不会把 LIMIT 推回昂贵筛选之后。入口条件和 freshness 比较沿用现有语义。
3. 在小页面内判断当前 Run 或休眠 promotion Run，计算该页必要的内容更新时间，复用现有 `dispatchFinalizeForRun`。
4. 一页恢复意图可靠入库或投递完成后，再持久化游标。Redis 入队失败不推进游标；崩溃重读同一页依靠原有 Job ID 去重。
5. 扫描按稳定 ID 前进，不用可变 updated_at 做唯一进度。已扫过的频道随后变化，由下一轮及第二阶段事件记录覆盖；新插入且位于游标后方之外的 ID 由下一轮处理。
6. 扫到上界后完成一轮并重新开始。分别维护扫描作用域和游标，覆盖现有调用所需的批次与 Run 语义；批次结束、切换不能永久遗留旧作用域工作。
7. 超时后保持该页可重试，必要时降低页面大小并记录持续失败的精确频道，避免无限忙重试或静默跳过。记录完整扫描一轮所需时间，不能仅以单页快作为验收。

索引由隔离数据库的 `EXPLAIN (ANALYZE, BUFFERS)` 决定：优先核对实际 Run 范围选择、content_candidates 的 run_id 更新时间读取、contents 的 channel_id/run_id 更新时间读取。只增加能减少实测读取的索引，并测量详情写入的额外成本；不盲目叠加已有索引。

线上大表索引若确有必要，使用独立迁移脚本并发创建，校验库身份、索引有效性和创建进度；失败清理无效索引后再重试。并发建索引本身仍有 I/O 成本，需限速和监控。

**5. 第二阶段：相关数据变化时登记 Finalize 待检查记录**

第一阶段消除单次无界扫描；第二阶段让常规恢复成本主要随变化量增长，轮巡只负责核对遗漏。

新增以 channel_id 去重的持久化待检查表。至少记录 requested_generation、handled_generation、下一次可检查时间、租约 token/到期时间及错误重试信息。Run 归属在检查时根据当前频道状态解析，并保留观察到的 Run/revision；旧 Run 的结果不能确认新 Run 的检查完成。

先梳理所有影响 Finalize 的写入口，包括频道状态和当前/promotion Run 变更、详情或 API 完成、内容和候选更新/删除、Agent 完成/修改，以及修复路径。按现有源版本语义判断哪些变化需要登记，避免 Finalize 自己的记账字段更新触发无限循环。

登记与源数据变更在同一个 PostgreSQL 事务中提交，以 generation 递增合并同频道通知。优先接在现有集中持久化入口；无法完整覆盖的写入口需要补齐或采用经过评审的定向数据库触发器。未证明写入口覆盖之前，轮巡仍是必需路径，不能关掉。

处理流程：

1. 用短事务和 `FOR UPDATE SKIP LOCKED` 领取到期记录，获得 token 与 generation；事务提交后执行源数据读取，不在网络/Redis 操作期间持有行锁。
2. 复核真实入口条件。不满足时按等待原因退避，并允许新 generation 唤醒，避免反复检查同一未完成频道。
3. 满足条件后按现有 Run/source revision 投递 Finalize。投递意图先持久化，优先复用符合该语义的现有 outbox；如不能复用，则在待检查记录中保留可重放的投递状态。
4. Redis 失败、崩溃或租约超时由同一意图重试；复用原 Job ID，不能因为游标前进而丢失投递。
5. 按租约 token 和领取到的 generation 条件确认，只处理当前版本。如果期间又有更新，新 generation 保留。
6. “已入队”与“已成功 Finalize”分别记录。Job 丢失、失败、被旧 source fence 拒绝时仍可恢复；完成时依据真实 Run/revision 核对，不能把入队当成发布完成。

上线迁移顺序：先建兼容表并开启写侧登记，再分批回填历史待检查记录；回填只追加或提升待检查版本，不能覆盖更高 generation 或既有租约。回填过程中数据继续变化也必须可追踪。新读取路径先在隔离副本对照结果，线上少量只读核验，再切换消费。之后将全量轮巡降为低频、有界核对，并监控每轮覆盖时间及其发现的遗漏数。

**6. API 兜底与续跑修复**

将 `dispatchVideoApiRequests` 从长 tick 中提取，保留当前 emergency 模式、每日共享额度、Worker 并发、批次归属和每视频重试上限。API 队列启停/额度状态必须及时可见，不能因提速绕过原约束。

补充区分：等待派发、已入队、API 执行中、额度等待、退避、请求已完成但 Run 尚未续跑。优先处理最老的可执行请求；每轮批次数和全局在途量共同限流，避免缩短周期后累计创建过多批次。

复用现有数据库 Batch、Task 锁及确定性 Job ID；事务已提交但 Redis 失败时仍恢复原批次。请求完成后继续原 Run、原视频检查点；还有网络步骤时重新进入现有受管网络执行。

第一阶段保留现有 15 秒延迟轮询续跑，它本身是容错机制。仅在实测显示轮询成本显著时，再增加按精确 Job 身份唤醒的优化，轮询仍作为兜底。待补数据不能通过强制修改 detail_status 或终态来“清积压”。

**7. 监控与页面统计**

记录各循环开始、结束、耗时、距上次成功时间、连接等待和锁等待；给 Finalize 扫描记录 examined/eligible/dispatched、扫描游标、整轮年龄、超时数，给待检查表记录未处理 generation 与最老可执行记录年龄。

迁移供给重点指标：存在合格 pending 且有 ready Worker 时，等待窗口是否耗空、连续空闲时长、补任务延迟；将等待代理、额度、退避及人工暂停单独计数。

页面保留累计平均，新增最近 15/60 分钟批次终态处理数、抓取完成数、成功/休眠/拒绝/最终失败数量与“执行/恢复中”。抓取完成和业务终态分开，避免把恢复尝试、重复完成或下游尚未完成当成新的频道成果。

滚动统计使用定期采样的累计终态计数，绑定 batch_id 和时间，处理暂停、批次切换及计数修正；避免页面每次轮询扫描数十万 control items。终态计数差分受结算周期影响，页面标明它是结算速率。对现有进度接口的慢查询单独测量，必要时复用持久聚合/短时缓存，保留周期对账。

**8. 回归与性能验收**

使用明确 `_test` 身份的隔离 PostgreSQL/Redis，先运行现有业务入口能触发的失败测试，再修改实现。测试夹具模拟约 40 万迁移清单，并设置 5 万、10 万、40 万已处理频道及相应内容量；清单规模和已处理数据规模分别验证，不能只生成空频道证明性能。

| 场景 | 必须验证 |
| --- | --- |
| Finalize 检查阻塞 120 秒 | 40 个模拟 Worker 的迁移补队列、API 派发继续运行 |
| 批次结算慢、数据库连接被维护占用 | 独立循环仍有受控连接预算；短 admission 不被长事务阻塞 |
| 运行中 pause/stop 与补任务竞争 | 提交后新频道不再 admission；已启动频道正常排空 |
| 所有新任务转为 API 延迟 | delayed 不吞掉新频道缓冲；API 限额仍生效 |
| 多页绝大多数无须 Finalize | 每页扫描有界、游标持续前进、尾部候选最终发现 |
| 已扫描后数据变更、Run 切换、休眠 promotion | 事件或下一轮能发现，旧 Run 不能覆盖新 Run |
| 注册/领取/入队/确认任一边界崩溃 | 意图可重放，不丢恢复，不产生重复有效发布 |
| generation N 处理时产生 N+1 | N 的完成不能清除 N+1；租约旧 owner 不能确认新 owner |
| API/detail pending、Agent 未完成 | 保持现有 pending 规则，不提前最终收尾 |
| 数据完整、部分完成、休眠、再次补齐 | 结果与既有 finalizePolicy/source fence 一致 |
| API 额度耗尽、Batch 入队失败、恢复续跑 | 等待有原因，预算不超限，继续原检查点 |
| 老新查询完整扫描同一固定数据集 | 恢复候选集合及最终业务效果相同；并发变化另有专项测试 |

隔离性能验收的初始目标：正常补队列检查 P95 不超过 2 秒，符合条件的新任务补充 P95 不超过 5 秒；有可执行库存和资源时，不出现供给原因导致的连续 10 秒以上全体空闲；Finalize 单页 P95 不超过 2 秒、单次维护查询设 5 秒保护预算。API 无额度/退避阻塞时，从可派发到入队 P95 不超过 10 秒。目标以明确硬件和夹具记录，达不到则继续调优，不能把超时退出当成查询性能达标。

单页快速之外，必须验证全轮扫描完成时间、最老待检查记录延迟有界，并且服务能力足以覆盖新增变化量。线上观察至少 60 分钟，按相同批次和样本构成比较 15/60 分钟终态吞吐、供给空闲、API 等待年龄、数据库 I/O/CPU、失败率和发布延迟。不能拿累计 2374/小时作唯一对照，也不预先承诺翻倍。

完成定向 PostgreSQL/Redis、worker/controller 联合测试，再执行仓库要求的 `./scripts/test.sh` 与 `./scripts/verify.sh`。未执行的依赖测试明确记录，不能以 skipped 作为通过证据。

**9. 实施包、上线与回退**

| 实施包 | 主要文件/范围 | 交付物 |
| --- | --- | --- |
| A：基线和供给隔离 | controller.js、controllerLifecycle.js、migrationBatchControl.js、videoApiBatchRequests.js、数据库连接封装 | 分阶段指标、短循环、锁与连接预算、阻塞回归测试 |
| B：有界 Finalize 恢复 | finalizeRecoveryPolicy.js、finalizeDispatch.js、扫描状态及必要索引迁移 | 游标恢复、相同候选语义、规模测试与执行计划 |
| C：持久化变化登记 | Finalize 待检查 Module、集中写入口、兼容 schema/outbox | 原子登记、generation/租约恢复、历史回填与完整覆盖清单 |
| D：可观测性 | migrationBatchPanel.js、进度接口、聚合统计 | 滚动速率、等待原因、循环耗时与告警 |

实施顺序为 A+B 形成第一阶段可上线修复，D 同步提供观测；C 作为第二阶段独立上线，解决日常恢复随历史量增长的问题。每个实施包都提供代码差异、失败复现、通过结果和回退开关。

发布遵循 `docs/RELEASE.md`：提交精确源码，构建不可变镜像，核对 OCI revision，在隔离 smoke 环境跑通 Migration/Query/Incremental/Agent/Finalize/Publication。禁止将源文件复制进运行容器。

第一阶段先应用兼容的扫描状态/必要索引，再切换唯一 Controller 的 A+B 路径；与实际运行的 `controller-fullcrawl-canary` 容器及 Compose 归属核对，避免顺手启动旧 Controller。保留原批次和 40 个 Worker；有 API/Worker 共用契约变更时按兼容顺序发布所有受影响角色。恢复原批次供给即可验证，无须为测速另建大批次。

第二阶段先发布所有写侧登记，验证回填与登记完整性，再启用事件消费；保留有界轮巡。新旧消费者不同时争抢同一恢复职责。

回退按能力层次进行：事件消费有问题则回退到已验证的有界轮巡，保留事件记录及 generation；有界轮巡故障则停止该读取路径并保留进度，恢复已知版本时明确会重新暴露慢查询风险。恢复意图、Run、检查点、业务发布和新增兼容表不因回退被清除。新增索引/表通常保留，避免回退时再做昂贵 DDL。

触发停止推广/回退的条件包括：重复或遗漏有效发布、源版本保护失效、pause 后仍启动新频道、最老恢复年龄持续上升、数据库锁/连接明显恶化或 API 超预算。回退后重新验证单 Controller、同批次身份、续跑状态和数据一致性。

本方案完成后的判断标准：有资源有任务时供给持续；未完成数据继续等待；已完成及后续变化的数据都能可靠收尾；单轮检查成本受控；提速能用真实滚动吞吐和等待时间证明。


**10. 实施记录（2026-09-10，发布前）**

用户补充的约束：同一 Run、同一数据版本已检查并分发后，直接跟踪已有 Job，不周期性重复扫描视频内容。数据变化、Job 失败或丢失才重新评估。检查记录完成不等于业务 Finalize 完成。

实际实现：

- `controllerWorkLoops.js` 为补队列、结算、API、Finalize 扫描、变化消费、统计提供独立不可重入循环；独立连接预算与超时，停机先排空工作再关闭连接。连接源数据库同样设连接超时并在 Controller 退出时关闭。
- 每 2 秒维持最多 100 个冻结清单中的未启动任务，已有 Job ID 跳过。采用每轮补足缺口，不另设 40 的低水位，减少波动；已启动的 API 延迟续跑不占该窗口。
- 批次结算每 5 秒最多检查 200 个 started 项，持久化 ordinal 游标。running 且仍有 pending 时跳过持锁全量总数统计；pause/stop 使用既有 admission 屏障。
- API 每 3 秒派发，事务锁内核对全局 queued/running 上限，保留现有额度与重试规则。
- Finalize 每页先读最多 200 个 channel_id，再执行原业务筛选；游标在投递或持久登记成功后推进。事件模式下全局扫描只做历史回填/漏事件核对，每轮结束休息 1 小时；正常恢复消费变化记录。
- PostgreSQL 事务触发器覆盖 channels、channel_runs、content_candidates、contents、agent_profiles、crawl_observations，和源数据提交/回滚一致。channel_runs 排除纯 Finalize 状态/时间写回，避免自触发。
- 变化消费者跟踪 generation、租约、Run 和 Job 回执。未齐数据消费本次检查并记录 not_ready，后续数据变化重新唤醒；不将未齐 Run 标为完成。已分发同版本只查询 Job 状态；完成还需核对当前 Run 和实际 source_revision。
- 页面读小型索引采样，每 30 秒更新，显示最近 15/60 分钟结算量、详情抓取完成量和有效运行时速率；重试的多个 Run 按频道只计一次。样本不足与过期有提示。
- 开关默认关闭：`CONTROLLER_THROUGHPUT_ENABLED`、`FINALIZE_CHANGE_RECOVERY_ENABLED`。先应用身份校验的兼容 schema，再启用前者；确认后启用后者。数据库触发器使现有 Worker 写入也能登记，不要求同步更换 40 个抓取 Worker。
