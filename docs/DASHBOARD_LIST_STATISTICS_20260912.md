# 每日 Clock / 频道列表：分页与统计分离

## 根因与范围

每日 Clock 原先把全量统计、筛选总数和当前页同时请求，并等待三者全部成功。频道列表先查询全量统计及总数，再请求当前页。因此即使只打开第一页，也会触发全量扫描。

2026-09-12 原请求现场 616 ms 内返回 HTTP 200，但 HTML 显示“每日 Clock 数据当前不可用”。Dashboard 日志为 PostgreSQL `53100`，申请 2 MiB / 4 MiB 的 POSIX 动态共享内存失败。数据库容器 `/dev/shm` 上限为 Docker 默认 64 MiB；主机数据盘仍有约 118 GB 空余。不是请求超时，也不是频道数据消失。

## 实现

- 每日 Clock、频道列表的初始请求只读取 `limit+1` 条，返回前 `limit` 条，并独立判断是否有下一页。统计错误不再决定列表是否显示。
- 频道列表先用 MATERIALIZED page 固定当前页频道，再读取这些频道的候选信息、Clock、内容数量等详情。排序增加 channel_id，避免同一创建时间导致翻页顺序不稳定。
- 新增只读 `/api/daily-clocks/statistics`、`/api/channels/statistics`，沿用现有认证路径。前端单独加载统计，显示统计时间；失败保留列表及上次结果，可点击重试。
- 相同统计缓存 30 秒；过期后最多保留 120 秒旧值，并标示“上次统计”。并发相同请求合并一次计算，最多 128 个缓存项，后台串行执行，最多排队 8 个不同统计，失败有 5 秒冷却。
- 统计使用独立的单连接池，事务只读、20 秒超时；仅该统计事务关闭并行扫描。列表和其它业务查询仍使用原连接池。原有 Clock 运行期间刷新行为保留。
- 页面统计 SQL 口径保持原样，按归一化筛选参数区分缓存；分页 offset/limit 不会导致重复计算全量统计。UTC 调度日期进入缓存键，统计请求固定为原页面的目标日期。

## 200 MiB 共享内存

运行中数据库挂载已在线扩至 200 MiB，`df -h /dev/shm` 核验为 200.0M，未重启 PostgreSQL。`deploy/compose.yml` 的 crawler-postgres 已设置 `shm_size: 200m`。

在线 remount 不会修改 Docker 原容器的 HostConfig.ShmSize，它仍可能显示 64 MiB；实际挂载以 df/findmnt 为准。后续重新创建数据库容器必须采用更新后的 Compose 配置，不能继续使用旧工作树中的 64 MiB 默认配置。单纯重启旧容器可能重新按旧元数据挂载 64 MiB；这是在线变更与容器重建的区别，不应以删除共享内存文件代替配置更新。

## 验证与部署

- 3 项真实页面数据函数回归：统计故障不影响第一页，独立下一页判断、末页判断；在旧实现上先观察到失败。
- 4 项缓存回归：20 个并发观看者合并、缓存时间保持、慢刷新/失败时保留旧值、并发及缓存大小有界。
- 预上线浏览器对两个页面逐一验证：统计请求挂起时 5 行已显示；统计 503 时仍可翻页；重试后卡片恢复；重复请求缓存时间相同；下一页 offset 正确；无页面脚本错误。
- 默认 100 行正式请求核验：每日 Clock 509 ms，频道列表 4,186 ms，均 HTTP 200 且具备异步统计入口。缓存统计响应 30 ms / 11 ms。这是当前负载的一次样本，不保证固定耗时。
