# 批量迁移队列恢复方案

状态：核心恢复修复已于 2026-09-22 发布，版本 `4a74edc`。实施结果、验证证据和实际观察范围见 `reports/migration-queue-recovery-release-20260922.md`；以下保留设计与验收目标，不将目标本身作为验收证据。

## 问题与证据

新批次创建接口当前只直接恢复频道采集队列，下游 Agent、Data API 等队列依赖 Controller 主循环恢复。主循环读取 query_scheduler 后执行多项数据库工作，最后才改变队列状态。

2026-09-22 检查发现：新批次于 05:31:53 UTC 创建并处理了 3 个频道，控制器在 05:37:42 UTC 以 query_scheduler_stopped 为由暂停频道队列；此时数据库调度状态指向新批次且为 finishing。97 个采集任务及 1 个 Agent 任务滞留在暂停队列，10 个全量 Worker 在线就绪但空闲。相邻主循环记录间隔约 7 分 56 秒。

上述证据确认队列状态与新批次不一致。耗时循环沿用旧状态是待用并发回归验证的首要假设，不能将其未经复现写成最终根因。

## 目标行为

开始或恢复批次后，系统自动恢复该批次需要的整条处理链，并核验实际队列状态。无需重启 Worker，也不改变执行节点配置的并发量。

| 批次状态 | 新频道准入 | 已启动任务及下游处理 |
| --- | --- | --- |
| preparing | 准备清单；冻结完成后准入 | 可恢复所需消费能力 |
| running | 开启，受当前有效限流约束 | 开启 |
| pausing / stopping | 停止新准入 | 保持所需队列运行，完成已有任务收尾 |
| paused | 关闭 | 仅允许已授权的恢复或收尾需求；不得自动恢复批次 |
| completed（自然完成） | 关闭 | 消费队列保持开启、空闲待命；仍受容量和拓扑策略约束 |
| ended（人工结束） | 关闭 | 保留人工停止语义，Finalize 继续运行 |

批次状态、全局调度器状态、节点接单开关和队列消费状态是不同层次。监控应分别显示，不能用单个 stopped 推导所有 Worker 都已关闭。

## 实施方案

### 1. 统一计算应有队列状态

新增独立队列控制模块，读取当前批次、调度器版本、人工操作、恢复任务需求和有效期内的容量信息，输出队列应有状态与原因。

启动或恢复批次时覆盖频道采集、Agent、Finalize；Data API 仅在当前策略允许且存在相应需求时恢复。独立 content-detail 只在实际执行拓扑需要时启用。迁移不自动打开关键词发现或增量任务，也不解除节点维护暂停。

区分暂停来源：批次已完成、用户主动暂停、代理不可用、下游压力。新批次可替代上一批次的完成暂停，但不能无条件覆盖当前人工暂停和有效限流。不同原因应重新计算，不能只按 Redis paused 标志决定恢复。

### 2. 将队列开关移出耗时主循环

建立独立的轻量状态协调循环，建议健康情况下每 2 秒检查一次，启动/恢复/暂停/结束提交后立即唤醒。该循环只做有限的状态读取和队列控制，设置数据库与 Redis 操作超时，不执行批次全量统计或历史恢复扫描。

API、主调度循环和恢复后台任务统一提交控制意图，不再分别调用 pause/resume。所有全局队列开关必须走统一入口；既有增量队列控制保持独立。

控制器启动时先核对持久状态并恢复一致性，再报告控制通道就绪。通知仅用于加快响应，丢失通知由周期协调补偿。

### 3. 防止旧决策覆盖新批次

控制意图携带 pipeline_cycle_id 和单调递增的控制版本；同一批次暂停再恢复也必须产生新版本。不能只比较批次 ID。

队列变更通过一个有序应用通道串行执行。API 不再绕过该通道直接 resume。对同一队列，旧版本操作不得在新版本已应用之后生效；协调器执行前重读当前意图，丢弃过期决定。

仅在 pause 前再 SELECT 一次并不能消除检查与执行之间的竞争。实现必须明确覆盖整个应用顺序，包含 API、主循环、后台恢复以及多进程接管。若沿用共享锁方案，所有这些调用方都必须遵守同一锁协议，且锁内不能执行长时间业务查询；若使用租约接管，还须在 Redis 执行端拒绝旧持有者的迟到操作。通过真实 PostgreSQL/Redis 并发测试选择并验证实现，不能只靠内存互斥或源码字符串测试。

### 4. 持久化恢复意图与失败补偿

批次状态变更与恢复意图在同一数据库事务中提交。Redis 更新不宣称与 PostgreSQL 原子提交；应用失败保留待处理版本，后台幂等重试。

只有逐项读取队列实际状态并确认匹配当前版本后，才记录 applied。批次已创建而 Redis 暂不可用时，接口返回已有批次标识和“正在恢复/恢复失败原因”，不能以普通错误诱导用户重复创建另一批。

人工暂停、结束或创建新批次后，旧恢复请求自动失效。进程在提交后、开队列前，或开队列后、写 applied 前退出，重启后均能重新协调；重复执行不重建任务、不清空队列、不增加业务重试代次。

### 5. 可观测性

展示批次状态、所需队列实际状态、暂停原因、最近控制版本与应用时间、在线/就绪/忙碌 Worker 数量。数据库中的 finishing 不直接翻译为“所有队列正常运行”。

记录拒绝旧决策、恢复成功、恢复失败及重试原因。若批次允许运行、存在可消费任务且 Worker 就绪，但队列持续暂停，给出明确告警；人工暂停和有效限流不按误暂停告警。

性能验收目标：依赖健康且不存在人工暂停或有效限流时，开始/恢复后 5 秒内完成所需队列状态协调。该目标不是依赖故障时的无条件保证。

## 回归验收

1. 上批完成自动停止后，新批自动恢复频道采集及所需下游队列。
2. 用同步屏障让旧 Controller 在读取 stopped 后阻塞，再启动新批，释放旧循环；新批恢复后不得被旧决定重新暂停。
3. 同一批次暂停后恢复、恢复后立即暂停、结束与新批创建交错，最终状态均服从最新有效操作。
4. 主循环模拟卡住数分钟，独立恢复循环仍能及时生效。
5. Agent 原本暂停、存在待处理任务时可恢复，pausing/stopping 保持必要收尾能力。
6. 代理不足或下游压力仍有效时显示受限，不能被自动恢复绕过；条件恢复后自动解除对应限制。
7. Redis 断连、进程在不同提交阶段退出、通知丢失、重复请求及控制器接管，均能幂等恢复；旧执行者不能覆盖新版本。
8. 人工暂停的批次、节点维护暂停、增量接单及旧批次任务隔离均被保留。

## 发布与当前积压恢复

先完成并发复现、实现与回归，再协调更新 API 和 Controller，确保旧的队列写入路径不与新控制器同时运行。发布过程保留现有 Job、批次和执行中任务。

上线后重新读取现场，确认批次仍允许运行，再由统一控制通道恢复其所需队列。不得假定检查时的 97 个任务仍未变化，也不重建这 97 个任务。验收观察队列取消暂停、全量 Worker 获取任务、待采集数下降、Agent 消费及最终批次收尾。

回退保留任务数据和控制意图；若回退到存在旧决策问题的版本，必须明确重新出现误暂停的风险，不能仅重启 Worker 后宣称恢复完成。

## 主要改动位置

- `services/qybullmq/src/server.js`：批次创建/恢复入口提交并跟踪统一恢复意图。
- `services/qybullmq/src/migrationBatchControl.js`：批次状态变更与控制版本在事务内同步。
- `services/qybullmq/src/controller.js`：移除旧快照直接控制队列的路径，接入独立协调循环，统一后台恢复开关入口。
- 新增队列控制模块、必要的持久化迁移，以及真实 PostgreSQL/Redis 并发回归测试。

全量远程 Worker 和监督进程在队列空闲时继续运行；本方案不改变已部署 Worker 数量决定的节点并发规则。
