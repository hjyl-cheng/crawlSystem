# Incremental Video Activity Evidence Contract Fix

Release date: 2026-09-03

Branch: `codex/fix-activity-evidence-contract`

Code revisions:

- `dd9278a` - `fix(incremental): align activity evidence contract`
- `8c642b7` - `fix(feature): accept first-seen publication evidence`

## Problem

Incremental Video observations added `payload.activity_evidence`, but Feature
Engine still used an older strict Video payload contract. Its
`extra="forbid"` policy rejected the new top-level field with HTTP 422.

The crawler had already completed the YouTube requests and persisted the
observation. The permanent downstream rejection prevented the Video event from
being applied, so otherwise finished Daily Plans remained `running`.

The manually accelerated Clock test exposed the issue at scale; it did not
cause the contract mismatch.

## Root Cause

The producer and consumer had different ownership assumptions for the same
`event_version=1` payload:

- QYBullMQ treated `activity_evidence` as producer-owned lifecycle evidence.
- Feature Engine rejected every Video payload field it did not model.
- The default cross-service contract test did not cover the real producer
  payload and therefore did not stop the incompatible change.

A second compatibility gap was found during canary testing: producer-generated
`discovery.first_seen` entries can contain `published_at_status` and
`published_at_source`, while the Feature Engine contract did not accept them.

## Fix

### QYBullMQ producer

- Centralized construction and validation of `activity_evidence`.
- Strictly validates all current evidence fields, types, ranges, and count
  relationships before an observation is emitted.
- Uses the same validated evidence object for the crawler result summary and
  the Feature event payload.
- Added producer and lifecycle regression coverage.

### Feature Engine consumer

- Accepts `activity_evidence` as an optional, non-null JSON object.
- Preserves the object losslessly through parse, pending serialization, hash
  verification, and waiting-gap replay.
- Rejects non-object evidence and non-finite JSON numbers.
- Keeps the Video payload boundary and all fields consumed by Feature Engine
  strict.
- Does not recalculate lifecycle from evidence; lifecycle changes continue to
  use only the producer's `payload.activity` conclusion.
- Emits structured warnings when an incremental event that should contain
  evidence omits it, without rejecting compatible historical events.
- Accepts and preserves `published_at_status` and `published_at_source` in
  `discovery.first_seen`.

### Contract gate

- Added a default cross-service fixture generated by QYBullMQ and parsed by
  Feature Engine.
- Verifies deep payload equality and canonical hash equality across the service
  boundary.
- Covers future fields inside the producer-owned evidence object without
  weakening other Video payload validation.

## Compatibility Rules

- Missing `activity_evidence` remains valid for historical, Full, Repair, and
  incomplete-discovery events.
- Present `activity_evidence` must be a non-null JSON object.
- Evidence may exist without `activity`; this represents an inconclusive
  lifecycle decision.
- `activity` may exist without evidence for backward compatibility and emits a
  warning.
- Adding fields inside `activity_evidence` no longer requires a Feature Engine
  release while Feature Engine treats the object as opaque.
- Changes to `discovery`, `recent_sampling`, `activity`, or other Video
  top-level fields still require consumer-first compatibility or an event
  version change.

## Verification

- QYBullMQ target regression: 67 tests passed.
- Feature Engine focused contract regression: 55 tests passed.
- Cross-service contract gate: passed.
- Canary replay of a previously rejected event: `applied`.
- Historical failed Feature jobs: fully replayed; Feature queue `failed=0`.
- Recovered 2026-09-02 Daily Plans: 144 `succeeded`, 10 `partial`, 0 `running`.
- Video-only runtime sample: 10 plans completed, 9 `succeeded` and 1 legitimate
  `partial`; all 10 Feature events were applied.
- Smoke runtime: Feature Ingest healthy and three Incremental Workers running
  without restarts attributable to this change.

The one `partial` sample was a crawler-domain result
(`video_cycle_partial_failed` with all 20 recent samples failing), not a
contract or queue failure.

## Deployment Scope

The fix has been built and verified in the isolated smoke environment.
Production has not been changed by this release work. Promotion must rebuild
and deploy both affected images from the intended Git revision:

- `qybullmq-api` for QYBullMQ workers and producer code.
- `feature-ingest` for Feature Engine contract and ingest code.
