# 2026-09-12 远程增量吞吐修复

背景见 `INCREMENTAL_THROUGHPUT_RECHECK_20260912.md`。修复中心接单遥测、领取锁竞争，以及采样进一步确认的异步上下文泄漏。采集规则仍由同一 IncrementalChannelRunner、YouTubeJS、Rota 和 API 续跑实现负责。

## 根因和改动

1. `incrementalCoordinator.js` 每次运行创建 AsyncLocalStorage，却没有 disable。Node 20 会将已启用实例保留在异步钩子传播列表；频道越多，之后每次 Promise 创建付出的成本越大。中心 20.58 秒 CPU 样本：`_propagate` 9.113 秒、`promiseInitHook` 2.087 秒、GC 4.445 秒。现在成功/失败/交接退出均在 finally 释放该 Plan 的上下文；全局执行上下文不受影响。
2. `centerExecutionSupervisor.js` 原先每轮顺序执行 20 次 ready 事务，续写 15 秒 intake TTL。实测刷新间隔 34.7 秒，20 个在线只有 5–7 个有效标记。现在两条批量只读查询取得部署状态与精确 PostgreSQL 执行锁，统一刷新已存在的消费者。单次真正接单前仍核对数据库状态、部署身份和执行锁，事务内归属栅栏保留。ready 单槽检查合并为一次只读查询，消除多次事务往返。
3. `RemoteNodeStore.claim` 的受管理槽位使用共享节点状态锁。单独的节点容量 advisory transaction lock 保护槽位占用检查及新租约分配；不同槽位的心跳/网络归属读取不再等待领取流程的节点排他锁。受管理节点以 worker_connections 心跳记录为准，不再每次 claim 更新节点行 last_seen_at。旧无槽位协议仍维护原 last_seen。没有移除容量上限或代次保护，没有新增数据表。
