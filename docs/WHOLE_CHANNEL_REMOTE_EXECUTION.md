# Whole-channel remote incremental execution

Status: implemented and validated on isolated infrastructure, followed by a single production Worker rollout on 2026-09-13. A compatible center and additive schema are deployed; one Worker uses whole-channel execution while the others retain the previous path. Real About/video Clock completion, stored data and business publication have been verified. See [production rollout and recovery fix](WHOLE_CHANNEL_PRODUCTION_ROLLOUT_20260913.md), [same-host comparison](WHOLE_CHANNEL_LIVE_COMPARISON_20260913.md) and [actual remote-node validation](WHOLE_CHANNEL_WAN_VALIDATION_20260913.md). Fleet deployment defaults remain unchanged.

## Execution boundary

The center freezes the existing Clock Plan and video eligibility under the original business/execution fences in a repeatable-read transaction. It reserves ContentEnrich work using the original reservation helpers. The snapshot includes anchors, pending repairs, known videos, dispositions, recent candidates and the managed route budget. API keys remain on the center.

The node receives one `collect_channel` command. Within its existing managed YouTubeJS/Rota session it opens About, scans uploads, selects targets with the shared planner and collects details with the shared validation/retry/API policy. It fsyncs local checkpoints between videos; no per-video center command or SQL round trip is needed. First-seen work still precedes recent work, and pending API work stops this pass.

The node returns a logical channel result over NATS JetStream. Input and result frames have 512 KiB binary chunks and a 32 MiB logical limit, with exact size/hash/identity verification. The center persists received chunks and seals the complete receipt in PostgreSQL under the original task/business fence. It then reuses the existing checkpoint, content, observation, Agent and completion writers. Fully captured results use one video-domain transaction; failures and API handoffs keep the existing incremental checkpoints. Agent/publication/Finalize remain on the center.

The node still holds its normal channel slot while the center applies a normal completed result and closes the managed session. A durable receipt means received, not applied or published. API waiting releases the slot through the existing continuation mechanism. This implementation does not introduce a separate asynchronous application queue or promise immediate slot release on receipt.

## Restart and ownership

- A journal contains immutable input, delivery identity, About/scan/targets, video evidence, API outbox and the final result. Only one executor may own a spool directory.
- Restart discovers delivery journals even if the final upload pointer was never written. It uploads complete evidence or seals interrupted progress before normal network recovery. It never resurrects the lost browser identity.
- Exact durable receipt replay is idempotent. A stale unreceived execution is archived locally and cannot write under another generation. An upload still awaiting a valid receipt is retained.
- A request interrupted before fsync may need repeating. An expired generation cannot upload new evidence, even if it still has local data. These are at-least-once collection semantics with fenced/idempotent persistence, not exactly-once YouTube requests.
- Whole-mode node startup allows up to 256 MiB of spool space per Worker for the input, journal, assembled result and retained stale evidence. This is a disk limit, not a preallocation. Exceeding it stops intake instead of discarding unacknowledged data.
- When a center dies after receiving a complete result but before applying it, a newly admitted execution can carry that verified evidence in its own snapshot. It revalidates details against its own targets and writes under its own fence. Reuse is limited to the same immutable Plan and video cycle; incomplete cached details are fetched again. If including cached evidence exceeds the logical size limit, only this optional reuse is omitted.
- Applied whole-result payloads and frozen inputs are retained for seven days. The opt-in center prunes at most 64 candidate rows per minute, using task locks with `SKIP LOCKED`; raw crawler data and pending/failed/API-waiting payloads are retained. Input/result hashes and chunk digests remain so exact historical ACK replay still works. This clears duplicate payload values for PostgreSQL reuse; it does not promise an immediate reduction in filesystem allocation.

## Opt-in and compatibility

Both services default to the existing execution path. The center only chooses whole mode for a Worker advertising `youtubejs-incremental-whole-v1` and when its whole-channel store is enabled. Existing `youtubejs-incremental-v1` Workers continue using the existing command path. A live instance cannot change its advertised runtime revision.

Deployment requires the explicit `--whole-channel` schema option in `scripts/applyRemoteNodeSchema.mjs`, followed by `REMOTE_NODE_WHOLE_CHANNEL=true` on the center and selected NATS nodes. Startup does not migrate the database. The center refuses whole mode without NATS or the required tables. Deploy the compatible center before enabling a node; never replace an executing Worker to turn this on. No production Compose defaults or dashboard deployment defaults were changed here.

## Validation evidence

- Real TLS NATS + PostgreSQL: original About/video/mixed Plans, frozen snapshot reservations, multipart results, duplicate delivery, old-generation replay rejection and API outbox adoption. The 44-test run passed after repairing older test fixtures that had invented attempt IDs without corresponding execution records.
- A 30-video integration case used one input transfer and one result transfer, with zero center requests between detail calls. All 30 contents were persisted. After receipt reconstruction, the coordinator performed three fenced transactions. This measures control overhead with fixture YouTube responses, not real network throughput.
- Real node SIGKILL: after a video checkpoint and after result fsync but before the upload pointer; lost final ACK; API-outbox/item-checkpoint gap; stale generation; receipt cleanup. Seven recovery tests passed, including revalidation of cached detail evidence.
- Managed runtime + local Go Rota relay + actual NATS/PostgreSQL: country recheck with and without a Brazilian reserve, network failure handoff, API wait while another channel executes, and API continuation into the untouched next video. The focused 16-test run passed. Rota management responses and YouTube responses are controlled fixtures; the local relay/session/transport and original state writers are real.
- Production-image Node 20, networking disabled and source mounted read-only: the final 107 unit/trial/recovery/snapshot tests passed without skips.
- Separate PostgreSQL databases: 15 Full Crawl → incremental, pending repair, dormancy, API checkpoint, schema and execution-fence tests passed.
- Center startup and mixed runtime activation/supervision: four integration tests passed, including whole-mode startup and exact runtime identity checks. An older supervisor-crash test initially timed out in a combined run; its isolated rerun actually executed the child-process crash and passed. A filename-only name-filter run did not execute its subtests and is excluded from these results.
- Real BullMQ + PostgreSQL + NATS + local Go relay: six scenario subtests (seven including the parent) passed for both old and whole modes: original Clock completion, API waiting while another queued channel runs, and country handoff during graceful shutdown. The first whole-mode fixture omitted the NATS activation service and could not admit work; wiring the same activation service used by the actual center resolved it.
- Real center SIGKILL at five boundaries, including whole About receipt and whole video receipt before application: all five scenario subtests (six including the parent) passed. BullMQ redelivered the original job, a new fenced owner completed it, and the two whole-receipt cases made no repeated YouTube fixture calls and produced one original business observation each.
- Result retention plus the center-entry regression run passed 31 tests: recent and pending payloads survive, old applied payloads are cleared, and exact historical receipts remain valid. The entry test restores its temporary broker ACL before subsequent tests.

## Before fleet rollout

Controlled real-channel comparisons using equivalent Clock masks, video targets and routes have passed on isolated infrastructure, including an actual remote node with disk-backed checkpoints, real Rota routes and the original BullMQ processor. The compatible center and one drained production Worker have now been deployed; normal Daily Clock completion through Feature ingestion and business publication passed. Continue observing this scope before fleet rollout. The cross-host diagnostic did not exercise Dashboard installation or production supervisor activation. Completed whole receipts have an end-to-end center-SIGKILL recovery test. This does not guarantee zero recollection for an unreceived result, expired lease, corrupt/incomplete evidence or oversized optional replay input.

Small receipt identities follow task retention through cascading foreign keys; large successfully applied payloads use the bounded seven-day policy above. Failed/pending payload retention should be evaluated separately from successful-payload cleanup. Journal tests establish process-crash recovery, not storage-device loss or sudden host power-loss guarantees. Confirm deployment configuration and image identity on the selected node before enabling either opt-in in production.
