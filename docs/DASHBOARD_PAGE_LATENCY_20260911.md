## 查询计划证据

### 迁移列表

`migrationInventory.js` 的第一页查询虽然使用 `(source_id, priority, source_candidate_id)` 排序索引，却必须关联迁移意图、候选、频道、最终状态，才能判断这条是否仍属待迁移。

一次 EXPLAIN ANALYZE 显示：

- 返回 50 行前，从库存索引实际扫描 63,023 行。
- 完成关联后过滤掉 62,973 行。
- migration intents、candidates、channels、finalized profiles 的对应索引查询各执行 63,023 次。
- 该次分析总计 33,116 ms；主页面独立查询设置 20 秒超时，因此负载或缓存不利时会显示列表不可用。
- 汇总查询另外关联约 48.6 万库存的估算范围，扫描多张约 15 万行的目标表。

这不是 LIMIT 没写，而是过滤条件依赖其他表，排序靠前的大量已处理记录必须先逐条排除。迁移完成越多，这条路径越容易变慢。

### “迁移频道列表当前不可用”错误链路核实

- 本轮检查 Dashboard 最近 3 小时日志，匹配 `migration channel inventory read failed` 的 4 条错误全部为 `canceling statement due to statement timeout`。此结论限定在检查窗口内。
- `migrationInventoryRead.js` 在只读事务中显式设置 `statement_timeout='20s'`。`migrationInventory.js` 并行等待列表和全量汇总，任一抛错都会让 `server.js` 的 `migrationChannelListData` 返回 `available:false`，页面显示上述通用提示。HTTP 状态仍可能为 200。
- 再次读取已保存的实际执行计划（没有重跑慢查询），确认迁移意图、候选、频道、最终发布状态各发生 63,023 次索引查询，之后过滤掉 62,973 条，才由 LIMIT 返回 50 条。内容计数只对返回的 50 条执行，不是本次扫描放大的位置。
- 根因是当前状态要跨表计算，现有索引只支持原清单的顺序，不能直接定位仍待处理的记录；第一页也必须反复检查排序靠前的已处理记录。仅增加普通排序索引或取消统计等待，均不能消除这个列表查询问题。
- 相同查询路径测得约 12 秒和 33 秒，跨过 20 秒阈值即可解释时好时坏。缓存和并发数据库负载的各自贡献尚未量化，不将其认定为网络故障、锁阻塞或硬件不足。

本轮定位完成，尚未实施页面查询修复；未修改采集流程、业务数据或部署配置。

### 每日 Clock

`dailyClockListData` 对相同 scope 分别查统计、总数、列表。scope 对每个 active Clock 使用 LATERAL 查询挑选当日/活动 Plan，随后关联 outbox、Run、channel。列表本身较快，两个完整统计决定页面延迟。默认无筛选时总数与统计卡片 total 还存在重复计算。

### 频道列表

`channelListData` 串行执行两条统计与 `channelSummaryRows`。列表执行计划先顺序扫描 active channels 并按 created_at 排序，再关联结果；当前排序没有直接走适配的索引。每个返回频道还分别统计全部、普通、Shorts、Live 内容。

### Query 词库

本次默认页面返回空词列表，未复现用户看到的卡顿。它仍串行执行词组统计、总数、列表、多项调度统计；不能据此认定在有待调度词、不同筛选或数据库拥堵时也同样快。经公网的未认证 GET 返回登录重定向，不能拿该响应时间代表用户登录后的页面时间。

## 后续优化范围

1. 将首屏列表与汇总统计解耦，列表不等待全量统计；汇总异步加载并显示更新时间，支持短期复用。
2. 迁移列表以可索引的待迁移状态清单读取；状态变化由现有迁移事件同步。要验证一致性、恢复和重建，不能在查询中直接跳过已处理 ID，否则会漏掉旧 ID 上的失败重试。页面展示状态仍按原规则核对。
3. Clock 先批量选出目标日/活动 Plan 的范围，再做关联，消除对每个频道重复执行的 LATERAL 选择；无筛选时复用汇总的总数。
4. 频道页先按匹配过滤/排序的索引挑出本页频道，再补 100 个频道的详情；四项内容计数合并。默认统计可复用且独立加载。
5. Query 词库继续针对实际慢请求和筛选条件测量，减少重复统计和无必要的串行等待。

本轮查询均已结束，没有留下常驻诊断进程。诊断复用了生产读取条件，没有修改调度、迁移/增量采集、任务队列或接单配置。
