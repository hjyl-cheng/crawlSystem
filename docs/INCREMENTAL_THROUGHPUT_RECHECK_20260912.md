## 已确认：接单容量标记过期，派发器少算 Worker

- 节点 01 共 20 个登记/在线/enabled/activation_requested/accepting，中心本地 20 个允许接单为 0。
- `workerIntakeTelemetry.js:6` 为每个消费者写 Redis intake 标记，TTL 15 秒。
- `centerExecutionSupervisor.js` 的 tick 按顺序遍历每个 Worker，先 await ready（SQL 事务及归属锁检查），再续写标记；没有独立的整批容量更新。
- `dynamicDispatcher.js` 的 incrementalWorkerCapacity 仅将值为 `1` 的标记计入容量，已过期键不计入。
- UTC 03:03:08–03:03:43 连续 35 次采样：20 个消费者均在 Redis 连接列表，只有 **5–7 个**有效标记，**13–15 个**标记过期。采样结束数据库仍确认全部 20 个在线并启用。

- 同期队列 active 从 19 降至 17，waiting 始终 0。标记失效不会中止已领取任务，因此 active 可以大于派发容量。
- 前序派发日志也将 capacity 计为 10–13；在现行 buffer=2、minimum_share=0.7 和迁移有积压条件下，增量队列目标为 14–19，单轮仅补 1–3 个。

这是具体的接单遥测/派发问题，不是用户把允许数量改小，也不是频道没有到期（尚有约 3.93 万 eligible Plan）。验证脚本 `/tmp/intake-window-20260912.mjs`。

## 同时确认的中心压力

- qy-remote-node-center 实际 cpu.max 为 `100000 100000`（1 核）；多个样本 CPU 约 97%–99%。两个 cgroup 样本相隔 419 个配额周期，CPU 使用增加 40.65 秒，244 周期被限速，throttled 时间增加 30.32 秒。配置见 deploy/compose.remote-node-center.yml。
- 领取任务仍在 `RemoteNodeStore.claim` 内持有节点级 `FOR NO KEY UPDATE` 行锁，覆盖多条容量/归属查询和 last_seen 更新。现场多次捕获其他领取请求和心跳等待此锁；共享读取已优化，但独占领取路径仍造成竞争。
- PostgreSQL 后台 `publication-auto-onboarding:backlog` 同一 SQL 先后已运行 78 秒和 151 秒，等待 DataFileRead，另两个并行进程等待 MessageQueueSend。中心主机多次 CPU 忙约 80%，磁盘读取明显；这是资源竞争证据，尚未量化该扫描对增量吞吐的独立贡献。
- 中心未重启，仍偶发 STALE_LEASE 执行重试；不能把全部租约失败归因于某条 SQL。
