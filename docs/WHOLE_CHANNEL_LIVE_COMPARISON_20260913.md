# 整频道远程执行：真实 YouTube 对照

2026-09-13 UTC 完成。两组真实频道、每组新旧两次执行的最终测试全部通过（4 个子测试，含父测试共 5 个）。生产模式未启用，线上 Worker、Clock Plan、迁移任务及采集数据未修改。

## 测试范围

- 临时 PostgreSQL、TLS NATS/JetStream 和结果目录。所有业务和浏览器身份记录写入临时库，测试后删除临时服务。仅通过正式 Rota 管理接口申请一个独立诊断槽，结束后释放。
- 真实 YouTubeJS About、上传列表、视频详情及评论请求；使用原指纹网关和共享采集函数。没有合成成功响应，没有调用生产 API-batch。
- 中心协调器和采集执行器在同一主机运行，通过实际 NATS/JetStream 和数据库交互；网络身份使用 `ChannelExecutionRuntimeAdapter` 的真实 Rota 诊断会话。本轮不是远程服务器完整部署验收，也没有测公网节点到中心的延迟。
- 使用 Node 26.7.0、仓库依赖和 curl-cffi 0.15.0。上一阶段已经独立验证生产镜像 Node 20 的 107 个单元/恢复/快照测试；不能把两种运行时的验证混为一次。
- 同一 Rota 槽、同一出口代次，最终一轮出口为 NL。顺序为样本 A 旧→新、样本 B 新→旧，减少先后顺序影响。
- 两组均为 About＋Video、Agent 不到期。先实际读取上传列表及必要的详情，把第四条视频的真实 ID 和发布日期作为双方相同的存量锚点；准备阶段不计入采集耗时。列表真实命中锚点后进入详情，没有强行把不完整扫描改成完整。
- 样本 A：3 条首次发现＋1 条存量复采。样本 B：3 条首次发现，锚点视频按原策略未被选为复采。每条路径实际请求 7 条详情，两条路径合计 14 次；每组库里另有预置锚点，不能把所有存储行数当作新增采集量。

首次预检查没有提供历史锚点，一页扫描按原策略返回 partial、未取详情；另一轮锚点准备遇到列表不带发布日期，改从真实详情取得。两者是测试输入准备问题，没有更改业务扫描或完整性策略。准备完成后连续两轮新旧对照均通过，以下使用增加字段断言后的最终一轮。

## 最终结果

| 指标 | 样本 A 旧路径 | 样本 A 整频道 | 样本 B 旧路径 | 样本 B 整频道 |
| --- | ---: | ---: | ---: | ---: |
| 总耗时 | 7.077 s | 6.043 s | 5.535 s | 5.004 s |
| About 调用 | 0.638 s | 0.576 s | 0.503 s | 0.524 s |
| 列表调用 | 0.629 s | 0.509 s | 0.441 s | 0.430 s |
| 详情调用合计 | 3.764 s | 3.717 s | 2.912 s | 3.065 s |
| 总耗时减上述 YouTube 调用 | 2.046 s | 1.240 s | 1.679 s | 0.986 s |
| 相邻详情之间等待合计 | 0.565 s | 0.018 s | 0.346 s | 0.016 s |
| 最后详情返回至中心完成 | 0.405 s | 0.580 s | 0.591 s | 0.585 s |
| 记录到的数据库调用 | 1,091 | 452 | 952 | 428 |
| 采集指令数 | 6 | 1 | 5 | 1 |
| 结果上传调用数 | 6 | 1 | 5 | 1 |

整频道模式的输入读取约 18 ms、结果上传约 61–64 ms。上传后还需要中心应用结果，不能把上传 ACK 当作已完成入库/发布。此处 Agent 不到期，没有运行 Agent 和搜索发布。

总耗时分别减少约 **14.6% 和 9.6%**。扣除 YouTube 调用后的其他耗时分别减少约 **39% 和 41%**。数据库调用计数分别减少约 **59% 和 55%**。测试记录的是通过 Promise 获取的数据库连接上的 SQL，包含事务控制、栅栏及会话记录；不包含所有 callback 形式的 Pool.query，因此不是整个 PostgreSQL 服务的总 SQL 数量。并发 SQL 耗时和 RPC 等待存在重叠，不能与总耗时直接相加。

两个模式都保留 NATS 心跳与任务状态通知。旧模式的 `pollCommands` 实际是 NATS 等待通知，并非 100 ms HTTP 轮询。整频道模式避免的是逐条视频的指令/结果往返和中心处理等待。

## 数据核对

- 两组目标 ID、详情请求顺序和保存的视频 ID 一致，无重复详情操作；About 和 Video 均由原中心逻辑记为 complete。
- 对实际请求的视频，标题、缩略图、发布日期、时长、播放量状态、点赞状态、评论状态和描述状态均通过断言；新旧的视频类型、描述、标签、关键词、时长、日期及核心字段状态一致。包含视频、Shorts、新视频和存量视频复采。
- 最终一轮播放量、点赞数和评论数也相同。前一轮一个视频的播放量从 1,183 增至 1,186，属于两个请求时点的变化，不是少存字段。
- 评论首屏返回数等于数组长度、评论 ID 不重复。额外逐条对比确认评论 ID 集合、作者及正文一致；允许排序位置、采集时间和相对发布时间换算存在变化。
- 频道 About 的外链、标签状态为 observed，总播放量和视频数量状态为 exact；订阅量沿用页面取整数的 estimated 状态。
- 预置锚点不是本轮新增数据。没有把未请求的样本 B 锚点行当成已完成详情，也没有把 Agent 的 pending 状态当成采集错误。

## 复现

入口：`services/qybullmq/scripts/compareRemoteWholeChannelLive.mjs`，用例：`services/qybullmq/test/remoteWholeChannel.live.integration.test.js`。默认测试集会跳过真实请求，只有此显式入口启用。

在已有 Rota 诊断环境变量、Docker 和 Python 指纹网关依赖的环境中执行：

```bash
node services/qybullmq/scripts/compareRemoteWholeChannelLive.mjs \
  --channel-id '<channel-A>' \
  --channel-id '<channel-B>' \
  --report /tmp/whole-channel-live-report.json
```

凭据只通过环境配置，不能写入命令示例、仓库或公开报告。报告保存在调用者指定的私有路径。临时测试启动器显式把 `DATABASE_URL` 指向其新建的隔离库，避免共享模块意外读取外部数据库默认值。测试会重置自己的业务表，必须通过隔离库检查才能运行。

本轮原始报告与日志在执行主机 `/tmp/whole-live-final-report.json`、`/tmp/whole-live-final.log`，均未加入仓库。

## 尚未证明的内容

这些是低并发小样本，不能直接换算 40 个 Worker 的增益。真实远程节点的镜像/环境切换、公网结果传输、长时间并发和更大频道需要下一阶段观测。API 等待、国家出口切换及崩溃恢复由前一阶段隔离集成测试覆盖，本轮没有再次在真实频道上制造这些故障。

本轮只增加可重复测试入口并补充证据，没有修改采集策略，也没有把整频道模式开启到生产。
