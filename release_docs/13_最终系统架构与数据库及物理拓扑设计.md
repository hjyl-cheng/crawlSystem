# 13 最终系统架构、数据库架构与物理搭建拓扑

状态：推荐方案与团队评审稿，尚未实施。编写日期：2026-09-14（UTC）。本文件复用 [01 当前基线](01_目标范围与系统基线.md) 的源码与现场快照，没有重新采样现网，也没有修改代码、配置、数据库或运行服务。

本文回答三个问题：长期应该建成什么系统；数据库怎样支持持续增长；近期与最终分别怎样放到物理服务器上。它收敛前 12 份文档的方向，不将待开发能力描述成现网功能。

## 一、推荐的最终形态

建议建成一个“统一管理、按频道归属执行、采集与数据处理可独立扩容、事务与分析分离”的爬虫平台。

长期有两条业务链路：自发现链路负责发现新频道并执行首次 Full Crawl，增量链路负责维护已有频道。执行层明确分成三个可独立扩容的集群：发现集群、Full Crawl 集群、增量集群。发现集群通过持久的“待 Full Crawl 任务池”向全量集群提供工作，不固定绑定某台全量机器。它们共享同一套频道身份、采集规则、数据一致性和发布契约。

最终应具有以下能力：

1. 管理中心负责配置、全局预算和任务归属，重采集与大范围统计拥有独立运行资源。
2. 发现、Full Crawl、增量、Agent、结果应用、业务发布分别配置处理能力，某个角色繁忙时不拖垮其他角色。
3. PostgreSQL 保留任务、检查点、当前状态与业务版本等事务数据；大范围历史分析进入独立 OLAP，原始证据进入对象存储。
4. 每个频道有明确的数据归属，规模增大时按频道增加采集数据库分片，并配套该分片的调度、队列和结果处理能力。
5. 核心持久服务具备主备或集群容错；节点失联、中心重启、消息重复均能在原规则下恢复。
6. 系统能根据积压和资源情况减少新接单，长期处理得过来，而不是用无限队列隐藏过载。
7. 数据有保留、归档和恢复规则，不把所有历史永久累积在同一热库里。

这是有明确演进路线的目标，不是“增加机器就能保证稳定”。稳定性最终需要由持续负载、故障恢复和数据核对共同证明。

### 推荐取舍

| 问题 | 本文建议 | 原因 |
| --- | --- | --- |
| 近期是否更换事务数据库 | 继续 PostgreSQL | 保留已有 SQL、事务、执行锁和恢复契约，先隔离与优化 |
| 自发现与增量是否独立部署 | 是，分别管理采集和下游预算 | 避免首次全量任务挤占日常维护时限 |
| 发现和 Full Crawl 是否分别集群化 | 是，中间使用持久候选任务池与可恢复派发 | 多个发现生产者和多个全量消费者分别扩容，保留资格反馈 |
| Full Crawl 是否继续保留 | 长期保留 | 自发现的新频道仍需首次全量；迁移只是阶段性来源 |
| 中心是否立即全面多活 | 先做职责拆分与可验证接管，再扩大多实例职责 | 已有部分锁机制不等于所有中心功能都能多活 |
| 长期是否支持数据分片 | 是，提前确定频道归属边界，按证据启用 | 数据与写入持续增长，不能把全局主库设为永久无限容量 |
| 是否让 OLAP 替代业务 PostgreSQL | 不整体替代；增加独立分析读模型 | 业务发布版本和当前状态仍有事务要求 |
| 是否统一远程采集协议 | 增量沿用现有协议；Full Crawl 远程化独立评估 | 当前 Full Crawl/Discover 仍直接访问基础服务 |
| 是否立即引入 Kubernetes | 不是本轮前提 | 先建立可部署、可恢复的角色边界；调度平台不能修复业务归属和数据库瓶颈 |

## 二、为什么当前系统需要这样演进

2026-09-14 约 01:57～01:58 UTC 的快照显示：中心宿主机可见 16 个逻辑 CPU、约 31.3 GiB 内存；同机有采集库、业务库、40 个 Full Crawl 容器、远程中心、消息层与后处理等服务。45 个远程整频道增量 Worker 已登记并允许接单，本地 20 个增量 Worker 未接单。

采集库约 133.8 GiB，业务库约 71.5 GiB；根文件系统约 93% 已用、剩余约 40G。远程中心容器限制为 1 CPU/768 MiB。上述是快照，不是资源峰值或吞吐测试。

这说明近期至少需要处理资源共置、存储余量和中心处理预算。它不证明“45 个连接导致网络堵塞”，也不证明 PostgreSQL 已达到自身极限。数据库复制到独立机器、停止不必要的写放大、缩短事务或隔离统计，可能比立刻引入分布式数据库更有效。

已有整频道模式减少了采集中途与中心的交互，但正常结果应用和网络收尾仍占用节点槽位。因此最终设计要同时考虑采集能力、入库能力和槽位周转。

## 三、整体逻辑架构

```text
                         用户 / 运维 / 业务系统
                                   |
                        管理入口与全局控制服务
                 配置、查询词、节点、归属、预算、审计
                                   |
                   +---------------+----------------+
                   |                                |
                   v                                v
              自发现业务链路                    增量业务链路
         评分集群 -> Discover 集群              Feature / Clock
                   |                                |
              候选去重、初筛                     冻结 Plan
                   |                                |
           持久待 Full Crawl 任务池                  |
           可恢复派发、资格结果反馈                  |
                   |                                |
              Full Crawl 集群                   增量采集集群
                   |                                |
                   +---------------+----------------+
                                   |
                      按频道归属交给相应采集分片
                                   |
          +------------------------+------------------------+
          v                        v                        v
    采集分片 1                采集分片 2                采集分片 N
    本地任务调度              本地任务调度              本地任务调度
    队列 / 执行协调           队列 / 执行协调           队列 / 执行协调
    结果应用 / 事务库         结果应用 / 事务库         结果应用 / 事务库
    检查点 / 观测 / Clock     检查点 / 观测 / Clock     检查点 / 观测 / Clock
    后处理 / 发布出口         后处理 / 发布出口         后处理 / 发布出口
          |                        |                        |
          +------------------------+------------------------+
                                   |
                          原认证业务发布链路
                                   |
                          业务当前态与查询服务
                                   |
                       增量同步到业务分析读模型

配套：受管代理/Rota、NATS 运输、对象存储、运营分析、监控和备份
```

图中“归属”是路由关系，不表示在采集完成后才选择数据库。目标方案中应在任务派发前确定频道归属及路由版本，后续检查点、结果、重试和发布沿同一归属处理。

初期可以只有一个采集分片，并继续复用原 schema 和事务。多个采集分片、分片内 Clock/队列和全局目录属于后续开发，不是现在已经存在的服务。

### 3.1 全局控制服务应保持轻量

长期集中管理的内容：节点注册、配置版本、能力、查询词和发现周期、频道归属目录、分片健康、全局 API/代理预算、发布目的地、操作审计。

高频执行状态应尽量由所属分片处理。全局服务读取汇总与容量信息，不对每一条视频获取详情、每一次结果写入做集中事务仲裁。节点登记与部署身份可以全局管理，执行心跳和热路径状态如何落到分片需专门设计，避免再次出现全局热点行。

全局控制数据库初期可仍位于当前采集实例中。只有拆分收益和事务边界明确后，才迁为独立库；不能先把参与同一原子事务的表拆到两台机器。

### 3.2 调度与执行分开，但不重复调度

管理层决定允许哪些工作、每个分片可以接多少；分片内调度负责真实的 Run/Plan、去重、执行代次和重试。全局层不再复制一套同名频道任务状态机。

Full Crawl 与增量可使用独立执行机器，任务仍由相应队列和原业务契约管理。单个 Worker 可以按设计在不同任务间服务不同分片，但一次执行的频道、分片和归属版本必须固定。

Query Quality 和 Discover 都按可多消费者执行的角色设计，初期可共用机器，但不是只能有一个 Discover 实例。发现集群与 Full Crawl 集群分别部署，前者生产候选任务，后者领取全量任务。任务体大、访问数据库频繁的 Full Crawl 先放在与数据服务低时延互通的可信私网；是否改成像增量一样的无数据库凭据远程执行，是独立工程项目。

### 3.3 发现集群与 Full Crawl 集群之间的任务池

推荐拓扑如下，箭头表示经持久任务与消息协调，不是发现节点直接调用某个 Full Crawl 容器：

```text
                    查询词与发现分页任务池
                              |
              +---------------+---------------+
              v               v               v
        DISCOVER-01     DISCOVER-02     DISCOVER-03..N
        查询/分页 A     查询/分页 B      其他可执行查询
              |               |               |
              +---------------+---------------+
                              |
                   按频道去重、保存来源与初筛证据
                              |
                 +-----------------------------+
                 | 持久待 Full Crawl 任务池    |
                 | 候选、待验证、派发代次      |
                 | 优先级、重试、归属、状态    |
                 +-------------+---------------+
                               |
                    可恢复派发 / BullMQ
                               |
              +----------------+---------------+
              v                v               v
        FULLCRAWL-01     FULLCRAWL-02    FULLCRAWL-03..M
        领取频道 A       领取频道 B      领取其他频道
              |                |               |
              +----------------+---------------+
                               |
                     数据、检查点与资格结果
                               |
                 +-------------+---------------+
                 |                             |
                 v                             v
          后处理 / 发布                 原发现页面资格收口
                                              |
                                    决定继续翻页或停止
```

因此业务上是“自发现完整链路”，执行上是发现生产者集群与全量消费者集群；两个集群的节点数不需要相同，也不需要一对一绑定。

**当前已有的基础。** `worker.js` 的 Discover 路径写入 `crawler.channel_candidates` 和 `crawler.channel_candidate_sources`，分配 `snapshot_dispatch_generation`，然后向 `youtube-channel-crawl` 投递任务。Full Crawl 消费原队列。这是现有的候选持久化与队列交接基础，不必另外发明一套全量业务表和执行器。

**“待 Full Crawl 列表”应是逻辑任务池。** PostgreSQL 保存候选、来源、状态和执行归属等权威事实，BullMQ 负责任务投递与消费者领取。页面上的待处理列表是这个任务池的视图。不能只把频道 ID 放进内存数组，也不能让多个消费者先 `SELECT pending` 再无条件改状态。优先复用现有 BullMQ 领取与业务栅栏，只有采用数据库领取时才设计原子锁定/条件更新及租约。

任务池至少要能回答：频道是什么、哪些查询/页面发现它、当前准入证据是否完整、属于哪个分片、哪次合法全量执行负责、是否已投递、何时可重试、最后失败原因，以及哪些上游页面需要接收资格结果。

**集群化需要保留以下约束：**

| 边界 | 设计要求 |
| --- | --- |
| 查询分配 | 多发现 Worker 并行处理不同词或已满足前置条件的页面；同一 continuation 链不能任意并行制造后续页 |
| 页面所有权 | 领取与重试保留原页面意图、业务执行归属和 Rota 身份，不靠机器名判断唯一执行 |
| 候选去重 | 多关键词/页面发现同频道时保留各来源，同时合并应共享的执行；资格、批次和重试语义不能被一个永久布尔去重标记替代 |
| 全量领取 | 对同一频道和合法执行代次只接受有授权的业务写入；重复交付可恢复，不要求外部网络请求绝不重复 |
| 持久化与投递 | 候选提交后进程退出、Redis 写入失败、ACK 丢失都应能对账补投；检查首次派发与重派各自的事务边界 |
| 资格反馈 | Full Crawl 产生的 accepted/existing/rejected/failed 等资格结果按原规则推进关联发现页面，不另造一套筛选口径 |
| 失败恢复 | 发现节点掉线由原页面任务恢复；全量节点掉线由原 Run/检查点恢复，不把整个查询周期从头重跑 |
| 流量控制 | 发现速率受待全量积压与后处理预算控制，避免长时间只增加候选而不能完成采集 |

当前 schema 的候选唯一约束包含 `(dispatch_batch_id, channel_id)`，不能由此宣称跨所有批次的全局去重已经完成。已有频道检查、候选批次约束、业务执行栅栏与未来频道目录需要共同核对。特别是多发现批次同时命中同一尚未入库频道时，应补并发验证。

当前首次 Discover 派发路径包含数据库状态分配后调用队列 `addBulk`；相关重派路径已有持久 Outbox 机制。集群化验收需要核对首次投递中断能否被现有恢复覆盖，不能因为某条重派路径有 Outbox 就推定所有派发都在同一原子边界内。

**现有分页并非完全脱离 Full Crawl。** Controller 的 `resolvePendingDiscoveryPageQualifications` 会等待关联候选退出 `discovered/queued/validating`，再按资格比例、错误和 continuation 决定继续或停止。因此候选入池后可以让其他查询并行推进，但不能无视某页资格未决状态就无限翻页。物理集群解耦不意味着删除业务反馈。

发现任务池与待全量任务池应分别设置容量与公平性。建议按词/发现周期限制在途页面，按候选数量、最老等待年龄和预估工作量限制新发现；全量积压高时减少新查询，保留资格反馈与恢复处理能力。不能要求精确做到发现速率永远等于全量完成速率，但长期必须可消化且有界。

未来多数据库分片时，“一个待全量列表”是统一逻辑视图，不必是一张无限增长的全局热点表。频道先确定归属，再向相应分片投递执行候选；全局发现来源和分片资格结果通过幂等、可恢复的通知协调，避免控制库与分片库之间出现候选丢失窗口。

第一轮集群验证至少覆盖：多发现节点同时命中同频道；候选落库后投递中断；多个全量节点并发领取与失权；某页资格待定时其他查询继续推进；Full Crawl 暂停后发现受到背压；恢复接单后候选与页面都能正常收口。

源码依据：[Discover 执行和投递](../services/qybullmq/src/worker.js)、[候选派发与代次](../services/qybullmq/src/channelSnapshotDispatch.js)、[候选结构](../services/qybullmq/src/schema.sql)、[资格收口](../services/qybullmq/src/controller.js)、[分页策略](../services/qybullmq/src/discoveryPagePolicy.js)、[资格就绪唤醒](../services/qybullmq/src/discoveryPageWakeup.js)。

### 3.4 后处理不能成为隐藏的中心瓶颈

Agent、Finalize、发布与业务 Projector 需要独立的并发、积压和资源监控。它们可以先共用一台后处理服务器，再按计算与 I/O 负载拆分。

长期多分片时，后处理应按频道所属分片读写，并保留发布顺序。不能让每个分片的全部视频都汇聚到一个无限扫描全库的 Finalize 或全局 Projector 进程。

## 四、数据库架构设计

### 4.1 数据库分层

| 数据层 | 推荐技术方向 | 保存内容 | 扩展边界 |
| --- | --- | --- | --- |
| 全局控制 | PostgreSQL，最终主备 | 节点、配置、归属目录、全局策略和发现协调 | 小体积控制信息；高频执行状态下沉 |
| 采集事务层 | PostgreSQL，单分片起步、按频道增加分片 | Run/Plan、内容、检查点、观测、Clock、结果应用与发布状态 | 同频道事务尽量在一个分片 |
| 业务在线层 | PostgreSQL，独立于采集，按需求主备/读副本 | 发布接收、版本、当前投影、详情及在线筛选 | 自己的读取和写入预算，不强制与采集分片一一对应 |
| 分析层 | 优先验证 ClickHouse 等列式 OLAP | 任务历史、指标趋势、业务聚合、榜单 | 独立机器、独立同步与查询配额 |
| 对象层 | 继续兼容现有 MinIO/S3 接口 | 原始证据、归档、最终载荷 | 容量与耐久性独立扩展 |
| Rota 状态 | 保留兼容的 PostgreSQL/TimescaleDB 部署 | 代理、Slot/Lease/Route 与相关管理状态 | 独立资源和恢复方案 |

不同层是数据职责，不意味着每层都立即部署新库。近期先把现有采集库和业务库放到独立资源上，再逐步拆分控制与分析数据。

### 4.2 每个采集分片保存什么

目标分片内部保留同频道的一组相关数据：频道与内容当前状态、候选与处置、Full Crawl Run、增量 Plan 与视频周期、检查点、观测、待应用结果、频道侧发布 Revision/Outbox，以及相应 Clock 状态。

全局发现来源与频道执行候选要区分：查询词和发现批次可以集中协调，频道执行所需的候选和归属证据应以版本化方式进入目标分片。现有跨表事务需逐一分析后迁移，不能仅凭表名机械搬迁。

主要原则是：一条频道结果应用所需的关键事务尽量在一个 PostgreSQL 中完成。涉及全局目录与分片的操作用明确的幂等流程和恢复记录协调，避免在每个采集步骤引入跨数据库分布式事务。

### 4.3 频道归属与跨分片路由

```text
全局频道目录〔目标数据模型，尚未建立〕
    channel_id -> shard_id + ownership_version + migration_state
                         |
              所有频道任务携带明确归属
                         |
        +----------------+----------------+
        v                v                v
     分片 1            分片 2            分片 N
     主库+备库         主库+备库         主库+备库
```

全局目录先解决不同 Discover 同时发现同一频道时的唯一归属。派发携带目录版本，目标分片核对归属；缓存只减少路由查询，不能允许旧版本继续写入。

不建议使用会随物理分片数变化而大范围重映射的简单 `% N`。优先评估固定虚拟分片加目录映射，并允许大频道单独调配。归属迁移应先阻止该频道新接单、收尾原任务、复制并追平、校验，再原子切换路由版本和恢复任务。

同频道 Full Crawl 与增量必须命中同一权威分片。不能按链路分别建一份频道主数据再靠异步同步维持两套可写状态。

### 4.4 队列和调度也要随数据扩展

如果只有 PostgreSQL 拆成多个分片，而所有任务仍依赖一个全局热点表、一套过载 Redis 或一个中心协调循环，扩容收益会受限。

目标是按分片划分队列 namespace、消费者与连接预算；规模增加后可为分片配置独立 Redis 持久实例及主备。全局展示通过汇总获取状态，不逐条远程扫描所有队列。当前单库/单队列契约的变更必须包含任务迁移、ID 与 prefix 兼容及重复投递恢复。

Redis 主从复制并不天然保证故障切换时所有刚确认的队列写入无损。对关键派发保留持久业务意图、可核对的投递记录和幂等补投机制；恢复能力需要真实测试，不能仅靠开启 AOF 或 Sentinel 宣称零丢失。

### 4.5 业务库如何支持增长

业务在线库继续保存发布顺序、当前版本和在线读模型。历史指标、快照与复杂分析逐步进入分析/归档层，但现有 API 依赖哪些历史表需要先核对，不能一刀切搬走。

业务在线查询先评估索引、增量投影、缓存和允许延迟的读副本。若多采集分片的总发布量使单业务主库饱和，再按业务域或频道划分业务写入归属。不能假定增加 OLAP 后业务当前态写入就自动获得无限容量。

跨分片的排行榜、总数和多维统计优先由异步聚合读模型承担。严格实时的跨分片查询需要单独明确延迟、资源和一致性成本。

### 4.6 数据增长与保留

当前采集库 `content_candidates`、`contents` 和业务库 `content_snapshots`、`channel_metric_values` 已是大对象；后续容量计划应分别衡量当前态、版本历史、执行历史和大载荷增长。

保留规则应以业务状态和引用关系为条件：未应用结果、未发布版本、有效恢复检查点不能因年龄被自动删除。历史统计进入 OLAP 后，也需确认重建窗口与恢复依赖，才能清理源数据。

分区优先用于适合按时间维护的历史事实和事件；更新频繁、按实体访问的当前表需单独设计。分区不等于分布式数据库，也不自动增加单机写入能力。

容量应按“在线数据 + 索引/TOAST + WAL + 临时文件 + 迁移/维护 + 恢复空间”预算，并持续观测可用天数。不能等磁盘使用率接近满额才开始复制大库。

## 五、结果接收与应用：最终怎样解耦

建议把接入、结果持久化与业务应用设计成可独立扩容的职责，但实施先取决于测量和状态机验证。当前已有整频道运输，不等于下面全部能力已实现。

```text
远程采集完成
      |
本地 journal/spool 持久化
      |
NATS / 结果接入
      |
目标分片验证身份并持久接收完整结果
      +----同一原子边界----> 建立待应用工作
      |
返回持久回执，完成网络会话安全收尾
      |
释放采集槽位〔业务任务仍可处于待应用〕

独立应用消费者 -> 原业务事务 -> checkpoint/observation/outbox
                                      |
                                后处理与业务发布
```

首版解耦建议继续利用现有 PostgreSQL 结果持久化，避免同时引入对象存储双写和新的应用队列。若以后大载荷迁往对象存储，必须证明对象持久性、索引提交、孤儿清理和回执之间没有数据丢失窗口。

关键约束：完整回执才可确认；接收与待应用登记不能出现遗漏；应用有独立且合法的业务所有权；同频道新任务不能越过尚未应用的前序结果；重放不会重复观测或倒退版本；节点槽位释放必须晚于网络会话安全关闭。

上游同时监控待应用任务数量、字节数和最老年龄。下游变慢时减少新采集，优先保留已领取任务完成回传的通道及心跳资源。普通 RPC、续租、结果接收、统计和后台清理不能无限争用同一连接池。

这项改造能够减少采集端等候和吸收短时峰值，但不会提高数据库长期可承受的总写入量。持续 λ > μ 的负载必须通过降速或扩容处理。

### 7.1 高可用必须补足的机制

| 对象 | 推荐目标 | 必须验证的行为 |
| --- | --- | --- |
| 管理/API | 至少两个可接管实例与冗余入口 | 配置写入和会话兼容，入口不保留新单点 |
| 调度/协调 | 每项职责有唯一所有者或明确分区 | 旧实例失权后不能继续写；重复调度可恢复 |
| PostgreSQL | 每主分片有异机备库和明确切换管理 | 故障检测、旧主隔离、连接重建、锁/租约失效与重新接管 |
| Redis | 持久化、副本及经测试的故障切换 | 投递差异可对账补偿；不假设复制无损 |
| NATS | 三节点及匹配的结果流副本策略 | 单节点故障、磁盘/网络分区、消息重投与容量限制 |
| Rota | 控制与状态可恢复、具备接管策略 | 旧网络执行安全收尾；不误复用失效身份 |
| 对象存储 | 多故障域耐久或具备相当能力的服务 | 数据可用、对象与数据库引用一致、恢复耗时可接受 |
| OLAP | 可恢复；业务需要时做冗余 | 分析故障不立即停采，源日志/缓冲仍然有界 |

PG 故障管理若使用需要一致性仲裁的组件，仲裁节点需满足其 quorum 和故障域要求。Redis Sentinel 若被采用同样需要独立的仲裁设计。具体产品、版本和放置方式在部署专项确定，图中两个数据库框本身不构成自动切换能力。

关键回执与元数据是否采用同步复制，应由 RPO 决定：同步复制可能牺牲部分延迟与网络分区时的可用性；异步复制则必须接受并处理切换时的可能数据损失。不能同时承诺任意故障下零丢失、零停顿和无额外成本。

### 7.2 机器规格如何确定

| 机器角色 | 优先资源 | 选型依据 |
| --- | --- | --- |
| 管理/控制 | 稳定 CPU、内存与网络 | 元数据请求、配置写入、全局协调；大报表分离 |
| 协调/应用 | CPU、RSS 上限、低时延数据库网络 | 结果解码校验、事务吞吐、尾延迟；当前 1 CPU 限制只作基线 |
| 采集数据库 | 可持续 IOPS、低 fsync 延迟、内存、扩容空间 | 工作集、WAL、索引/TOAST、自动清理、备份和重建需求 |
| 消息/队列 | 独立持久盘、复制网络、内存预算 | 峰值结果字节、缓冲窗口、复制开销 |
| 采集节点 | 每槽真实 CPU/RSS、代理吞吐、本地 spool | 大频道及失败恢复峰值，不能只相加容器理论上限 |
| Agent | 模型所需 CPU/内存 | 模型并发与每批输入，按实际推理方式测试 |
| 业务库 | 在线查询延迟、投影更新、存储维护 | 业务 QPS 与发布峰值分别测量 |
| OLAP | 扫描吞吐、列式存储、批量导入能力 | 真实查询集、保留期限、重放/更正与并发 |

本次缺少目标日工作量、峰值 QPS、增长趋势及采购预算，不给出未经测试的“某配置可以撑多少 Worker”承诺。先决定角色与故障域，再按第 06 份的测试确定规格和备用容量。

## 八、稳定运行的核心机制

### 8.1 先保证下游，再开放上游

发现、全量与增量分别设置接单预算，给有时限的增量留出能力；待全量候选、发布积压、应用积压、数据库或磁盘压力达到阈值时降低相应上游新工作量。阈值带恢复区间和稳定时间，避免频繁开关。发现受限时仍应允许已执行任务的资格反馈和收尾，避免依赖互相等待。

下游故障时应有受控降级：统计不可用可展示旧数据；OLAP 暂停可延迟报表；业务发布中断允许在有限缓冲内继续采集；数据库持久接收不可用时节点保留结果并停止新增任务。不会承诺任一服务无限期故障时采集还能无限继续。

### 8.2 重试有预算，故障按范围隔离

网络失败、API 等待、数据格式错误、数据库拥塞和失去归属是不同错误类别。只有可重试故障才使用有上限的退避；格式损坏或身份冲突需要隔离与诊断，不应触发全体节点重试。

一个节点异常优先影响该节点/槽位；一个分片不可用优先阻止该分片新接单；分析故障优先降级统计。共享 Rota、NATS、全局控制等仍有跨分片影响，需要独立容错和预算，不能声称分片后故障完全互不影响。

### 8.3 监控业务事实与恢复能力

同时观测成功提交量、端到端时延、有效采集槽位、积压数量/字节/最老年龄、错误重试、数据库连接/锁/I/O、对象与日志增长。监控也要有限采样，避免监控 SQL 自身反复扫描大表。

演练必须覆盖节点断线、中心失权、PG 切换、Redis/NATS 故障、对象读取失败、发布积压和磁盘压力。高可用副本不能代替备份，备份文件存在不能代替恢复成功。

## 九、从当前系统走向目标的顺序

| 阶段 | 具体目标 | 开始条件 | 验收重点 |
| --- | --- | --- | --- |
| 1 | 解决存储余量与建立性能基线 | 当前快照与责任人确认 | 磁盘增长可解释，恢复空间有计划，时延可分段 |
| 2 | 采集库、重计算、业务库逐步隔离 | 可用主机、迁移与恢复演练 | 数据一致、旧写入端隔离、竞争减少 |
| 3 | 完善并发、背压和最关键恢复路径 | 实际错误/等待与 SQL 证据 | 持续吞吐提升，无界积压和重试得到控制 |
| 4 | 接收/应用解耦与受控多实例 | 槽位等待占比及状态机评审通过 | 回执与所有权正确，强杀可恢复，同频道顺序不破坏 |
| 5 | 运营和业务分析独立 | 统计负载与允许延迟明确 | 主库统计开销下降，同步/回填影响可控 |
| 6 | 事务主备、消息与入口冗余完善 | RPO/RTO 与预算明确 | 任一约定故障域失效可恢复，实际演练通过 |
| 7 | 单分片演进到多频道分片 | 优化后的写入容量/存储增长达到触发条件 | 路由迁移正确，新增资源提升可持续容量 |

高可用工作可依据业务风险提前到第 2 阶段，分析试点也可与修复并行；这个顺序表达依赖，不强制按编号串行做完所有项目。唯一不应跳过的是正确性、容量、恢复与版本兼容验证。

OLAP 和分片都不需要先行于磁盘余量处理。近期磁盘不足时，同盘部署分析库、复制全库或运行大表重写会增加风险。

| 持久结果与检查点 | 已有 | 保留正确性，明确独立应用授权 |
| 收到回执后即可安全释放普通采集槽 | 尚未完成此通用解耦 | 新状态机、独立应用工作、同频道顺序与恢复 |
| 全部中心职责多实例 | 不能从部分锁测试推定已支持 | 逐项拆分独占/分区/无状态职责 |
| 全局频道目录与多采集库 | 尚未实施 | 路由、分片内调度/事务、迁移与全局协调 |
| 分析库同步与 API 切换 | 尚未实施 | 选型验证、可靠同步、模型与对账 |
| PG/消息/对象层整体高可用 | 本轮未验证具备完整能力 | 故障域设计、切换、旧主隔离、恢复演练 |
| 统一部署版本与容量基线 | 现场存在不同版本与历史材料 | 维护角色版本矩阵与持续指标 |

## 十一、首轮讨论应该定下什么

建议先确认以下五项方向，再进入产品和机器规格细节：

1. **认可两条业务链路、三个独立采集执行集群和统一频道权威归属。** 发现集群通过持久待全量任务池向 Full Crawl 集群提供工作，二者共同构成自发现；增量独立扩容，保留原资格反馈与业务规则。
2. **认可 PostgreSQL 事务层与分析层分开。** OLAP 承担分析，不接管任务所有权与发布完成判定。
3. **认可先拆资源，按证据实施结果解耦。** 当前优先解决存储余量、数据库竞争和中心处理预算。
4. **认可单分片起步、长期可按频道扩展。** 先设计边界，不在当前性能结论不明时直接重写全部数据访问。
5. **给出稳定性的具体目标。** 日工作量、增量截止时间、可容忍积压、RPO/RTO、历史保留和可用预算。

上述内容是本文推荐方向，仍待团队确认。后续每项决定关联 [12 决策与实施计划](12_测试验收与实施计划.md)，并落到可验收的开发、迁移和恢复任务。

本文件的验收不是“图画完”，而是团队能够明确回答：每项数据由谁负责、每个任务归谁执行、某个节点失效后谁接管、下游变慢时怎样降速、数据增长时增加什么资源，以及这些行为如何测试。
