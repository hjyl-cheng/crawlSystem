# 07 数据存储、生命周期与 OLAP 演进方案

状态：当前存储职责说明与待评审设计。未安装分析库、未执行清理或数据迁移。基线见 [01](01_目标范围与系统基线.md)。负责人角色：数据库、后端、业务、数据开发。

## 当前规模和职责

采集 PostgreSQL 约 133.8 GiB，业务 PostgreSQL 约 71.5 GiB。采集侧 `content_candidates` 约 52.6 GiB、`contents` 约 22.3 GiB；业务侧 `content_snapshots` 约 30.3 GiB、`channel_metric_values` 约 17.1 GiB。容量包括关联索引/TOAST；这些对象应优先做增长和访问模式调查。

| 存储 | 权威职责 | 不应承担的额外职责 |
| --- | --- | --- |
| 采集 PostgreSQL | 候选、执行、检查点、内容、观测、Clock、采集侧发布状态 | 无限制的历史全表报表 |
| 业务 PostgreSQL | 业务发布接收、版本和当前投影、在线详情/筛选 | 所有长期历史分析都直接扫描主库 |
| Rota 数据库 | 代理库存、Lease/Route/Slot 状态 | 作为采集数据仓库 |
| Redis/BullMQ | 队列、交付与调度相关运行数据 | 取代持久业务事实与幂等检查 |
| NATS JetStream | 远程消息与结果缓冲 | 永久历史分析仓库 |
| MinIO | 原始证据、最终载荷等对象 | 替代需要事务更新的任务状态 |
| 节点 spool | 未完成上传与恢复所需本地证据 | 可随意清理的缓存 |

业务查询目前通过已发布的 `creator_search_live` 等投影和快照工作。已有增量发布优化避免正常发布全量复制搜索数据；仍需保留 revision、观测和必要历史，不能将“增量发布”理解成数据不再增长。

## 生命周期矩阵

| 数据族 | 当前情况 | 后续策略与前置条件 |
| --- | --- | --- |
| 频道/视频当前状态 | 在线业务与增量决策依赖 | 保留当前权威状态；归档不能破坏增量锚点和处置历史 |
| Candidate/Run/视频检查点 | 包含执行恢复与审计证据 | 按终态、引用关系、重试与修复窗口设计清理；不能按创建时间直接删 |
| 历史观测/任务事件 | 支持 Feature、排查和统计 | 分析出口与归档优先；先证明在线消费者不再依赖 |
| 已应用整频道载荷 | 源码按 7 天、每分钟最多 64 候选进行清理 | 保留 hash/身份回执；未应用、失败、API waiting 不按成功策略删除 |
| 节点未确认结果 | 在本地持久保存 | 只有合法回执及既有归档语义允许的情况下释放；满额停止新接单 |
| Publication/Business 版本 | 幂等、顺序、撤回、修复依赖 | 先确定恢复/回放窗口，再做冷热拆分 |
| Creator Search legacy 数据 | 存在专用清理工具 | 先确认当前读取模式、回滚版本和引用；不得泛化为删除所有历史 |
| MinIO 原始证据 | 与数据库引用相连 | 按对象引用和保留策略删除，处理孤儿对象需独立核对 |
| Redis、NATS 历史交付 | 受各自配置限制 | 容量不足不应通过丢失在途工作解决；审计不能仅依赖队列历史 |

7 天策略只针对已应用整频道大载荷，不是全库保留期限。若待清理量增长超过每次扫描能力，需要监控年龄与处理速率后调整，不能盲目扩大事务。

## 近期存储工作

1. 核对所有数据卷实际文件系统及目录体积，区分数据库、WAL、MinIO、镜像层、日志、备份、测试实例。
2. 按表记录容量、索引/TOAST 占比、估计死元组、写入频率、保留窗口和活跃引用。
3. 检查长事务、自动清理与分析时间；死元组估计不直接等于可释放空间。
4. 优先审查重复载荷与已完成执行历史，而不是删除业务当前数据。
5. 所有清理先生成范围与计数预览，保留恢复材料，以小批事务运行并监控锁、WAL 和磁盘。

当前根文件系统约 93% 已用。新建索引、VACUUM FULL、表迁移和历史回填需要额外空间，有锁与 I/O 成本；不应把它们当作无需容量预算的日常修复。

## OLAP 如何服务采集性能

分析库的目标是让大范围统计离开采集/业务事务主库，避免报表与采集争抢资源。它不参与领取、租约、精确完成判定或发布顺序检查。

```text
采集 PostgreSQL ──运行事件/观测同步──> 运营分析数据集
                                                |
                                                v
                                        ClickHouse 等候选 OLAP
                                                ^
                                                |
业务 PostgreSQL ──已发布数据同步────> 业务分析数据集

运营看板 → 运营分析数据集
业务趋势/榜单 → 业务分析数据集
任务控制、写入与当前详情 → 原事务库
```

初期可在一台独立服务器部署候选分析库并隔离两个数据集和查询资源；后续按负载拆集群。不能为了隔离 I/O 又把分析库和初始回填放到当前近满的根文件系统。

ClickHouse 为讨论候选，尚未确定产品和版本。Doris、StarRocks 或继续使用 PostgreSQL 汇总/只读副本应依据真实查询比较；具体产品 DDL、引擎和部署命令待选型验证，不在本文伪装成可直接执行方案。

### 首批候选查询

| 查询 | 处理建议 |
| --- | --- |
| 按日、节点、链路的吞吐/失败/耗时 | 优先作为运营分析试点 |
| 存储对象总数、大小、类型分布和增长 | 增量汇总或 OLAP；总量不能对时间窗口简单重复相加 |
| 行业/国家分布、历史增长与榜单 | 业务分析试点，从已发布口径同步 |
| “批次是否真正完成”“是否有未发布版本” | 继续使用权威事务状态 |
| 当前频道详情、结果即时可见性 | 保留当前业务读模型，按延迟要求单独评估 |

### 同步选项与可靠性

| 方式 | 使用条件 | 实现责任 |
| --- | --- | --- |
| 定时增量读取 | 小范围、较低更新复杂度 | 稳定游标、迟提交补偿、更新/删除捕获、校验 |
| Outbox 事件 | 有明确业务事件与事务边界 | 原子记录、独立交付状态、幂等与版本化 |
| CDC | 需要持续捕获多表变化 | 初始一致快照、日志衔接、复制槽/WAL 限额、DDL 兼容、回放 |

不能简单使用 `id > last_id` 并假定无遗漏：事务可能分配较早 ID 却较晚提交。`updated_at > last_time` 也存在相同时间戳、事务提交顺序和删除遗漏。选择方式时必须证明断点、重叠窗口和幂等补偿正确。

现有发布和任务事件是可评估的来源，不代表可以直接接第二消费者共用一个会删除消息的 WorkQueue。新增分析消费者应有独立消费进度与保留/交付语义，不得抢走业务发布或远程接收需要的消息。

同步中断不阻塞采集，但持久积压、源数据保留和 WAL 必须有容量上限与报警。不能声称“分析库故障永远不影响主库”，无限滞留日志同样会耗尽磁盘。

### 分析建模

- 执行事实：稳定事件 ID、Run/Plan/attempt、链路类型、节点、时间、结果与耗时。执行次数和业务完成数分开。
- 指标观测：稳定观测 ID、频道/视频、观测时间、版本、值与字段状态。缺失值不补成零。
- 当前维度：频道国家、分类等要决定使用当前属性还是历史属性。
- 更正与撤回：设计版本、删除标记或重算策略。不能依赖后台合并自然完成去重就立即承诺查询绝无重复。
- 汇总：明细去重后聚合，迟到、更正和重放应可重建受影响时间桶。

试点采用“历史分批回填 → 增量追平 → 同口径并行比对 → 小范围 API 切换”。回滚时切回旧查询路径，保留同步进度；不自动删除源库历史。

## 分区、副本与分片的区别

表分区便于按范围查询和清理，但仍可处于同一服务器。只读副本分担允许延迟的查询；主备主要提高可用性。二者都不等于主库写入横向扩容。

如果单库事务写入在优化与独立部署后仍达上限，再评估按频道分片：

```text
统一频道归属目录：channel_id → shard_id + 路由版本
                         |
             +-----------+-----------+
             v           v           v
           分片 1       分片 2       分片 N
        同频道的 Full Crawl / 增量 / 内容 / 观测尽量共址
```

查询词、发现批次和全局候选去重需要统一协调；频道维度的执行状态、Clock 和内容尽量在分片内处理，避免每条视频都回全局库事务。大频道会形成热点，分配需要按内容量与更新负载，不能只平均频道数。

新增分片不建议简单改 `hash(channel_id) % N`，否则 N 变化导致大量归属改变。具体采用目录、虚拟分片或一致性路由应评审，并包含排空、复制、校验、路由版本切换和回退。

应用层 PostgreSQL 分片与原生分布式数据库均为候选。需要评估当前 SQL、扩展、事务、锁和故障恢复契约的兼容性；OLAP 不是这些事务需求的替代品。
