# 02 完整业务链路与数据流

状态：当前源码说明及演进边界。基线与术语证据级别见 [01](01_目标范围与系统基线.md)。主要读者：采集、调度、Feature、业务与测试团队。

## 两条长期业务链路

```text
人工查询词 ────────────────────────┐
采集到的关键词/Hashtag ──可选收集──┤
                                  v
                           Query Quality
                                  |
                        查询调度 / Discover
                                  |
                         候选去重与资格筛选
                                  |
迁移输入〔阶段性〕──────────> Full Crawl
                                  |
                          检查点、观测、数据
                                  |
                      Agent / Finalize / 发布
                                  |
                         业务当前数据与查询

采集观测 ──Feature 接入与状态推进──> Clock / Plan
                                          |
                                     Feature Dispatch
                                          |
                                      增量执行
                                          |
                          About / Video / Agent 到期域
                                          |
                                观测与更新、后续发布
```

图示为业务依赖，不表示所有步骤都在一个进程里串行执行。Feature 通过观测更新 Clock，不应简化成“所有发布完成后统一创建 Clock”。具体域的就绪与调度条件由既有 Feature 规则决定。

## 自发现链路

### 查询词来源与质量控制

`queryCollector.js` 支持频道关键词、视频关键词和 Hashtag。元数据自动收集受 `QUERY_METADATA_COLLECTION_ENABLED` 控制；自动启动后续发现周期还受 `QUERY_METADATA_AUTO_CYCLE_ENABLED` 和调度状态约束。代码具备能力不证明现网已开启所有开关。

质量任务进入 `youtube-query-quality`。评分、身份策略、词集范围和有效时间共同影响调度。不能把未评分词全部投递，也不能让自动周期覆盖操作者主动停止的状态。

### Discover

Controller 负责到期查询和分页续跑，`worker-discover` 消费 `youtube-discover-page`。搜索候选按频道聚合，保存来源、分页和策略证据；对已有频道、低于准入要求或证据不足的候选按既有规则处理。

`worker.js` 对可派发候选分配 `snapshot_dispatch_generation`，通过 `buildDiscoveredChannelSnapshotJob` 投递 `youtube-channel-crawl`。不应增加第二套绕过去重和代次分配的发现调度器。

### Full Crawl

Full Crawl 是自发现内部的首次全量阶段，同时复用于迁移输入。当前 Worker 根据冻结的抓取契约选择 `executeFullCrawlYoutubeJs` 或兼容的 `processChannelCrawlV2`；历史 Run 不应在升级后被强制改写契约。

主要行为包括频道资料与准入、上传列表、目标固化、详情/评论等采集、检查点、资格与完整性收口，以及交给既有后处理。迁移特有的批次、活跃度和恢复策略继续按原入口工作。

网络成功不等于业务成功。列表不完整、字段缺失、失败、合法空值以及确切零值应保留差异；不能为了吞吐把 partial 当作 complete。

`youtube-content-detail` 和 `youtube-content-enrich` 是补采/修复能力，不应在部署图里遗漏。Data API fallback 使用共享机制、配额与等待状态，不由每个采集节点独立管理密钥和额度。

## 增量链路

Feature Engine 接入采集观测，维护 About、Video、Agent 等域的 Clock 状态，冻结 Plan；Feature Dispatch 将符合条件的任务接到原增量队列 `youtube-channel-incremental`。

Plan 的任务域、预算、策略版本和执行归属是契约。增加 Worker 不能改变 Plan 语义，不能把分页和每条视频变成不受频道所有权约束的新业务任务。

### 当前远程整频道执行

```text
中心取得合法业务执行归属
       |
冻结 Plan、已知内容与待修复信息，准备网络身份
       |
NATS 指令 / 分块输入
       v
节点同一频道会话：About → 列表 → 目标选择 → 详情
       |
每阶段/视频保存本地检查点
       |
分块结果 → JetStream → 中心持久接收
       |
中心校验并应用原业务写入、检查点、观测
       |
正常会话收尾与槽位释放 → 后续任务
```

本轮中心登记的 45 个远程 Worker 均声明整频道版本。旧逐指令执行路径仍在代码中保留兼容，不能仅凭节点在线状态判断其执行版本。

正常已采完结果的持久接收尚不等于应用完成，也不意味着立即释放节点槽位。API waiting 走已有 continuation，可释放节点采集容量；后续必须回到原 Plan 和检查点。

Agent-only Plan 留在中心侧处理，不需要远程采集；“中心侧”指协调与后处理职责，不要求这些进程永久部署在同一台物理机。

## 后处理与发布

Local Agent 由 Worker 启动 Python 子进程，不是现成的远程 HTTP 推理服务。分离物理机时应移动对应 Worker 及模型运行环境。

Finalize 生成版本化发布材料。采集侧 Publisher 经既有发布传输到 Business Ingress，再由 Reconciler/Activator/Projector 按顺序和版本更新业务当前数据及搜索投影。

```text
Crawler Revision / Outbox
        |
Publication Publisher
        |
Business Ingress → Inbox / Revision
        |
Reconciler / Activator → result.*_current
        |
Projection Outbox → Projector
        |
业务 Snapshot / facts / metrics / creator_search_live
```

业务前端查询通过业务 API 访问业务数据，不经过 Projector 执行一次即时投影。发布延迟和采集完成时延需要分开观测。

## 等待、失败与恢复

| 情形 | 应保持的业务行为 |
| --- | --- |
| 节点断网但已保存结果 | 保存 spool，重传合法证据，不直接重新采完整频道 |
| API 等待 | 保存部分结果与 API 请求归属，按原 continuation 续跑 |
| 路由失效/国家重检 | 由原 Rota 与执行规则处理，不能随机切换正在执行的身份 |
| 中心重启 | 根据任务栅栏、持久回执和执行记录恢复，不用内存进度覆盖数据库 |
| 重复发布 | 按 revision、版本及 hash 校验幂等处理 |
| 发布失败 | 保留可恢复材料，不把采集数据删除或标成从未采集 |
| 统计页面失败 | 保留列表和可用操作；不得据统计缓存决定业务完成 |

## 两条链路的资源关系

自发现可以拆成评分、Discover、Full Crawl 多台机器；增量可运行多个远程节点。两条链路仍可能共享采集库、Rota 资源、API 配额、Agent 和发布能力。

因此并发控制不能只看采集端。需给不同链路设置接单和后处理预算，避免自发现或迁移大量写入使增量超出完成时限。按频道组织后续分片时，Full Crawl 与增量必须找到同一频道归属，见 [07](07_数据存储与分析库方案.md)。
