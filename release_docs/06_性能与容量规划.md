# 06 性能基线、并发预算与容量规划

状态：测量方案与扩容决策标准，未完成本轮性能压测。数据基线见 [01](01_目标范围与系统基线.md)。负责人角色：采集、后端、数据库、运维、测试。

## 当前能下的结论

采集库约 133.8 GiB，业务库约 71.5 GiB；根文件系统已用约 93%。现场登记 45 个远程整频道增量 Worker，40 个本机 Full Crawl 容器运行。中心接入容器上限 1 CPU/768 MiB。以上说明资源共置、存储增长与处理预算值得优先核查，不能证明网络已经堵塞或某一 SQL 是当前唯一根因。

历史整频道小样本减少了逐视频等待和数据库调用，但不能作为 45 Worker 满载性能保证。历史节点锁竞争、连接耗尽与健康检查开销已有修复记录，验收要基于当前镜像重新定位，不重复假定旧问题仍然存在。

## 指标口径

| 指标 | 建议定义 |
| --- | --- |
| 采集吞吐 | 单位时间成功提交的频道域/视频；分别统计首次全量、增量 About/Video/组合 Plan |
| 业务完成吞吐 | 单位时间到达目标发布版本的频道；与仅采集完成分开 |
| 首次成功率 | 首次执行完成量 / 符合口径的首次执行总量 |
| 最终成功率 | 在规定观察窗口内完成量 / 同批应完成量；API 等待和 partial 分列 |
| 重试放大 | 实际执行/外部请求数量相对有效完成工作的比例 |
| 端到端时延 | 从 eligible/入队到目标完成状态；不能只记录最后一次成功 attempt |
| 积压 | 等待数量、估计字节数、最老年龄与增长斜率 |
| 有效并发 | 真正执行采集的槽位数；不同于 Docker running、节点 connected 或 BullMQ active |

按视频数量、首次发现/复采比例、评论工作量、代理出口和 API 等待分层比较。仅比较“频道数”会被频道规模变化误导。

## 时延拆分

```text
可执行/入队 → 开始执行 → 会话准备 → 采集 → 回传
      → 持久接收 → 应用结果 → 会话释放 → 后处理 → 发布
```

为同一 Plan/Run/attempt 关联中心与节点日志，记录以下时间段：队列等待、路由准备、节点采集、上传与回执、中心排队/应用、槽位释放、Agent/Finalize、业务发布。跨机器绝对时间要考虑时钟偏差；单阶段耗时优先使用本机单调时钟，不能直接相减不同机器的未校准时间。

现有 `remote_nats_status`、任务事件和检查点可提供部分信息，完整阶段分解属于待补观测，不应宣称当前已有完整链路追踪。

## 可持续容量模型

设单位时间新进入的结果工作量为 λ，中心有效处理能力为 μ。长期必须有 λ < μ 且保留故障和波动余量，否则缓冲只会延后拥塞。

在近似稳定系统中，平均在途工作量 L ≈ 吞吐率 × 平均端到端时间。增加槽位可能同时增加等待时间，并不保证增加完成量。

`有效上限 = min(节点采集能力, 代理/API预算, 接入处理能力, 数据库能力, 后处理能力)`。不同工作量要用加权单位或分类型预算，不建议简单把一份 About 结果与数百视频结果按一条消息等权计算。

### 并发预算需要覆盖全链路

| 资源 | 当前源码/模板事实 | 扩容检查 |
| --- | --- | --- |
| 接入事务池 | gateway 12、heartbeat 4、result 8 | 总池数、等待、PgBouncer 后端预算 |
| 监督锁 | 默认 4 组 session | 组故障影响、恢复队列，不能混用事务池 |
| NATS 结果处理 | 默认并发 8 | 解码/校验 CPU、数据库结果事务时延 |
| NATS 结果流 | 默认上限 1 GiB、单副本 | 现场值需核对；满额拒新消息时节点需保留 spool |
| 整频道消息 | 32 MiB 逻辑上限、512 KiB 二进制块 | 内存峰值、Base64 开销、重传带宽 |
| 节点暂存 | 整频道模式文档上限 256 MiB/Worker | 含未确认和 stale 证据，不是预分配容量 |
| 节点采集模板 | 768 MiB、0.5 CPU/容器 | 这是上限而非预留；主机调度、内存总量另算 |

完整预算还包含本地 Worker、Feature、发布、Dashboard、Rota、数据库后台维护和备份。不把 PostgreSQL `max_connections` 增大作为默认优化。

## 测量与调优顺序

1. 获取磁盘/卷分布、增长与可恢复余量；建立业务指标口径。
2. 采样中心 CPU throttling、event-loop 延迟、内存、数据库锁/连接等待、I/O 延迟和代理失败。
3. 优先定位完成量损失：错误重试、未能收尾、长时间 API 等待或中心应用等待。
4. 对高频 SQL 按总耗时、调用频次、读写块、临时文件和锁等待排序；本次采集库未安装 `pg_stat_statements` 扩展，不能假定现成可用。
5. 一次只改变一个主要变量，在可比任务分布下比较吞吐、尾延迟、错误率和积压。
6. 只有新增并发能提升稳定完成量且不造成持续积压时，才继续加量。

生产 `EXPLAIN ANALYZE` 会真正执行查询；大查询、写语句和负载试验应先在隔离环境验证。记录当前查询计划和数据规模，避免将不同数据量的实验直接比较。

## 压测设计建议

测试环境覆盖小/中/大频道、不同目标视频数、About-only、Video-only、组合 Plan、API waiting、慢代理及失败恢复。首次全量和增量既分别跑，也测试资源竞争。

并发从小批逐级上升，阶梯大小由当前基线确定，不固定照搬 10/20/45 等数字。每级运行时间需覆盖多个完整任务和清理周期；最终稳定性测试至少跨一个完整业务调度周期，并覆盖发布、清理和备份等周期重叠。具体时长由第 12 份评审确定。

停止加压条件：数据正确性失败、最老积压持续增长、租约/数据库超时显著上升、磁盘预算不足、内存限制反复触发或吞吐不再提高。精确数值阈值需先建立基线后签入配置和验收表。

## 长期数据增长预算

```text
每日新增存储
  = 新实体/候选与索引
  + 全量/增量历史观测与快照
  + 执行记录、回执、发布版本
  + 对象存储与日志
  - 已验证保留策略实际回收/复用的空间

预计剩余天数 = 可用容量预算 / 近期每日净增长
```

容量预算先扣除应急余量、WAL、临时排序、备份/恢复、索引重建和数据迁移空间。普通 DELETE 后 PostgreSQL 可复用页不意味着文件系统立即释放空间，不能从删除行数推算扩盘时间。

至少建立 7/30 天趋势；没有趋势时可以做 3 倍/10 倍的情景分析，但要标成假设。不能把单次 205 GiB 左右的两库体积线性外推为容量承诺，因为历史保留、索引和压缩都会改变增长率。

## 扩容决策表

| 观测 | 首选评估 | 不应直接采取 |
| --- | --- | --- |
| 统计扫描占主要 CPU/I/O | 缓存、汇总、读隔离、OLAP | 直接重写采集调度 |
| 数据库锁等待占主导 | 缩短事务、减少锁范围、恢复流程修正 | 删除所有权检查 |
| 接入进程受 1 CPU 限额限制 | 调整限额或拆职责，重新测量 | 单纯增加远程 Worker |
| 数据库写入/维护长期饱和 | 减少写放大、独立存储、分片评估 | 增加同库接收消费者 |
| 代理/API 成功率低 | 路由/预算/恢复调查 | 无限制重试 |
| 磁盘即将不足 | 扩容、经审查保留清理、归档与恢复空间计划 | 同盘回填 OLAP 或全库重写 |
