# 11 备份、恢复与灾难演练

状态：依据当前数据边界制定的恢复设计。现网备份频率、最近可恢复点和跨主机恢复成功记录本轮未核验，不宣称已有完整灾备。基线见 [01](01_目标范围与系统基线.md)。负责人角色：运维、数据库、核心后端、测试。

## 恢复目标需要先明确

RPO 是允许丢失的最大数据时间窗口，RTO 是允许恢复所花的时间。不同数据族可能采用不同目标；必须由业务与团队确认，不能用“有副本”代替恢复承诺。

| 数据族 | 主要影响 | 目标状态 |
| --- | --- | --- |
| 采集执行与检查点 | 重复采集、状态丢失、错误接管 | RPO/RTO 待评审 |
| 原始采集与观测 | 证据和历史可能无法重建 | RPO/RTO 与保留期限待评审 |
| 发布版本与业务当前态 | 错序、重复、业务数据回退 | 需跨库恢复核对方案 |
| Redis/NATS 在途交付 | 排队工作和待接收结果 | 需持久化配置与恢复测试 |
| 节点未上传结果 | 未完成回传的采集证据 | 单节点磁盘故障容忍度待评审 |
| OLAP〔将来〕 | 分析不可用或落后 | 可重建范围和重建时长待验证 |

## 备份覆盖范围

| 对象 | 备份内容 | 配套元数据 |
| --- | --- | --- |
| 采集 PostgreSQL | crawler、Feature、remote_ingestion、publication 等实际 schema 与数据 | 大版本、扩展、角色/权限、数据库身份、时间线/恢复点 |
| 业务 PostgreSQL | publication、result、public 投影和版本关系 | 业务身份、stream/ownership、版本与投影进度 |
| Rota PostgreSQL/TimescaleDB | 代理库存与路由管理状态 | PG/Timescale 版本、密钥依赖、恢复后的租约协调策略 |
| MinIO | 对象内容、bucket 配置、版本/生命周期设置 | 对象清单、hash、与数据库引用的对应关系 |
| Redis | 持久化文件和配置、队列 namespace | 快照/AOF 时间与应用版本 |
| NATS JetStream | 流/消费者配置与符合其备份方式的持久数据 | 消费进度、认证配置、服务与副本版本 |
| 节点 spool | 未确认结果、journal、身份配置 | node/deployment/slot、运行时版本、签名验证材料 |
| 运行配置与镜像 | 已部署 Compose 组合、配置版本、不可变镜像摘要 | secret 的受控加密备份、解密钥匙独立保管 |

Git 中的 schema 快照没有生产数据，也不含全部 ownership、凭据和运行身份。`backups/README.md` 只说明加密备份约束，不是已存在自动数据库备份服务的证据。

## 存储与备份策略建议

当前根文件系统仅约 40G 空闲，而采集库和业务库合计约 205 GiB。不得假定可以在同盘先生成完整未压缩备份再上传。使用具备容量与吞吐预算的外部备份位置，避免与在线数据库共用唯一故障域。

PostgreSQL 可评估物理基础备份加 WAL 归档以实现 PITR，同时保留适合对象级恢复的逻辑备份。具体工具、周期和保留窗口需要 DBA 选型并演练，不能直接宣称现网具备 PITR。

备份应加密、校验、限制访问并保留至少一个独立故障域的副本。备份频率与留存决定 RPO；副本复制会复制误删除，不等于历史备份。

逻辑备份参数示意，仅用于有独立目标空间和受控连接配置的环境：

```text
PGSERVICE=<backup-service> pg_dump \
  --format=custom --no-owner --no-privileges \
  --file=<external-backup-path>
```

`--no-owner/--no-privileges` 意味着恢复时另行重建角色与授权。逻辑备份不是跨数据库原子快照，不包含 PostgreSQL 集群全部运行状态。禁止在文档或命令历史中内联生产密码。

## 跨数据层的一致性

采集库、业务库、对象存储、队列和节点 spool 不共享一个全局事务。分别恢复到“相近时间”不足以证明一致。

需为恢复点记录：采集发布 Revision/Outbox 进度、业务 Inbox/激活/投影进度、对象清单、队列快照时间、节点身份与已确认结果范围。异步差异通过原幂等和 reconciliation 机制修复，不能手动提高 watermark 来跳过丢失数据。

如果源备份缺少业务库已经应用的某些版本，必须制定双向核对与补偿方案；不能假设重新发布总能恢复，因为必要的源历史可能已按保留策略删除。

## 恢复顺序

1. 确认故障范围，关闭受影响范围的新接单，保留仍可读取的磁盘、消息和日志。
2. 选择经校验的恢复点、版本和配置；隔离旧写入端，防止恢复期间出现双主或重复实例。
3. 在目标环境恢复 PostgreSQL/扩展/权限以及对象存储；验证数据库身份与核心结构。
4. 恢复 Redis/NATS 的持久状态和匹配配置，但暂不开放采集消费。
5. 核对数据库与对象引用、发布进度和在途结果；建立需要重放与人工核查的列表。
6. 恢复 Rota 控制服务，按原执行所有权机制处理过期租约与未知在途网络；不盲目续用旧浏览器身份。
7. 启动中心协调与恢复服务，验证旧实例隔离、合法执行归属、回执重放和待应用证据。
8. 启动后处理与发布恢复，核对业务版本和当前数据。
9. 小范围恢复自发现/增量接单，验证完整业务链路，再逐步恢复容量。
10. 恢复分析同步并核对断点；确认源历史仍覆盖需要重建的窗口。

该顺序是职责依赖；具体服务启动命令由第 09 份的实际部署清单生成。需要保留因故障未完成的任务和 API waiting 状态，不能直接批量改为成功。

## 节点磁盘与中心故障的区别

进程退出但 spool 完整时，节点通常可按原机制重传。节点磁盘永久丢失则未获中心持久回执的结果可能无法恢复，需要按业务预算重新采集，不承诺零重复请求。

中心已持久接收的整频道证据在符合 Plan/视频周期和新执行栅栏时可复用；可选证据超出载荷上限或不完整时仍可能需要补采。不能将隔离环境 SIGKILL 测试描述成硬盘损毁无损恢复。

若要为节点 spool 增加远程备份，需要验证 journal 的一致快照和实例锁语义。直接复制正在写入的目录不一定得到可恢复结果。

## 恢复验收清单

- PostgreSQL 版本/扩展/角色和应用镜像兼容，数据库身份与预期一致。
- 关键实体、检查点与发布记录按范围核对；统计估计行数不能作为唯一校验。
- 对象可读取，hash 与必要数据库引用一致。
- 重复消息被正确处理，旧执行代次不能写入。
- 频道字段状态、视频集合、评论完整性和 Feature Clock 规则没有被恢复过程改写。
- 发布没有缺口、倒退或未经处理的撤回；业务 API 读到合法版本。
- 节点接单和路由重新就绪，无持续恢复循环、异常重启或无界积压。
- 实测 RPO/RTO、重复采集范围及无法恢复的数据已记录。

## 演练计划

先做隔离环境单库恢复与对象引用核对，再做采集库/业务库不同恢复点的重放，最后做中心或数据节点丢失的完整演练。演练必须包含真实在途任务、API waiting、已收到未应用结果和发布积压。

频率与持续时长由团队评审确定；每次重大 schema、发布契约、保留策略或分片变更后至少复验受影响场景。将最近一次成功恢复的时间、范围与证据纳入运维看板，而不是只显示“备份文件存在”。
