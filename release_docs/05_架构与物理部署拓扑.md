### 迁移优先顺序建议

1. 先确认根文件系统 93% 占用的构成、数据库卷位置、增长速度和扩盘方案。不能在余量不足时直接做全库复制、重建索引或新分析库回填。
2. 给采集 PostgreSQL 提供独立 CPU、内存和持久存储资源；方案必须包含一致性迁移、恢复验证与回退。
3. Full Crawl 和 Agent 等重计算与数据库隔离，给增量接入保留处理余量。
4. 业务库、业务投影和对象存储按实际 I/O 与容量压力独立部署。
5. 单独隔离统计；有收益证据后再引入 OLAP。

数据迁移先后可根据现有空闲机器调整，但恢复能力和磁盘空间是前置条件。不能仅搬采集容器就认为数据库写入竞争已经消失。

## 网络与部署依赖

| 路径 | 当前或目标通信要求 |
| --- | --- |
| 用户 → 管理入口 | HTTPS，经 Auth；内部管理接口不直接暴露 |
| 节点 → 中心 | NATS WSS/TLS，独立节点身份与 subject 权限 |
| Worker/服务 → 采集库 | 私网 PgBouncer；专用锁/LISTEN 会话使用明确直连 |
| 服务 → Redis | 私网认证，环境 prefix 隔离 |
| 发布 → Business Ingress | 保留认证发布接口，避免跨库超权限直写 |
| Worker → Rota | 控制权限与只读路由权限分离 |
| 服务 → 对象存储 | 独立身份与 bucket 范围，按职责授权 |

仓库模板中：远程中心内部端口 3187；NATS TCP 4222 的宿主机映射限制回环，WSS 经现有 HTTPS 反向代理；9222 是模板中的内部 WebSocket 入口。跨主机拆分时必须重新设计 DNS、TLS、私网路由与访问控制。

Docker external network 名称不能跨主机自动连通。不得把单机网络名原样复制到另一台机器并期待已有依赖可访问；也不应为图方便把 PostgreSQL、Redis 和管理端口直接开放公网。

## 可用性与多实例边界

| 部件 | 扩展方式 | 仍需解决的事项 |
| --- | --- | --- |
| 采集 Worker | 多机器多实例 | 接单与代理容量、实例身份、下游预算 |
| 结果协调服务 | 多实例或职责拆分〔待开发〕 | 所有权、重复结果、全局维护任务与配置竞争 |
| NATS | 多节点 JetStream〔待部署验证〕 | 副本数、故障域、磁盘与带宽、认证同步 |
| PostgreSQL | 主备、只读副本 | 故障切换、旧主隔离、复制延迟、连接恢复 |
| 数据库写入扩容 | 频道分片〔待设计〕 | 路由、共址事务、在线迁移、热点、全局任务 |
| OLAP | 独立节点到集群〔待选型〕 | 数据同步、去重、查询配额、持久恢复 |

主备提高可用性，不等于写入翻倍；多结果消费者写同一饱和主库也不会突破数据库上限。NATS 三实例放在同一机器不构成主机故障容错。

## 部署图需交付的附件信息

每个服务器角色在执行前补齐：主机标识、CPU/内存、存储介质与文件系统、数据卷、服务和镜像摘要、资源限制、私网地址、依赖端口、备份位置、监控负责人、停机影响范围。

同一源代码版本可对应多个角色；实际配置必须随版本归档。当前数据库容器检查得到 `Memory=0/NanoCpus=0`，表示未配置相应 Docker 上限，不代表无限资源。远程中心的 1 CPU/768 MiB 是现场限制，调整前应证明存在限额瓶颈。

## 扩容前团队决策

- 近期可用机器与存储预算，数据库能否迁至独立高速持久存储。
- 全量与增量的服务等级和资源保留策略。
- 单点停机可接受多久，哪些部件先做主备。
- Full Crawl 长期采用可信私网直连，还是另立远程协议项目。
- 是否需要多中心协调；如果只有资源不够，先评估职责拆分是否足够。
