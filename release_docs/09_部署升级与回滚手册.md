# 09 部署、升级、扩容与回滚手册

状态：基于现有工具的执行指南及跨机部署前置要求。本轮未执行本文部署命令。版本和现场快照见 [01](01_目标范围与系统基线.md)。负责人角色：发布负责人、运维、模块开发、数据库。

## 部署边界

仓库标准部署入口是 `scripts/compose.sh`，支持 `bundled`、`fresh-migration`、`shared-qy`、`shared-qy-workers`。独立远程中心使用自己的 Compose 文件和运行目录；Feature/Publication 也有独立运行入口。

当前现场有不同提交的镜像、独立中心与历史单独创建的 Worker。不能通过一次普通 `compose up` 假定已复现或覆盖所有现场服务。首次部署、新版本升级、远程节点扩容和数据迁移是四种不同操作。

## 发布前资产清单

每次发布建立清单：环境、主机、角色、容器/实例、旧新镜像摘要、OCI revision、配置文件集合及顺序、数据库身份/结构版本、数据卷、网络、节点允许接单数、在途工作、回滚规格、负责人和窗口。

只将非敏感摘要放 Git。完整运行凭据和配置备份保存在受控运行/备份系统，不把 `docker inspect` 的全部 Env 或渲染出的明文配置粘贴进报告。

当前模板中的历史 override 可能固定旧镜像标签；应用前检查最终镜像，不要为恢复某个配置功能同时退回旧程序。

## 首次部署顺序

1. 确认主机、磁盘和网络满足 [05](05_架构与物理部署拓扑.md)、[06](06_性能与容量规划.md)，准备独立 runtime。
2. 初始化数据库/对象存储身份，分配服务账户、TLS 与密钥，确认环境隔离。
3. 启动持久基础服务，验证 PostgreSQL、PgBouncer、Redis、MinIO、Rota 的运行与权限。
4. 应用与角色匹配的 schema、种子和发布 ownership/stream 配置。
5. 启动后处理与接入服务，确认消费者和发布目的地就绪。
6. 启动调度及少量 Worker，先限制新接单；验证自发现和增量实际链路。
7. 分级增加接单，观察错误、积压、磁盘和发布延迟。

`fresh-migration` 必须遵循 [新库迁移流程](../docs/NEWCRAWLER_FRESH_DATABASE_MIGRATION.md) 的分阶段角色列表。不能把 bundled 全栈启动命令作为迁移流程替代品。

## 环境与构建命令

以下使用已配置的环境。创建 smoke runtime 会写文件，应在开发/验证主机进行：

```bash
./scripts/bootstrap.sh smoke
./scripts/compose.sh smoke config --quiet
./scripts/compose.sh smoke config --services
```

完成代码提交、必要测试和验证后构建不可变镜像：

```bash
./scripts/test.sh
./scripts/verify.sh
git rev-parse HEAD
git status --short
```

构建参数模板（替换尖括号内容后执行）：

```text
./scripts/build-images.sh <environment> pachongsys-<short-commit> [service ...]
```

例如只改 Dashboard 时可指定 `dashboard`；QYBullMQ/Local Agent 变更的镜像构建服务通常为 `qybullmq-api`。Rota 身份策略变化还可能影响嵌入同一策略的 Worker 镜像。构建后核对 OCI revision 与受影响消费者，而不是只看镜像标签。

## 中心与远程整频道升级

### Schema

`applyRemoteNodeSchema.mjs` 需要预先由私密环境提供 `REMOTE_NODE_DATABASE_URL` 和 `EXPECTED_CRAWLER_DATABASE`。默认只读检查，`--apply` 才执行变更：

```bash
node services/qybullmq/scripts/applyRemoteNodeSchema.mjs --nats --whole-channel
```

该只读模式主要核对数据库身份和列出表，不是完整迁移 diff 或所有字段兼容性证明。检查 SQL 文件和旧结构后，执行阶段才使用：

```bash
node services/qybullmq/scripts/applyRemoteNodeSchema.mjs --nats --whole-channel --apply
```

脚本使用事务、3 秒锁等待和 15 秒语句超时。先确认原业务 schema 已就绪；仅安装 remote schema 不能建立完整业务执行环境。

### 升级顺序

1. 记录原允许接单数与各实例镜像，停止选定范围的新接单。
2. 等待业务、网络与 spool 排空；避免操作期间另一个管理入口恢复接单。
3. 先升级支持旧/新节点的中心及必要 schema，验证状态接口和 NATS 权限。
4. 再升级已排空的少量节点，保留 node/deployment/slot 身份与 spool。
5. 同步中心镜像登记、Dashboard 默认镜像和已有部署登记，核对摘要与运行版本。
6. 恢复原允许数量或灰度数量，跑通真实频道及业务发布后再扩大。

整频道使用 `REMOTE_NODE_WHOLE_CHANNEL=true`，且依赖 NATS/schema。Dashboard 当前 NATS 采集部署模板会设置相应模式，但现有节点必须经身份和排空流程升级，不是改默认变量即可切换。

### 中心配置检查

现有独立中心相关文件包括：

- [中心](../deploy/compose.remote-node-center.yml)。
- [私有服务与 Rota 路由](../deploy/compose.remote-node-services.yml)。
- [NATS](../deploy/compose.remote-node-nats.yml)。
- 现场实际采用的 runtime Compose 与环境文件；应按发布清单保留其组合和覆盖顺序。

基础模板示例仅用于理解检查方式，不能省略现场其他 override 来重建生产：

```text
docker compose --env-file <private-compose-env> \
  -f deploy/compose.remote-node-center.yml \
  -f deploy/compose.remote-node-services.yml \
  -f deploy/compose.remote-node-nats.yml config --quiet
```

健康检查可使用已有 `scripts/checkRemoteNodeCenter.mjs`，但它不能证明真实采集吞吐或完整发布链路。

## 远程节点新增与数量调整

Dashboard 负责服务器准备、配置、部署、容器核验和中心连接核验。采集镜像必须是节点可拉取的 `repository@sha256:...`。节点使用独立 spool、受限权限和固定实例身份。

当前任意 32 Worker 人为上限已取消，允许接单不超过实际部署数量；这不表示可以忽略主机内存、代理和数据库容量。数量增加与镜像替换不同：增量部署保护既有容器，不能假定也会升级旧镜像。数量减少、镜像替换和退役要排空后执行。

新增节点先验证连接、身份和少量真实任务，再扩大接单。不要只根据 Docker running 或心跳数量宣称部署完全成功。

## 数据库和跨主机迁移

现有 Docker network 是单机网络。跨机部署需要另行落实私网地址、TLS、账户、端口、数据库连接池和故障切换地址。调度与写入服务不能因为复制 Compose 就跨主机连通。

迁移数据库至少包含：源目标版本兼容、容量、备份、复制/停写窗口、增量追平、一致性核对、切换、旧写入端隔离与回退。该流程须在隔离环境演练；本文不提供未经验证的一键跨机迁移脚本。

## 回滚矩阵

| 变更 | 回滚方式 | 注意事项 |
| --- | --- | --- |
| 普通应用镜像 | 排空后恢复旧摘要与旧规格 | 数据格式必须仍被旧程序理解 |
| 兼容性新增 schema | 回退应用，保留兼容结构 | 不默认删除新增表/列 |
| 新节点镜像 | 排空、恢复旧镜像及匹配登记 | 保留 spool 与凭据；验证旧程序能处理保留载荷 |
| 接单数量 | 恢复记录的原数量 | 接单操作要有并发变更检测 |
| 新结果应用状态机 | 先处理或兼容新状态，再回应用 | 不能简单停止消费者留下无所有者工作 |
| OLAP 读切换 | 切回原统计路径或已验证降级展示 | 控制主库统计并发，避免流量突然回灌 |
| 数据库迁移/分片 | 按预演的复制与路由回退方案 | 切换后新写入不能丢失或产生双主 |

禁止用 `down -v`、删除在途消息或手工标成功替代回滚。具体生产命令应由现场清单生成，不能用历史容器名猜测目标。

## 发布后验收

确认角色版本、重启/OOM、连接预算、实际有效接单、租约/路由、数据字段、Feature 状态、发布进度、磁盘增长和新旧查询一致性。观察窗口需覆盖受影响业务周期，短时容器健康不能代替验收。
