## 一、目标、范围与决策边界

### 1.1 重构目标

目标是让采集开发主要维护请求、解析和业务规则，通用的执行协调交给 Temporal，数据写入集中在经过验证的模块中。系统需要支持发现、全量、增量分别部署到多台机器，在节点重启、网络中断、重复交付和数据持续增长时可恢复。

验收不能只看容器启动或短时抓取速度，必须同时检查业务正确性、持续吞吐、积压可消化性、故障恢复和部署可回滚性。

| 事项 | 本方案决定 | 实施限制 |
| --- | --- | --- |
| 执行协调 | 采用 Temporal 作为目标底座 | 先迁移一个受控增量范围，通过验证再扩展 |
| NATS／JetStream | 完成所有依赖迁移后，从爬虫目标架构移除 | 不能只替换任务领取就关闭共享消息服务 |
| BullMQ | 已迁移的工作由 Temporal 单独负责执行协调 | 过渡期仅承接明确未迁移的范围；最终按依赖清单退役相关队列 |
| 爬虫事务数据 | 保留 PostgreSQL 与现有业务规则 | 不把疑似应用缺陷归因于数据库类型 |
| 原始数据 | 保留 MinIO／S3 接口，完善可靠接收与保留规则 | 不向 Temporal 历史传递大型完整载荷 |
| 业务分片 | 先完成数据边界设计，Citus 为第一验证候选 | 不能把整个现有 schema 原样转换成分布表 |
| 数据库运维 | 评估 Pigsty／Patroni 等现成部署工具 | 工具解决复制、备份与运维，不替代 SQL 和业务一致性设计 |
| ClickHouse | 从爬虫必选清单排除 | 下游业务分析独立决定；运行统计先做限流、缓存、预聚合 |
| 业务库与 Rota | 保留对外契约和独立职责 | 不把业务 Projector、代理状态库顺带替换为 Temporal 存储 |
| 修改范围 | 本轮只写文档 | 所有实现、部署与数据操作均属未来阶段 |

Temporal 服务端负责持久执行协调；应用 Workflow 代码和 Activity 代码运行在应用 Worker 中。生产可以将 Workflow Worker 与重采集 Activity Worker 分开配置，不能让浏览器或大型 JSON 解析挤占 Workflow Task 的执行资源。

“数据层”是固定的数据契约与事务实现。第一阶段可以是复用现有 Store 的模块与服务，随后按负载独立部署；不是要求所有查询经过一个新的单进程中心。远程采集节点原则上不持有全库凭据，数据应用 Worker 位于数据私网。

### 3.1 唯一事实来源

| 内容 | 权威来源 | 其他层的使用方式 |
| --- | --- | --- |
| Workflow 执行顺序、计时与 Activity 调度 | Temporal 历史与服务 | Dashboard 查询／展示，不从列表缓存反推是否完成 |
| 频道资格、视频事实、合法版本、已应用批次 | 爬虫 PG | Temporal 通过 Activity 调用，重试仍校验这些事实 |
| 当前执行写入权与切换代次 | 业务执行归属记录 | 所有新旧写路径必须检查；Workflow Run ID 不是替代品 |
| 路由、代理容量、请求权限、网络静默证明 | Rota 及其现有契约 | Activity 申请／续租／释放，不能用 Temporal 心跳替代 |
| 原始内容 | 已验证对象和数据库元数据 | Workflow 只引用，不存整个内容 |
| 业务端接受与发布成功 | 原发布回执与 Outbox 状态 | Activity 完成不自动等于业务系统已接受 |

业务 PG 可以保留便于查询的执行摘要，但不得用定时同步的摘要另建一套可独立调度的同名任务状态机。Temporal 的 Visibility 是最终一致检索，不作为领取、资格判断、迁移接管的依据。

### 3.2 首期收敛部署：模块可以多，网络层次要少

首期应用只划分三个主要运行池：编排／调度池、网络采集池、数据服务池。Agent 的外部模型请求可放独立计算角色，但不为每个 Store、检查点或幂等操作新增服务。以下是目标部署边界，不表示当前 Controller／远程中心直接复制多个容器就已经具备多实例安全性。

图例：框为部署边界；`-->` 为跨进程／跨机器通信；框内相邻模块可为本地函数调用。角色池不等于固定一台机器；数据库主备、Temporal 内部服务和对象存储仍需各自的资源／故障域规划。

```text
                       [Temporal 服务及专用存储]
                          ^       ^       ^
                    SDK/gRPC  SDK/gRPC  SDK/gRPC
                          |       |       |
     +--------------------+       |       +-------------------+
     |                            |                           |
+----+---------------+  +---------+-------------+  +----------+-------------+
| 编排／调度池       |  | 网络采集池             |  | 数据服务池             |
| Workflow Worker    |  | Discover / Full Crawl |  | 接收 API / Apply       |
| 准入／启动意图     |  | Incremental           |  | Store / Publisher      |
| 低频恢复扫描       |  | 本地解析 / journal    |  | 对账／有界查询         |
+--------------------+  +-----+------------+----+  +------+----------+-------+
                             |            |              |          |
                    授权 API |            | 结果小信封   |          | SQL
                             v            +------------->|          v
                       [Rota 服务]        |              |     [PgBouncer]
                             |            | 对象直传     |          |
                       合法网络请求       v              |          v
                             |        [MinIO / S3] <-----+     [爬虫 PG 主]
                             v          大输入／结果       读取对象   |
                         [目标网站]                              复制
                                                                  v
                                                            [爬虫 PG 备]
```

编排／调度中的应用数据库操作采用数据私网的受控 Store，与数据角色共享事务契约；纯 Workflow 代码仍不能执行 SQL。数据服务池内部的接收、应用、发布有独立并发配额，可以使用同一发布包和部署单元；若大对象解析影响接收接口，再将解析／Apply 移到受限工作线程或独立进程，不能让一次 CPU 密集解析阻塞全部接收。

首期优先让完整响应直接流入对象存储，中心接收小信封；不增加“采集节点 → 通用网关 → 消息转发器 → 数据 API → Store 服务 → 数据库”这种逐层转发。对象层与数据接收是并行职责，不存在 MinIO 自动把业务结果推到 Apply 的隐式流程。

### 3.3 一次采集的正常时序：跨节点调用在哪里

下面以一个有界采集批次为例。实际一个频道可有多个批次，不为每个字段或每条视频都启动一次完整的此流程。

```text
Workflow        数据角色           采集 Activity        Rota       对象存储
   |                |                    |                |            |
   |--Prepare------>|                    |                |            |
   |                |--短事务 T1         |                |            |
   |<--输入引用-----|                    |                |            |
   |                                     |                |            |
   |--Collect（由 Temporal 派发）-------->|                |            |
   |                                     |--取得授权----->|            |
   |                                     |<--租约---------|            |
   |                                     |--抓取／本地解析             |
   |                                     |--有界上传------------------>|
   |                                     |<--对象版本／校验信息--------|
   |                |<--登记小信封-------|                |            |
   |                |--核验对象（事务外）----------------------------->|
   |                |--短事务 T2：RECEIVED＋Apply 意图     |            |
   |                |--持久接收回执----->|                |            |
   |                                     |--安全收尾----->|            |
   |<--小型结果／回执（经 Temporal）------|                |            |
   |                |                    |                |            |
   |--Apply-------->|--读取／解析对象（事务外）------------------------>|
   |                |--短事务 T3：事实＋检查点＋APPLIED    |            |
   |<--应用回执-----|                    |                |            |
   |--Finalize----->|--短事务 T4（满足整轮完成条件时）      |            |
   |<--运行摘要-----|                    |                |            |
```

Workflow 的箭头表示 Activity 派发／完成，不是 Workflow 进程直接 RPC 调用指定节点；Temporal 为这些动作持久记历史。租约续期、心跳、输入对象读取和重试未全部画入，其开销单独计量。

正常批次的业务交互收敛为“数据准备 → 有界采集 → 持久登记 → 数据应用”，接收服务不等待 T3 完成才回复。一次采集跨多批时在稳定检查点返回或采用已验证的有界窗口，不一次派出整个频道所有批次；后续批次若依赖已应用游标，必须等待对应应用回执。

Apply 优先由 Workflow 正常派发；持久 Apply 意图只负责补偿丢失派发与恢复，不能再建一套独立抢执行的调度器。重复派发由相同批次身份和数据库栅栏收敛。代理释放、会话检查点与本地 journal 删除仍服从既有收尾契约，不因这张简图省略而被删除。

### 3.4 数据服务内部：哪些交互不需要网络

```text
一个数据服务实例／发布包
+-------------------------------------------------------------------+
| 接收 HTTP handler ----> 接收模块 ----+                             |
| Apply Activity -------> 应用模块 ----+                             |
| Publish task ---------> 发布模块 ----+--> 受控 Store（本地调用）    |
| Recovery task --------> 恢复模块 ----+       |                     |
| 查询 handler ---------> 查询模块 ----+       v                     |
|                                      SQL 并发闸门                 |
|                                            |                     |
|                                  本进程共用 PG Pool               |
+--------------------------------------------+----------------------+
                                             |
                                      PgBouncer / PG

对象读取、解析、外部业务发布：在 SQL 事务与借用连接之外执行
```

每个模块不能各创建一个默认 10 连接的 Pool。只在确认需要独立权限／连接语义时建单独池，全部计入总预算。跨模块业务事务传递同一个 transaction client，不让 Store 内部另借一个连接破坏原子性。

本地调用不等于不限流：接收、Apply、查询、发布和恢复分别排队，最后共享数据库预算。只有需要资源隔离或独立扩容的模块才拆进程；模块边界不自动升级为网络边界。大响应解析需要限制工作线程／进程的并行数、内存和取消时间。

```text
                  Full Crawl Workflow
                         |
             资格校验 -> 分批采集 -> 应用结果
                         |
                  资格结果持久化与反馈
                         |
           原发现页按资格和 continuation 决定下一页
```

多 Discover 同时发现同频道时，保留各自来源与页面关系；同一合法执行可以满足多个来源的需求。当前候选唯一键是批次内唯一，迁移时不能伪装成已具备跨批次全局去重。需先定义频道身份、资格策略版本及可共享执行的条件，再设计并发合并。

同一查询的下一页 token 尚未产生、或原业务要求等待资格反馈时，不允许为了提高并行度提前构造后续页。不同查询可以并行；等待资格期间 Workflow 不占用采集 Activity 槽位。

发现周期不展开为一个包含所有频道的巨大 Workflow。使用有限页面／有限候选批次的 Workflow，持久保存来源与资格结果；跨流程通知丢失时从业务记录重读。信号只用于推进，不取代持久资格事实。

### 4.2 Full Crawl 流程

建议顺序：冻结业务输入与规则版本 → 取得业务执行授权 → 读取恢复快照 → 申请 Rota 资源 → 抓取频道与资格信息 → 有界批次采集 → 持久接收／应用 → 网络与会话收尾 → Agent／Finalize 及发布交付。

“全量”继续遵循当前内容窗口、数量限制、国家与订阅数规则，不借迁移改变为无条件抓取全部历史视频。API fallback、解析契约错误、休眠或终止频道处置继续复用当前判断。

超大频道可按稳定视频集合或已确认页面边界拆成子任务；各任务以同一频道执行代次为前提，并有独立批次标识。父流程根据持久完成集合收口，不能依靠计数凑齐掩盖重复或缺失。

### 4.3 增量流程

Feature／Clock 继续决定“该抓什么”，生成冻结 Plan。Temporal 决定“这些已确定的步骤怎样执行与恢复”。保留 plan_id、task_mask、规则版本、恢复模式，以及 about／video／agent 的终态语义。

建议顺序：核验 Plan → 获取业务执行代次 → 恢复已应用批次与检查点 → 执行必要采集域 → 处理 API 或国家复核交接 → 应用结果 → 完成网络收尾 → 需要时等待 Agent → 形成终态与下一次调度事实。

业务上允许并行的采集域才并行；共享会话、代理身份或前置证据的步骤保持依赖。不能把所有步骤同时启动当作性能优化。等待 API 配额或 Agent 结果时使用 Workflow 等待机制，不占用 SQL 事务或浏览器进程。

### 4.4 Agent、Finalize 与发布

Agent 作为独立 Activity Worker 池，保留其读取快照的一致性要求；目前合理的 REPEATABLE READ READ ONLY 不能按“只读不用事务”删除。CPU 密集型工作与网络采集分开限额。

Finalize 与发布第一阶段复用已有实现。频道事实、Publication Revision、Outbox 的原子关系不能被拆成三个互不关联的 Activity。发布发送在事务外进行，以业务接收方持久回执标记交付状态。

本方案不改写业务数据库架构、业务 Projector 口径或引入 ClickHouse。发布源的身份、顺序、哈希、重放和回执兼容属于本次必测的交付边界。

## 五、Temporal 执行契约

### 5.1 Workflow 与 Activity 边界

以下名称是待实现的逻辑职责，不是已有代码或最终 SDK 接口。

| Workflow 类型 | 负责的范围 | 主要 Activity |
| --- | --- | --- |
| DiscoveryPageWorkflow | 一个有限发现页面／批次及资格反馈 | 抓取页面、登记候选、读取资格结果 |
| FullCrawlWorkflow | 一个合法频道全量执行 | 准备、采集批次、登记结果、应用、收尾 |
| IncrementalChannelWorkflow | 一个冻结 Plan 对应的频道执行 | 核验 Plan、分域采集、恢复、应用、收尾 |
| AgentWorkflow（按需独立） | 一个有界分析请求／批次 | 读取快照、计算、提交分析结果 |
| RepairWorkflow | 已授权的具体修复意图 | 对账、重放已有证据、补齐结果 |

Workflow 内只放决定性编排；HTTP、SQL、S3、随机外部状态、进程执行进入 Activity。SDK 提供的可重放计时与随机能力按所选版本使用，不在 Workflow 顶层调用普通外部 I/O。

Activity 按“可独立重试的业务边界”划分，不机械地一条 SQL 一个 Activity，也不把整套任务管理中心原封不动包成一个超长 Activity。当前复杂采集函数可以先作为粗粒度适配，在已有检查点边界稳定后再细分。

### 5.2 输入与结果契约

每次执行至少携带：业务意图标识、频道 ID、冻结 Plan／候选标识、契约版本、规则版本、执行归属代次、数据版本预期、区域／能力需求、输入对象引用和追踪标识。

结果返回小型摘要：业务批次标识、接收回执标识、内容哈希、对象引用、业务版本、成功／延期／终止分类和处理数量。令牌、代理密码、浏览器 Cookie、完整 HTML、视频大列表不进入普通 Workflow 参数、返回值或 Search Attributes。

建议把单次业务参数／结果的内部预算先设为几十 KiB 量级并监控，最终数值由选定 Server／SDK 的限制及压测确定。不能把服务端最大载荷限制当正常设计尺寸；错误堆栈、心跳详情和大量子任务结果也会增加历史体积。

### 5.3 Workflow ID 与业务幂等

建议 Workflow ID 由稳定业务意图派生，例如 `incremental/<channel_id>/<plan_id>`，全量包含可重复执行的合法业务代次。Activity 重试次数、机器 ID、随机运行时间不参与业务幂等键。

明确设置运行中冲突策略和已关闭 ID 复用策略：重复启动应返回／核验同一业务意图，不能自动终止旧执行后启动新执行。具体枚举名称由 SDK 版本确定。

Temporal 的已关闭 Workflow ID 去重受保留期限影响，不能承担永久去重。业务 PG 持久保存意图、批次结果和版本记录，保留期限覆盖允许的重放窗口；永久禁止重复的身份需独立长期记录。

一次 Activity 重试应复用同一业务操作键。其实际执行者需要新的受控执行令牌时，由业务授权接口分配，不能简单用 SDK 的 attempt 数字充当跨进程全局递增代次。

### 5.4 Task Queue 与节点部署

按 workload、执行区域和必要能力建立有限数量的任务队列，例如 discover、fullcrawl、incremental、agent、apply；这些只是命名示意。确有隔离需求时增加有限的区域或数据分片组后缀，不为一亿个频道各建独立队列或 Schedule。

同一 Task Queue 上的 Worker 必须能够执行其收到的 Activity 类型；浏览器、语言运行时、代理区域和数据权限不能仅靠任务 payload 临时猜测。Workflow Worker 可以共享受支持的 Workflow 类型，Activity Worker 使用独立并发预算。

Node.js／TypeScript 与 Python 可以通过各自 SDK 承接不同 Activity，协议类型、序列化和错误分类必须契约测试。Go Rota 第一阶段继续作为服务，不强迫整体迁为 Activity。

节点主动向 Temporal Frontend 发起 gRPC／HTTP/2 请求，任务领取使用长轮询，连接可以复用。入口和代理需支持 HTTP/2、合理的长轮询时限、TLS 和连接重建；不能复用仅支持 HTTP/1.1 WebSocket 的配置就认为完成迁移。

### 5.5 超时、心跳、取消和历史管理

| 项目 | 设计要求 |
| --- | --- |
| Schedule-to-Close | 限制业务步骤含排队与重试的总体期限，不能无限重试 |
| Start-to-Close | 根据单批次实测耗时配置，过大延迟恢复，过小造成重复工作 |
| Heartbeat | 长采集 Activity 主动上报；详情只放已持久检查点引用，频率考虑 SDK 节流和服务负载 |
| 取消 | 将取消信号传给请求、浏览器和子进程；确认请求结束并释放 Rota，不只结束一个 Promise |
| 重试 | 短暂网络错误退避并加抖动；配额耗尽转等待；永久契约错误进入明确失败或人工处理 |
| 多层重试 | HTTP 库、Activity 与业务修复的次数共享总预算，避免乘法放大 |
| 历史 | 有界批次、事件／字节告警、保留配置；必要时 Continue-As-New |
| Continue-As-New | 只在安全边界传递持久游标；等待必要子流程与消息处理完成，不能假定在途子流程会自动继承 |
| Worker 升级 | 使用选定版本支持的 Worker Versioning／兼容代码与历史重放测试；旧历史仍可执行前不删除旧实现 |

Activity 超时表示服务端认为本次执行失败，不表示失联节点已停止。网络请求和数据库写入仍要校验业务执行权。心跳不提供远程强制杀进程，也不替代业务检查点。

### 5.6 通信连接复用：长连接也需要并发和流量预算

```text
一个采集进程（可有多个受控执行槽）
+------------------------------------------------------------------+
| Temporal SDK 连接管理 --gRPC / HTTP/2----> Temporal Frontend       |
|   长轮询、Activity 完成、心跳；按 SDK 支持范围复用                  |
|                                                                  |
| 控制 API 客户端池 ------HTTPS-----------> Rota / 数据接收入口      |
|   小请求：授权、续期、回执；独立排队和 deadline                    |
|                                                                  |
| 对象客户端池 ----------HTTPS-----------> MinIO / S3               |
|   大上传／下载：限制并发、字节数、重试；不经过 Temporal            |
|                                                                  |
| 网站客户端／浏览器 ----授权网络---------> 目标网站                |
|   连接、Cookie、代理及会话按当前身份隔离，不能跨身份混用            |
+------------------------------------------------------------------+
```

不同协议各复用自己的客户端；一条 SDK 逻辑连接不承诺底层永远只有一个 socket。每个进程／合法连接配置初始化长期客户端，不能每条任务创建 TLS 连接、SDK connection 或 HTTP Agent。业务 HTTPS 可用经验证的 HTTP/1.1 keep-alive；是否采用 HTTP/2 应看客户端、代理和并发表现，不要求所有接口改写成 gRPC。

| 通信方向 | 频率／体积控制 | 需要验证的失败模式 |
| --- | --- | --- |
| SDK → Temporal | 少量业务事件与小型心跳；限制 poller、活动槽与历史 | 长轮询被代理提前截断、GOAWAY、重连后集中领取、服务端限流 |
| Worker → Rota／会话接口 | 按合法租期续期；稳定请求 ID 支持恢复 | 授权即将过期时控制请求被大上传挤占，旧连接恢复后继续越权 |
| Worker → 接收 API | 每稳定批次登记，返回 RECEIVED；有请求体上限 | 响应超时但已提交，重复登记，入口故障切换 |
| Worker／Apply → 对象层 | 有界 multipart、流式读写、限速和内存上限 | 大包重试放大、未完成 multipart、校验读取流量、对象版本不可读 |
| Publisher → 业务接收端 | 保持原信封与回执；按频道／域处理顺序 | 对端已接收但回执丢失、下游限流、旧版本晚到 |

HTTP/2 多路复用不代表流量无限，也不保证单连接适合全部并发；stream 上限、流控、TCP 丢包和负载均衡都可能影响延迟。尤其长连接可能把请求长期集中在少数后端，需观测各实例负载分布，再采用 SDK 支持的负载分配、受控连接轮换与平滑扩容，不通过频繁断开连接“均衡”。

心跳、授权续期与对象上传分开连接池和工作配额；同机出口带宽仍共享，需给控制通信留余量。连接超时、单请求期限、租约安全窗口和停止请求时间应共同设计；keep-alive 探测不能证明请求成功，也不能替代应用 deadline。自动重试加抖动、设总体期限，并保留原业务操作键。

当前源码基础与限制：

- [httpClient.js](../services/qybullmq/src/httpClient.js) 已复用 Undici Agent，默认 connections=8、pipelining=1。Agent 的连接设置按 origin 等连接分组生效，不是全系统最多 8 条；进程数、目标 origin 与自定义 dispatcher 都会改变总量。
- [channelNetworkSession.js](../services/qybullmq/src/remoteNodes/channelNetworkSession.js) 默认 renewMs=5000，但还按剩余授权时间缩短续期间隔。按每活跃会话 5 秒一次粗估，45 个约 9 次／秒，10,000 个约 2,000 次／秒；这仅是一类续期，不能当作总 RPC／SQL 量或最大频率。缩减请求必须证明租约安全，不能任意延长心跳。
- 当前 NATS 客户端也有连接复用。是否迁 Temporal 与“长连接一定更快”无关；迁移需要用同输入比较控制调用数、字节数、CPU 与有效完成量。

## 六、移除 NATS／JetStream 的具体替代关系

| 旧通信职责 | 目标承担者 | 必须保留的语义 |
| --- | --- | --- |
| claim、commands | Temporal Activity Task Queue 与 Workflow | 持久业务意图、唯一执行归属、重复启动可识别 |
| 执行 heartbeat | Activity 心跳与超时 | 业务写入栅栏另行校验，节点健康不等同任务完成 |
| node_heartbeat／部署控制 | 节点管理 API 与监控 | 节点身份、启用意图、镜像／配置版本与接单状态 |
| whole_channel_input | 版本化输入引用＋对象／快照接口 | 输入哈希、Plan 版本、权限与完整性校验 |
| result stream、分片上传、result_receipt | 对象上传、业务接收回执、Apply Activity | 已接收与已应用分离，重复提交返回一致回执 |
| network_grant／release／abandon | Rota 兼容的 HTTPS 接口 | Route／Lease 版本、撤销、静默和幂等释放 |
| youtube_session／checkpoint | 受限会话接口 | Cookie／身份不进入流程历史，恢复沿原身份规则 |
| local-intake、SQL 通知转发、管理侧订阅 | 对应链路迁移到 SDK／管理 API／持久查询 | 每个生产者与消费者都需盘点，不能遗漏本地执行路径 |

不新建一套自定义 gRPC 任务系统；Temporal SDK 已提供任务通信。现有 Rota HTTPS 接口可以继续复用，只有确有必要才改为业务 gRPC。大结果直接进入对象和数据接口，不绕行 Temporal Server。

本地 spool／journal 在过渡期保留。最终可简化到明确需要的采集中检查点和未确认交付，不因 Activity 返回成功就直接删除全部日志。删除条件见第七节的持久回执定义。

退役 NATS 的前提是第十三节切换协议和第十五节退出清单全部满足；本文不是执行停服命令的授权清单。

## 七、存储与查询层重构

### 7.1 存储职责

| 层 | 技术与隔离 | 内容 |
| --- | --- | --- |
| Temporal Persistence | 专用 PostgreSQL 实例及受支持版本 | 内部历史、任务与计时状态，业务代码不直接读写内部表 |
| Temporal Visibility | 独立逻辑数据库，PG 起步验证 | 执行检索；生产搜索负载大时评估 Elasticsearch／OpenSearch |
| 爬虫事务层 | 现有 PostgreSQL，后续验证 Citus | 频道、内容、候选、业务执行权、检查点、幂等回执、Outbox |
| 对象层 | MinIO／S3，独立容量与耐久预算 | 完整原始内容、大型输入快照、重放材料 |
| Rota 状态 | 保留独立 PG／TimescaleDB 兼容部署 | 代理、授权、容量和网络资源状态 |

Temporal Persistence 与采集高写入数据库生产上隔离实例／资源；同实例内两个 database 不隔离磁盘、CPU 和 WAL。Temporal 文档支持 SQL Visibility，但对生产搜索也推荐 Elasticsearch／OpenSearch；PG 起步是本方案的简化试点选择，不是无限容量承诺。

Temporal 数据库版本按最终 Server 发布说明验证，不直接复用当前业务 PG 18，也不把 Citus 当成官方已支持的 Temporal 持久化后端。Citus 的候选范围仅为爬虫业务数据。

### 7.2 复用 Store，限制业务代码直接访问底层

以现有 FullCrawlYoutubeJsStore、IncrementalRunStore、结果 Store 和 Publication Store 为起点，逐步形成如下业务操作边界。第一阶段允许是进程内模块，远端通过受限 API，接口稳定后才按资源需求拆服务。

| 逻辑操作 | 必须封装的内容 |
| --- | --- |
| 登记发现 | 频道身份、发现来源、资格策略版本、合法全量意图与补偿 |
| 开始／恢复执行 | 执行引擎归属、业务代次、冻结输入、已应用批次和检查点 |
| 登记结果对象 | 对象存在与完整性、归属权限、稳定结果键、持久接收回执 |
| 应用采集批次 | 锁顺序、执行权、版本条件、事实写入、检查点、批次去重、Outbox |
| 完成业务执行 | 必须域终态、覆盖范围、未决后处理、发布状态、下一次采集事实 |
| 查询与统计 | 有界分页、索引与字段投影、缓存、预聚合、超时和访问权限 |

这些操作不是一个万能 CRUD 服务。事务边界由业务一致性决定；不能拆成“更新视频”“更新游标”“发送事件”三个互不关联的网络调用，也不能因为引入 ORM 就认为并发与恢复问题已消失。

### 7.3 批次提交与回执

目标写入流程：

```text
采集／解析
    |
写入不可变或带版本的对象，计算并记录哈希
    |
接收服务核验对象完整性和权限（外部 I/O 在 SQL 事务外）
    |
短事务：登记稳定结果键与对象引用 -> RECEIVED
    |
由 Workflow 调用 Apply Activity，或由已记录意图恢复派发
    |
读取对象、解压、解析、准备写入批次（在事务外）
    |
短事务：再次校验身份和版本
    +-- 幂等回执已存在：返回已有结果
    +-- 校验合法归属、固定锁顺序
    +-- 写入业务事实与必要观测
    +-- 推进已经成功应用的检查点
    +-- 写入业务交付 Outbox
    +-- 记录批次 APPLIED
    |
提交 -> 返回小型业务回执 -> Activity 完成
```

RECEIVED 仅表示对象和重放所需元数据已按目标耐久策略保存，中心能独立恢复；不表示业务数据已应用。APPLIED 表示业务事务已提交；DELIVERED 表示下游已给出持久接收回执。三个阶段不得共用一个含糊的 done。

RECEIVED 之后即使 Workflow 没收到回复，重试登记必须返回相同记录；即使 Apply Activity 未被成功调度，对账器也可依据持久意图补启动。Temporal 启动和 PG 提交不能假装是一个事务。对账器只补缺失执行，不与 Workflow 竞争同一批次的执行权。

原始包上传成功但 PG 登记失败会产生孤儿对象。采用稳定命名／版本引用，重试可核验复用；孤儿清理必须设置安全等待期，并排除活跃上传、未登记但仍可恢复的本地日志。完整 multipart 成功和哈希校验之前不能回 RECEIVED。

Worker 收到可核验的 RECEIVED 后，可以按契约清理交付副本，但未被中心保存的细粒度采集检查点仍需保留。释放代理／会话还必须满足 Rota 收尾条件；不能因对象上传成功就宣告所有在途请求结束。

### 7.4 事务与连接使用规则

1. 同一事务只使用同一个已借出的客户端；事务回调不能绕回全局 pool 执行本应原子的写入。
2. 外部 HTTP、S3、等待 Activity、长时间解析与压缩放到事务外；进入事务后重新校验可能变化的身份、版本和前置事实。
3. 锁按固定顺序获取；条件更新、唯一约束和结果行数共同判断是否取得写入权。
4. 设置按操作类型区分的 lock／statement／idle-in-transaction 预算。单条 statement_timeout 不是整个事务总时限。
5. 40001／40P01 等可安全重试错误重做完整事务；提交结果不确定时先按操作键查回执，不能无条件再次写入。
6. 回滚失败独立记录，不覆盖原错误；失效连接不回收到可复用池。失败路径避免持有一个连接再等待同池另一个连接。
7. PgBouncer transaction 模式仅用于兼容调用。LISTEN 与会话锁保留专用会话，不能在切换连接方式时破坏其生命周期。
8. 单次简单读取可用自动事务；多表一致快照、读锁与事务局部参数是显式只读事务的合理用途。
9. 连接预算按进程数、进程池、数据应用并发、长会话和运维预留计算，不用 Worker 数量直接乘一个猜测值。

### 7.5 表与查询治理

当前事实、热控制状态、观察历史、原始内容元数据和临时传输数据分别治理。小型可查询 JSONB 可以留在 PG；完整大响应优先对象化。PG 未改变的外置 TOAST 字段通常不会因更新其他列而重写，是否拆表应依据真实更新、读取、索引和 VACUUM 成本。

频繁更新的租约／游标尽量不与大型快照及大量索引放在同一热行。读取使用必要字段与有界分页；大列表优先稳定键游标，避免无上限 OFFSET。禁止每次 Dashboard 打开就默认精确统计所有历史行。

运行统计采用缓存、定时增量汇总和独立查询并发。只读副本可承接允许延迟的浏览，不用于领取、去重、迁移归属或检查点推进。长查询也要预算，避免影响副本回放和恢复。

时间分区优先用于可按时间到期删除的观察、事件或传输历史。分区后的唯一约束可能要求包含分区键，不能为分区而削弱跨时间幂等；全局去重需要独立账本或经评审的身份规则。

清理采用有界批次或安全分区退役；监控 WAL、死元组、长事务、复制延迟、索引增长和恢复空间。大表在线迁移／建索引必须另外编写变更方案，不在 Worker 启动路径自动执行。

### 7.6 数据库到底分成几部分

本节补充数据库详细设计。以下 `设计表`、字段组合、API 和索引是待实施契约，不是当前已存在的 schema，也不是已通过 Citus 验证的 DDL。当前表名依据 [schema.sql](../services/qybullmq/src/schema.sql)、[远程表](../services/qybullmq/src/remoteNodes/schema.sql)、[整频道传输表](../services/qybullmq/src/remoteNodes/wholeChannelSchema.sql) 与 [业务接收表](../services/qybullmq/src/businessPublicationSchema.sql)。

推荐先形成五个清楚的存储边界，爬虫数据层先运行普通 PG 主备，达到扩容门槛再迁验证后的 Citus。这里的“逻辑域”不等于必须立即新增独立数据库；有原子事务关系的表先留在同一实例内。

| 存储边界 | 保存什么 | 谁能写 | 扩容方式 |
| --- | --- | --- | --- |
| Temporal 内部库 | Workflow 历史、持久任务、计时等内部状态；Visibility 单独预算 | Temporal Server；应用不能直接修改内部表 | 按 Temporal 支持的部署与容量方案 |
| 爬虫控制逻辑域 | 查询词、发现页、策略版本、准入配额、派发与恢复索引 | 调度／发现控制模块 | 先隔离并发和索引；规模化时按控制业务域拆分，不把所有频道心跳集中写一行 |
| 爬虫频道数据域 | 频道事实、候选、运行、执行权、视频、结果回执、检查点、观察、发布源 | 数据接收／应用及受控 Store | 普通 PG → 兼容验证后的按频道共置分片 |
| 对象存储 | 原始响应、大型输入与结果、重放快照 | 受限对象接口及有授权的采集节点 | 独立存储容量与冗余扩展；不靠 PG 备库扩大对象容量 |
| 原业务接收库与 Rota 库 | 前者保存原发布 Inbox／投影，后者保存网络资源授权 | 原有业务接收器／Rota | 分别治理；不合并进 Temporal 内部库 |

频道执行权记录必须和受保护的频道写入在同一个原子边界内。控制域可以缓存“该频道在运行”，但缓存不能授权写入。如果将控制域另拆实例，采用频道侧持久意图和异步确认，禁止先在控制库验锁、再无条件写频道分片。

发现候选尚未通过资格验证时也需要执行权；目标设计可以建立轻量频道身份／执行控制记录，不能因此提前把候选升级成当前业务意义的已接纳 Registry 频道。

### 7.8 新增持久协议的数据字典

以下是设计表的最小字段契约，实施时可复用合适旧表，但不得仅依赖 Temporal 历史保存这些信息。

| 设计表 | 身份／关键字段 | 约束和用途 |
| --- | --- | --- |
| `channel_execution_state` | `channel_id`、`owner_engine`、`execution_epoch`、`active_run_id`、`lease_until`、`state_version` | 一频道权威控制行；版本条件更新；代次只增不减。细分互不冲突域前先验证同频道互斥 |
| `crawl_result_batches` | `channel_id`、`run_id`、`stage`、`logical_batch_key`、输入版本、提交代次、`payload_hash`、对象引用、`received_at`、`applied_at`、状态 | 唯一键覆盖频道和稳定逻辑批次；同键同内容返回原回执，同键不同内容隔离，不能静默覆盖 |
| `crawl_apply_intents` | 频道、批次身份、`next_attempt_at`、领取代次、状态、最后错误 | 与 RECEIVED 同事务登记；Workflow 未派发时仍可恢复；每批只允许合法领取者推进 |
| `crawl_checkpoints` | 频道、运行、阶段、分区／页段、已提交游标、连续完成位置、`checkpoint_version` | 游标只代表已经应用的范围；乱序批次先记录完成集合，不直接取最大页号 |
| `crawl_start_intents` | 频道、稳定运行键、计划版本、目标引擎、Workflow ID、状态 | 频道准入与启动意图同事务；启动 Temporal 失败可补偿，同一业务运行不会靠新 UUID 绕过去重 |
| `crawl_object_refs` | 频道／控制域、批次、bucket、key、version、hash、字节数、schema version、保留截止 | 不保存临时签名 URL 作为永久身份；多段上传 ETag 不等于内容 SHA-256 |
| `crawl_due_state` | 频道、任务域、`next_due_at`、优先级、计划版本 | 表示下一次业务采集资格，不表示已经有一个活动 Workflow；与完成事实一致推进 |
| 发布记录 | 沿用 Stream、channel、domain、sequence、revision、envelope hash、receipt | 优先扩展现有发布表，不能另创不兼容序列替换旧契约 |

稳定逻辑批次键由冻结输入与批次划分契约决定，不能每次 Activity 重试随机生成。执行代次是授权字段，不是允许重复应用相同业务批次的理由。新代次恢复旧已接收结果时，必须显式核验输入版本和可复用范围；未经授权不能应用旧执行产生的结果。

`RECEIVED/APPLIED` 属于采集批次；`DELIVERED` 属于发布事件。一个批次可能没有可发布变化，也可能生成多条不同域事件，因此实现上采用两套状态机和关联键，不能要求每个采集批次都对应一条 DELIVERED 记录。

### 7.9 四个明确的事务边界

| 事务 | 事务外工作 | 同一次 PG 事务必须完成什么 | 失败后依据 |
| --- | --- | --- | --- |
| T1 准入与派发 | 读取有界候选，检查总体容量 | 条件领取频道执行权、建立／核验运行与冻结输入、写启动意图 | 稳定运行键、执行代次与启动意图 |
| T2 接收结果 | 上传对象、核验版本／哈希／大小／权限 | 检查批次身份与授权，写对象引用、RECEIVED、Apply 意图 | 原批次键、哈希、接收回执 |
| T3 应用批次 | 读取解压对象，解析并准备有界写集 | 核验执行权与输入版本、去重、写事实／观察、检查点、必要发布变化、APPLIED | 原批次 APPLIED 回执；重复请求不得再增观察或发布序列 |
| T4 完成运行 | 检查任务域摘要，准备完成命令 | 复核所有必需域与批次完成、运行终态、下一次采集资格、必要发布收口与完成回执 | 完成命令身份与运行终态 |

T3 锁顺序建议固定为：频道执行控制 → 运行 → 批次／检查点 → 按稳定 ID 排序的视频行 → 发布域状态。该顺序需与保留的旧 Store 锁顺序一起评审，不能只让新代码遵守。

如果同一频道允许多个视频分段采集，它们可以并行做网络 I/O，但应用批次先按上述边界短暂串行提交。后续只有锁等待证明成为瓶颈，才评估拆域锁；不能在第一次重构时放弃频道完成和发布的原子保证。

无变化的事实更新应按字段版本／内容哈希跳过不必要的 `UPDATE`；是否仍生成观察由原业务观察契约决定，不能为了减写把必须保留的观测次数抹掉。单批提交规模以行数、字节数和事务 p99 联合限制；整频道百万视频不允许作为一个事务。

### 7.10 结果接收、应用、发布的故障处理

| 故障窗口 | 权威证据 | 恢复动作 |
| --- | --- | --- |
| 对象已上传，接收事务未提交 | 对象存在，无 RECEIVED | 原键重试登记；孤儿等待期内保留对象 |
| 接收事务已提交，响应丢失 | RECEIVED＋相同 hash | 返回原回执；不重采、不创建不同批次 |
| RECEIVED 后 Temporal 不可用 | 同事务 Apply 意图 | 恢复器补派发，受容量上限约束 |
| T3 执行失败且已确认回滚 | 无 APPLIED | 原批次重新准备并重试完整事务 |
| T3 提交时断线 | 提交结果未知 | 重连当前主库查询回执；必要时以相同幂等键重试，由约束和栅栏裁决，不能仅凭一次未读到记录判定未提交 |
| 旧 Activity 在新执行后恢复 | 当前 execution_epoch | 拒绝旧写入；已有合法 RECEIVED 是否复用走恢复协议 |
| 发布接收成功，源端回执丢失 | 业务 Inbox 中相同 revision/hash | 重发相同事件取回执；不重新分配 sequence |
| PG 主备切换丢失最近提交 | 复制策略、主库恢复点、接收端回执 | 按 RPO 对账；不能在异步复制下保证所有已确认写入永不丢失 |
| 对象丢失或损坏 | 引用存在但指定版本／hash 无法读取 | 停止该批次推进，恢复副本或从保留证据受控重建；不空包标记 APPLIED |

对象上传与数据库提交没有跨系统原子事务。正确性依靠不可变版本、持久意图、可重复登记和清理保护。RECEIVED 对外承诺必须同时说明对象冗余和 PG 同步复制／允许损失策略；仅设置数据库 `synchronous_commit` 不会自动配置同步备库。

### 7.11 查询接口与索引设计

目标 Store/API 让业务脚本调用有业务意义的操作，具体实现方式在进程内模块与受限 API 之间选择。爬虫脚本不直接拼跨表 UPDATE。

| 设计接口 | 查询形态／建议索引 | 一致性与限制 |
| --- | --- | --- |
| `getChannel(channel_id)` | 频道主键；按需关联小型当前事实 | 应用前置校验读主库；界面浏览可读允许延迟的副本 |
| `listChannelVideos(channel_id, cursor, limit)` | `(channel_id, published_at DESC, content_key DESC)`；若含空时间，定义明确游标排序 | 有界 keyset 分页；并发更新下需稳定快照语义或接受列表变化，不能称为精确历史导出 |
| `getRun(channel_id, run_id)` | `(channel_id, run_id)` | 单频道路由；返回阶段摘要和待处理计数，不读取完整历史 JSON |
| `getResultReceipt(channel_id, logical_batch_key)` | 批次唯一键 | 从主库核验提交；禁止副本延迟触发重复应用 |
| `listDueChannels(scope, cursor, limit)` | 到期状态上的有选择性索引；按范围分批 | 只生成候选；最终领取必须回到频道主库原子验证 |
| `listPendingApply(scope, cursor, limit)` | 对 RECEIVED 未应用记录的部分索引，含下次重试时间与稳定 ID | 有界恢复扫描；先受分片预算限制再派发 |
| `listPublicationBacklog(scope, cursor, limit)` | 未完成交付状态及下次尝试时间索引 | 发布版本顺序和归属仍由原协议裁决 |
| `getOperationalSummary(time_range, scope)` | 时间桶／角色／错误类别汇总表 | 展示汇总更新时间；不默认扫全部 contents、候选与历史观察 |

索引为候选设计，不是“全部建上”。必须用典型参数与热点参数检查执行计划、实际扫描行数、写放大、索引体积及 VACUUM 成本。全局精确总数采用受控离线任务；日常监控用增量汇总，必须保留重建和抽样对账机制。

热表不默认给整个 `raw_json/result_json` 建 GIN；确有业务过滤的 JSON 字段才考虑表达式索引。分页响应不包含原始大包；原始包通过有权限、有过期时间的对象读取接口获取。

### 7.12 原业务数据库接收如何衔接

```text
爬虫频道数据分片：事实／观察＋发布 revision＋publication.outbox
                       | 同一短事务产生发布意图
                       v
Publisher 多实例：有界领取 -> 提交原发布信封（事务外网络 I/O）
                       v
原业务接收器：校验 stream／channel 归属、revision、sequence、hash
                       |
                       +-> 业务 Inbox 持久接收 -> 返回原契约回执
                       +-> 按原流程应用 revision／业务投影
                       v
爬虫源端：保存匹配的持久回执，推进交付状态
```

两边 PostgreSQL 不共用一个本地事务；通过源端 Outbox＋接收端 Inbox＋幂等回执实现可靠交付。消息重复是正常恢复路径，同一身份不同内容才是冲突。业务持久接收、投影完成、爬虫采集完成是不同指标，不能将 HTTP 200 或 Temporal Activity 成功直接解释为所有投影已经可见。

下游变慢时先积压并限制发布并发；发布积压逼近磁盘／保留预算后再向 Apply 和新采集准入传播背压。不能用无限增长的 Outbox 换取表面上采集永不暂停。

### 7.13 数据库连接：明确谁能借、借多久、总共多少

目标架构中，网络采集节点不直连爬虫 PG。网络并发、数据应用并发、PG 客户端连接数、PG 实际后端连接数是四个不同指标。

```text
45 / 450 / 更多采集执行槽
          |
          | 对象直传＋小型结果登记（不创建爬虫数据库连接）
          v
数据服务多实例：接收／Apply／发布共用受控 Pool
  实例 A：Pool <= 8 ----+
  实例 B：Pool <= 8 ----+
  实例 C：Pool <= 8 ----+---> PgBouncer transaction ---> PG 活动后端
  实例 D：Pool <= 8 ----+       客户端可能等待              |
                                                        主库
调度／恢复：2 进程 × Pool <= 3 -----------^                |
专用会话：示例预留 2 条（按实际需求直连／专用入口）--------+

示例业务客户端上限：4 × 8 + 2 × 3 + 2 = 40
这不是推荐生产值；也不包括 Temporal、Rota、业务库各自的独立预算
```

这个示例要求 Publisher／查询没有偷偷另建 Pool，进程内模块也没有重复初始化池。以每个数据进程 8 个 SQL 槽为例，可先验证 Apply 上限 6、接收事务预留 1、其他短操作预留 1；查询与发布共用后者的有界排队，调度／恢复使用上图单独预算。若槽位动态借用，仍要保留控制与接收的最低服务能力。

```text
一次 Apply 的连接生命周期

等待任务 -> 取得对象工作槽 -> 下载／解压／校验／生成有界写集
                                              |
                       以上阶段不借 PG 连接    |
                                              v
                    取得 SQL 槽（有等待上限）
                                              |
                                              v
                 pool.connect -> BEGIN -> 业务 SQL -> COMMIT
                                              |               |
                                       异常则 ROLLBACK        |
                                              +-------+-------+
                                                      v
                                       释放／销毁失效连接
                                                      |
                                      归还 SQL 槽 -> 返回回执

连接释放之后才能等待外部发布、下一条网络请求或下一次重试
```

借连接前还应限制已准备写集的总字节数，不能下载一万个大对象后在 Pool 前堆积。外部调用各有超时；ROLLBACK 失败保留原错误并销毁失效连接；不能在已持有一个连接的事务中等待另一个同池连接。

三个连接预算分别核算：

```text
客户端潜在总量 = SUM(每类进程数 × 该进程所有 Pool.max) + 专用会话

PG 后端上限 = 各 PgBouncer 实例可连入该主库的上限之和
              + 所有绕过 PgBouncer 的连接

PG 可分配预算 = max_connections - 管理／应急预留 - 其他使用者预算
```

PgBouncer 的池通常按 database/user 等配置划分；DEFAULT_POOL_SIZE 不是整个部署的唯一总限额。两个 PgBouncer 若各允许连入 70 个后端，不会自动共享一个 70 上限。数据库／用户限制的作用范围、reserve pool、滚动升级期间旧新实例重叠都要纳入计算。Citus 还另算 Coordinator 到各数据组的连接，不能只限制应用入口。

当前 [db.js](../services/qybullmq/src/db.js) 的主 Pool 默认 max=10、连接等待 10 秒、空闲超时 300 秒；max 是上限，不表示启动立即建立 10 个连接。`withTransaction` 已在事务内设置 `publication.writer_version`；迁移时仍须核对其他入口和事务语义。当前 [compose.yml](../deploy/compose.yml) 模板已经设置 PgBouncer transaction 模式，模板客户端上限 500、默认池 40、reserve 10、数据库连接上限 70、用户上限 60；这些是模板值，不是本次线上读取结果。

因此本方案不把“改 transaction 模式”当成尚未完成的唯一修复。应审计所有实例的池总量、事务时长、实际等待、专用 LISTEN／会话锁及启动参数。模板忽略 `options` 启动参数，不能依赖它将任意会话设置传给后端；事务内参数与直连专用会话必须分别验证。

稳态可用 `平均活跃连接 ≈ 事务到达率 × 平均连接占用秒数` 做量纲估计。例如 100 个事务／秒、平均占用 30 ms 对应约 3 条平均活跃连接，但锁等待、突发和尾延迟会显著提高需求；不能据此断言 3 条连接足够，更不能靠调大 max_connections 消除慢 SQL。

## 八、面向一亿频道的数据分片方案

### 8.1 Citus 的候选范围

Citus 是 PostgreSQL 分布式扩展，可承担分布表的分片、SQL 路由、共置与再平衡，减少自研物理分片目录和迁移机制。它是容量候选，不是现有事务缺陷的修复工具，也不是整套爬虫 schema 的透明替代品。

优先验证频道当前事实、视频、频道内观察、批次结果、检查点和频道侧 Outbox，按 channel_id 共置。现有远程节点管理、全局任务领取、跨频道计划生产与会话监督锁先保持原有语义，不能因为名称属于 crawler 就全部分布化。

当前稳定发布与 PostgreSQL 兼容版本要作为完整组合锁定。例如本轮核查的 Citus 14.2.0 构建检查允许 PG 16／17／18，不表示可以在一个集群中混用任意大版本，也不代表其他扩展和现有 SQL 已通过验证。

### 8.2 当前 schema 的具体适配障碍

| 现有对象／操作 | 分片影响 | 必须提交的设计证据 |
| --- | --- | --- |
| channel_candidates 主键 candidate_id | 按 channel_id 分布时，主键／唯一约束需包含分布列 | 候选 ID 定位方式、引用表改造、跨批次去重语义 |
| contents 主键 content_key | 当前全局键不能简单改成频道内唯一后就宣称等价 | 全局内容身份、所属频道校验、查询路由和跨频道冲突处理 |
| content_candidates 的 run_id、位置及内容唯一键 | run_id 的路由信息与外键需要审计 | 同一运行相关表共置，原唯一性不被削弱 |
| channel_runs／Plan 的唯一约束 | 仅按 plan_id 查找时可能无法单分片定位 | 业务 ID 契约增加频道上下文或明确定位索引 |
| 全局 FOR UPDATE SKIP LOCKED | Citus FOR UPDATE 只支持单分片查询 | 改为带分布键的安全领取，或保留受控的本地控制表；完整 CTE／UPDATE 组合单独测试 |
| 会话／事务 advisory lock | PG 锁域不能假定跨所有 worker 实例共享 | 明确锁在哪个实例取得和失效；优先由合法执行权记录约束业务写入 |
| 外键、触发器和跨 schema 事务 | 共置要求、分布列与本地／reference table 限制 | 按事务调用链决定一起迁移的表，验证触发器执行位置及副作用 |
| 全局统计／排序／分页 | 可能变成跨节点查询和中心汇聚 | 限定频道／分片范围，使用汇总读模型和稳定分页 |

Citus 分布表 PRIMARY KEY／UNIQUE 通常需要包含分布列；分布表间外键需要满足共置及分布列要求。不能为了让 DDL 执行成功，静默降低原来“全系统唯一”的业务约束。

### 8.3 路由、共置与扩容

使用 Citus 时，以 Citus 元数据作为物理 shard placement 的权威；应用按稳定 channel_id 查询，由数据库路由。数据访问层可以携带数据集／迁移版本，但不再维护一份独立且可能过期的“频道→物理主库 IP”写入目录。

同频道的写入原子组建立共置关系，再平衡按共置组迁移。新增节点并非所有查询自动线性加速；需要检查 shard 数量、共置组大小、热点、协调节点负载、数据搬迁和复制所需空间。

若验证后不采用 Citus，应用分片才需要独立的逻辑分片映射、路由版本、迁移工具和故障接管。该替代路线增加的自研工作应明确记录，不与 Citus 路由同时成为权威。本方案不在首轮同时实现两套路由。

一频道多计算任务与一频道多数据库分片是两回事。先按页面／视频集合拆计算并保持数据共置；仅对实测超大热点频道单独设计内容桶。跨桶检查点、完成集合、全局唯一性和发布收口是新工程，不能假设普通频道方案自动适用。

### 8.4 Citus 验证不通过时

保留普通 PostgreSQL，继续执行访问层收敛、热冷分离、保留策略和资源隔离，不阻塞 Temporal 单独验证。只有证据显示关键业务需要频繁跨分片事务或 Citus 适配成本不可接受，再把 YugabyteDB 等列入独立迁移评估。

PostgreSQL 协议兼容不代表 LISTEN、advisory lock、触发器、隔离与重试语义全部等价。MongoDB 不作为当前大量关系约束与事务代码的直接替代。任何换库都必须用现有事务契约测试证明收益和正确性。

### 8.5 分片后一次频道写入究竟去哪里

```text
Apply Worker：channel_id + run_id + 稳定批次键 + execution_epoch
        |
        v
受限 Store / PG 连接池 -> Citus Coordinator 写入口
        |
        | Citus 按 channel_id 的分布规则与元数据路由
        v
数据组 B 当前主库：同频道共置原子组
  执行权 -> 运行 -> 结果回执 -> 视频／观察 -> 检查点 -> 发布源
        |
        +-- PG 复制 -> 数据组 B 备库（同一份数据的冗余副本）
```

一个物理数据组可以持有多个逻辑 shard；一个频道在正常设计中归入一个共置分片组。A、B 保存不同频道来分摊容量与写入；B 的主、备保存同一组数据来应对故障。增加备库通常不会提高这组数据的主库写入能力，增加协调节点也不能替代增加数据节点。

**先采用单写协调入口与故障切换入口，不宣称任意多个 Coordinator 都能同时安全写入。** 协调节点主备不等于多主；多协调入口／直连数据节点属于后续独立验证项。连接池只指向当前合法写入口，应用不保存物理 shard IP 来绕过 Citus 路由。

### 8.6 全局唯一性和跨频道操作怎么处理

| 问题 | 设计处理 | 迁移门槛 |
| --- | --- | --- |
| 两个发现节点找到相同频道 | 同一规范 channel_id 路由相同位置；频道侧条件准入；保留多个发现来源 | 重复输入只产生一个合法活动全量运行，来源不丢失 |
| 同频道重复视频 | 共置唯一键包含频道与视频身份 | 重试和多个结果批次不产生重复事实 |
| 同一 content_key 被不同频道错误声明 | 保留现有全局唯一规则；若改共置键，必须有受控的全局内容归属机制与冲突隔离 | 外部视频 ID 全局唯一不代表应用写入一定正确；未证明该约束等价前不迁生产 |
| 只拿到 run_id／candidate_id | 调用契约补 channel_id；必要时建立可校验定位索引 | 定位索引不得成为授权来源；定位失败不能散射更新全库 |
| 一页发现涉及多个频道 | 页面持久输入＋逐频道登记回执＋页面汇总恢复 | 中途失败能按缺失集合续跑，不依赖跨全部频道的大事务 |
| API 一批涉及多个频道 | 配额与 API 结果在批处理域登记；分别为频道生成消费意图／回执 | 一次 API 成功后局部频道入库失败不应再次无条件请求 API |
| 全局清单／排序／统计 | 有界读取或汇总读模型，单独预算 | 禁止业务热路径无界跨分片扫描 |

全局内容归属是本方案的明确 Citus 阻塞项之一：不能用 UUID 的低碰撞概率代替业务唯一约束，也不能随手把全量视频目录做成每个节点都复制的 reference table。可以在 PoC 比较保留原全局身份库与受控归属服务的成本，但跨库预约、孤儿清理、重放和故障恢复必须先通过验收；首阶段普通 PG 继续由原约束承担保护。

调度建议采用“有界到期候选读取 → 按频道原子领取”的两段协议。对 Citus 的跨分片到期读取设置并发、范围和批量上限；候选重复可由频道侧条件更新排除。不能把跨分片 `SELECT ... FOR UPDATE SKIP LOCKED` 当成普通单库领取直接复制，也不能只加一个普通 bucket 字段就假定查询已经单分片路由。

### 8.7 时间分区、分片与扩容过程

分布按频道解决机器间分摊，时间分区解决历史维护，两者职责不同。频道当前事实和长期去重身份不因日期自动淘汰；观察历史、事件、已完成传输记录才优先按时间管理。分区粒度、分布 shard 数与共置组数量必须共同测量，否则“月份数 × shard 数 × 表数”会造成过多物理对象和维护开销。

新增数据组的生产流程：

1. 新组先建立主备、备份、监控和故障切换，确认版本／扩展与原集群一致。
2. 盘点待迁共置组的容量、写入率、复制延迟、临时空间和 WAL 预算；不能只按频道数量均分。
3. 使用已验证版本的 Citus 再平衡能力迁移共置组；是否在线、锁窗口、复制标识要求和失败恢复，以该版本实测为准。
4. 搬迁期间限制新采集／Apply／回填总负载；业务仍经权威协调入口，不自行双写新旧物理分片。
5. 验证行与键、批次 hash、APPLIED、检查点、发布序列和待交付 Outbox；观察路由及主备延迟后再恢复并发。
6. 原 placement 的清理、备份链与可回退边界单独确认，不能在刚搬完时删掉唯一恢复来源。

普通 PG → Citus 的初次迁移不是一次普通再平衡；它涉及数据模型、约束和应用契约变更，仍须执行第 14.3 节的影子验证与切换。

### 8.8 主备部署、连接与容量预算

生产参考角色如下，数量用于说明故障域，不是当前机器配置或吞吐承诺：

| 角色 | 基础形态 | 故障处理与资源约束 |
| --- | --- | --- |
| 普通爬虫 PG | 一主＋至少一独立宿主机备库 | 主库故障切换；同步／异步由 RPO 与延迟决定；读取旧数据的副本不能参与领取 |
| Citus Coordinator | 一主＋独立备库 | 连接入口跟随合法主库；元数据和集群级切换一起验证 |
| Citus 数据组 | 每组一主＋独立备库；生产分片试验至少验证两个数据组 | 多组才可验证跨组路由、搬迁与局部故障；一组故障是否影响其他组要实测 |
| Patroni 仲裁／DCS | 常见参考为 3 个成员分布于独立故障域 | 数据库一主一备不等于具备安全选举；仲裁不应全部跟着同一宿主机失效 |
| 备份仓库 | 独立于数据库数据盘与单个对象存储故障域 | 保留基础备份与 WAL，验证恢复点；备库不能替代备份 |
| Apply／接收 API | 多实例，单独 CPU／内存预算 | 总并发受每个数据组及协调入口共同限制；故障恢复时逐渐回补 |

若有 N 个数据组，采用一主一备时仅 Citus 数据库实例就约为 `2 + 2N` 个，另计 Temporal、Rota、业务库、仲裁及对象存储。多个实例挤在同一服务器不能提供对应的物理容错。本方案不要求初期就部署此规模，先完成独立普通 PG 主备与数据应用限流。

连接预算从真实借用时间推导：稳态活跃连接量可粗估为 `事务到达率 × 平均占用秒数`，再按尾延迟、突发和运维预留设计上限；不是看到 45 个采集 Worker 就要求 450 个 PG 后端。还要计算所有 Apply、Publisher、调度、恢复器的进程连接池总量，以及 Citus Coordinator 到数据节点的连接放大。

容量预算至少拆开当前事实、运行工作集、历史观察、索引、对象、WAL、复制槽滞留、备份、搬迁临时空间。主备复制和对象冗余另乘其真实策略；不能只用“一亿 × channels 行大小”估算整个系统。扩容触发看增长斜率、磁盘安全余量、事务 p99、锁等待、复制落后和回补速度，具体阈值由压测与恢复演练填写。

### 8.9 数据库工作包必须交付什么

1. 按本节表归属给出 ER 图与逐表数据字典，标明旧字段、拟增字段、唯一键、外键、保留期与读写责任人。
2. 给出 T1～T4 以及发布接收的事务调用图；列出所有绕开 Store 的 SQL 并逐个迁移。
3. 提交重复登记、提交断线、旧执行回流、乱序批次、字段未知值、对象丢失、主备切换的契约测试结果。
4. 提交前十类热查询的执行计划与数据量、连接池等待、事务时长、WAL／VACUUM、历史清理和恢复耗时报告。
5. 单独提交 Citus 全局内容身份、候选外键、跨频道 API 批次、发布共置、全局领取和备份恢复的验证；任一关键不变量未通过，保留普通 PG。

## 九、容量、背压与数据生命周期

### 9.1 一亿频道的数量级示例

以下采用十进制容量，均为假设计算，不包含索引、副本、WAL、对象冗余和临时空间，也不是数据库性能承诺。

| 假设 | 推算 |
| --- | --- |
| 一亿频道，每条基本信息平均 1 KB | 约 100 GB |
| 每频道平均 100 个视频 | 100 亿条视频记录 |
| 每频道平均 1,000 个视频 | 1,000 亿条视频记录 |
| 每频道每轮原始包平均 1 MB | 每轮约 100 TB |
| 每天更新 1% 的频道 | 每天 100 万，平均约 11.6 个频道／秒 |
| 所有频道每周更新一次 | 平均约 165 个频道／秒 |
| 所有频道每天更新一次 | 平均约 1,157 个频道／秒 |

容量表必须补上单频道请求数、视频量分布、重复更新比例和峰值因子。总写入不是“频道数”一个指标：频道完成速率乘每频道提交批次、行数和字节数，才接近数据层负载。

平均在途量可用“到达速率 × 平均处理时长”估计，但还需留尾延迟和恢复余量。恢复能力必须大于正常到达量；净排空速率等于恢复处理速率减新到达速率，不能用总消费速度直接估算清空积压时间。

### 9.2 调度策略

频道全集保存在业务数据库，按到期时间、优先级和频道 ID 的合适索引分批选择。活跃、低变化、休眠和失败隔离频道使用不同频率；保留反饥饿规则，不能让低优先级永久无法被处理。

采用普通 PG 时可以利用本地原子领取；采用 Citus 时全局到期选择与锁定必须用第八节通过验证的实现。调度器只为可接纳工作创建业务派发意图和 Workflow，不一次性将一亿条记录展开到 Temporal。

### 9.3 端到端背压

| 信号 | 应采取的动作 |
| --- | --- |
| Full Crawl 待处理数量／最老年龄超预算 | 减少新发现，保留资格反馈和恢复处理 |
| 数据应用积压或事务延迟超预算 | 降低新采集准入，优先消化已持久结果 |
| 对象存储上传错误或空间不足 | 停止新增大结果任务，不把失败数据转存到 Workflow 历史 |
| PG 连接等待／锁等待增加 | 降低对应分片数据应用并发，避免所有角色一起重试 |
| Rota／API 配额不足 | 推迟相应任务，避免占用浏览器与数据连接等待 |
| Temporal 历史／检索压力增加 | 减少无效心跳和事件、大批次结果引用化，调整有界执行 |
| 某频道成为热点 | 单频道预算／批次拆分，避免抢占全部写入资源 |

Task Queue 限流控制活动派发速率，不替代网站全局速率、代理资源、租户／频道公平性或 PG 写入预算。各层预算由同一个容量决策协调，避免队列限流正常但数据库仍被多个任务队列共同打满。

### 9.4 保留与清理策略

| 对象 | 保留原则 | 删除前的条件 |
| --- | --- | --- |
| 频道／视频当前事实 | 按业务生命周期长期保留或归档 | 有明确删除／撤回规则，不以任务完成替代 |
| 原始快照 | 按证据重要性、变化及重放价值分级 | 所需重放窗口已过，引用和审计规则满足 |
| 观察历史 | 保留必要维度与期限，避免每轮复制全部对象 | 分区／批次删除不破坏长期身份和当前投影 |
| 批次幂等账本 | 覆盖全部允许重放、备份恢复和迁移回滚窗口 | 不再存在可提交旧结果的授权；永久身份另有记录 |
| Outbox／接收回执 | 未交付、未应用不可清理；终态按审计期限保留 | 对账完成，重放与唯一性不依赖即将删除的数据 |
| 本地 spool | 活跃未确认数据保留，stale／blocked 有界归档 | 中心能独立恢复或已明确终止，并保留必要证据 |
| Temporal 历史 | Namespace 保留策略与历史归档需求单独决定 | 不将历史保留当业务数据备份，也不靠它永久去重 |

不得通过把一切移到对象存储来回避增长控制。备份、复制、再平衡和恢复临时空间必须纳入总容量预算。

### 9.5 高并发背压图：扩采集节点不自动扩写入并发

```text
业务待采全集（PG）
         |
    [准入预算] <---------------------------------------------------+
         |                                                       |
         v                                                       |
Temporal 活动窗口：只派有限在途批次                               |
         |                                                       |
  [采集并发 C]    网站／Rota／机器限制                             |
         |                                                       |
  [上传并发 U]    对象连接、带宽、内存、未确认本地数据限制           |
         |                                                       |
  RECEIVED 积压：批次数＋字节数＋最老年龄 -----------+               |
         |                                        |               |
  [解析工作槽 P]  CPU 与解压后字节预算               |               |
         |                                        |               |
  [Apply SQL 槽 A]  主库连接／锁／WAL 预算           |               |
         |                                        |               |
     APPLIED                                      |               |
         |                                        |               |
  [发布并发 D] -> 下游持久接收                     |               |
         |                                        |               |
  Outbox 积压 ------------------------------------+               |
                                                  |               |
                      高水位：先减新准入／非关键重试 --------------+
                      低水位：滞后确认后逐步恢复，避免反复开关
```

C、U、P、A、D 分别设置，不用一个 `concurrency=100` 控制全部阶段。每个限制同时写明作用域：单进程、单机器、单 Task Queue、单数据组或全局；仅配置单 Worker 的 Activity 并发，增加 Worker 后总量仍会成倍增长。

先取得容量再实例化大量任务／Promise。内存队列同时限制条数和字节数；持久积压也有容量和年龄上限。接收服务只在完成 T2 后承诺 RECEIVED，不能在内存队列里排队就返回耐久成功；达到接收容量上限则返回可识别的延期／拒绝，采集侧保留未确认结果并停止扩大在途量。

容量分配可由低频准入控制器发放有限执行预算，数据进程在本地闸门落实，预算总和受主库容量约束；最终业务所有权仍由 PG／Rota 校验。不要为每条视频再增加一次中央“是否有容量”的同步 RPC。扩副本、滚动更新、失联实例恢复都要重新计入预算；预算服务故障时不得自动变成不限流。

接收／续租／取消留独立服务配额；重放和发布可以继续消化已接收数据，但也不能无限占用数据库。热频道设并发与字节配额，新发现、增量、修复按业务优先级公平分配，避免大频道长期占满全部 Apply 槽。

### 9.6 数据量图：中心瓶颈要按字节和事务测量

```text
                    小信封、回执、心跳
采集节点 --------------------------------------> 控制／接收入口
    |
    | 大型原始／结果对象
    v
对象存储 -------------------读取---------------> Apply 节点
    ^                                              |
    | 必要校验／恢复读取                            | 结构化写集
    +----------------------------------------------+--> PG

站点流量、对象流量、PG/WAL 流量分别计量；共享网卡仍会竞争
```

假设每秒 20 个批次、每批线上实际对象大小 4 MB，仅上传即约 80 MB/s；Apply 再完整读取一次又约 80 MB/s。若接收校验还需读取整对象，会再增加读取流量。这个例子不含协议开销、重试、压缩前内存、存储冗余复制和备份；如果这些流量经过同一受限链路，采用长连接也无法消除带宽瓶颈。

上传阶段独立检查对象来源、版本和校验能力；不能未经验证就假定 HEAD 返回的 metadata 已证明完整内容。采用支持的可靠 checksum 或不可变对象协议可以减少重复读取，但要证明其语义，不能为性能省掉完整性校验。

采集节点直接连接对象入口，避免应用中心转发全部字节。对象节点的存储／复制网络与数据库资源尽量隔离；同一台机器多容器不提供带宽、磁盘 I/O 或 CPU 隔离保证。控制连接池分开后仍需给网卡、CPU、文件描述符和内核连接资源留余量。

```text
估算与测量用量纲（不作为固定配置）

每秒批次数   = 每秒完成频道数 × 平均每频道批次数
每秒 SQL 数  = 每秒批次数 × 每批 SQL 数 + 控制／恢复／发布 SQL
对象上传速率 = 每秒批次数 × 平均对象线上字节数
进程内存     >= 基础内存 + 在途上传缓冲 + 解压工作集 + 待写集合
净排空速率   = 消费速率 - 新到达速率
排空时间     ≈ 积压量 / 净排空速率（净速率必须大于 0）
```

批次不能越小越好：过小增加 RPC、Temporal 历史、对象请求数和事务提交次数；过大增加内存、锁持有、重试字节及恢复时间。按行数、压缩／解压字节、采集时长和事务 p99 联合选择，不能仅设每批固定视频数。试点比较几个候选批量，记录有效完成数和失败后的重放代价再定参数。

### 9.7 故障恢复图：避免所有节点同时重试

```text
PG 变慢／切换
     |
     +--> SQL 闸门维持上限；超时调用释放／销毁连接
     +--> Apply 积压上升；接收容量逼近上限
     +--> 减少新采集准入；保留未确认 journal
     +--> 各客户端退避＋抖动，禁止无间隔循环建连
     |
PG 恢复并确认合法写入口
     |
     +--> 先小流量核验写入／回执／租约
     +--> 同操作键重放，拒绝旧 execution_epoch
     +--> 分批恢复 Apply 与发布
     +--> 积压净下降后逐步恢复新采集
```

```text
Temporal 暂时不可用                 对象存储暂时不可用
       |                                   |
SDK 按策略重连                       暂停新增大结果工作
已有采集受本地窗口／授权约束           未确认结果留在有界 journal
已有 RECEIVED＋意图保留在 PG           不往 Workflow / PG 填巨型包
不可新派发的 Apply 等待恢复            不返回虚假的 RECEIVED
       |                                   |
恢复后按持久意图补派发                 恢复后复用对象／批次身份续传
```

不要承诺 Temporal 故障时所有工作照常执行；没有可用派发服务，尚未领取的 Activity 就会等待。已运行 Activity 是否继续由业务期限、Rota 授权和本地容量决定，不能因拿不到完成确认就无限继续采集。

关闭或滚动升级节点按“停止新领取 → 限时排空活动任务 → 取消并确认网络静默 → 保存未确认数据 → 关闭连接池”执行。`ready` 与 `live` 分开，过载实例不接新任务但保留回执／收尾能力；重连、健康探测与恢复扫描不能互相造成重启风暴。

## 十一、安全、版本和操作约束

1. Temporal 服务入口使用受控网络和认证授权；Namespace 用于隔离运行范围，但不能仅靠名称当安全边界。Worker 只访问所需队列与服务，按最终版本的授权机制配置。
2. 远程采集不发放 PG 管理权限。对象访问采用最小权限、短期授权或受限上传接口；不复用 MinIO root 凭据给所有 Worker。
3. Rota 密钥、Cookie、数据库密码不写入 Workflow 历史、Search Attributes、日志或对象可公开路径。需要长期保存的敏感会话沿现有加密与身份契约处理。
4. 所有应用和平台镜像锁定摘要，配套记录 Node／Python／Go、Temporal Server／SDK／UI／CLI、PG／扩展的兼容矩阵。固定 Tag 不自动等于不可变内容。
5. 现有部分镜像默认 Node 20；按本次日期其维护期已结束。升级受支持运行时作为独立兼容任务，不与首次业务切换混成一个不可定位的大变更。
6. Schema migration 由独立发布步骤执行并验证版本，不由每个 Worker 启动时竞争执行。扩展、索引、回填和约束启用分步骤、可观测。
7. 退出时先停止领取，再等待有界收尾、持久化检查点并停止在途请求。超过停机预算时依照恢复契约退出，不谎报成功。
8. 权限收紧、旧凭据撤销和消息服务退役属于最终部署阶段，当前文档交付不执行这些操作。

| W2 执行归属与交接 | engine、epoch、稳定业务意图、双引擎拒绝、交接账本 | 现有执行身份／业务栅栏、Controller 与派发器 | 在新引擎写生产事实之前，全部旧写路径也必须执行检查 |
| W3 Temporal 基础 | Server／SDK 版本、Workflow Worker、Activity 契约、历史预算、重放测试 | 新增适配包，复用当前领域函数 | 独立测试环境；无业务 SQL 藏在 Workflow 中 |
| W4 增量与结果传输 | Plan 适配、Rota API、对象引用、接收回执、Apply Activity、恢复 | remoteNodes、incrementalCoordinator、wholeChannelCollector、spool | W1～W3；全套断线和旧执行测试 |
| W5 Discover／Full Crawl | 发现分页、候选合并、资格反馈、全量恢复 | worker.js、channelSnapshot*、fullCrawlYoutubeJs* | W4 稳定后；不改变原资格与采集范围 |
| W6 Agent／后处理／发布 | 独立队列与计算预算、领域终态和持久回执 | local-agent、Agent Backlog、Finalize、Publication | 分批迁移；不修改下游发布口径 |
| W7 容量与 Citus 验证 | 实际 SQL 兼容矩阵、共置数据模型、约束保持、故障和再平衡测试 | schema.sql、结果应用与查询路径 | 与单库 Temporal 验证解耦；不通过不迁生产 |
| W8 运维与可观测 | 部署模板设计、版本升级、监控、备份、恢复手册 | 现有 deploy 与运行手册 | 生产切换前完成核心恢复演练 |
| W9 灰度与退役 | 交接清单、灰度证据、回滚记录、NATS／旧队列依赖清零 | 全链路角色、镜像与配置 | 第十三至十六节门槛全部满足 |

不能并行切换编排引擎、全部数据分片、运行时大版本和业务发布模型。这样一旦出现差异，无法判断是采集、传输、存储还是数据模型变化导致。

## 十三、新旧引擎的业务交接协议

### 13.1 先建立共同执行栅栏

需要为会产生冲突写入的业务范围定义唯一执行归属，至少包含 channel_id、允许的 engine、单调递增的 execution_epoch、迁移状态、当前业务意图及策略版本。这里是逻辑模型，实际优先扩展已有执行身份体系，避免另建无法协调的第二套频道锁。

同频道的全量和增量如果会相互覆盖，必须共享能够阻止冲突的归属规则；不能仅按不同队列名各自允许一个“独占执行”。合法可并行的采集批次则在同一业务代次下用独立操作键区分。

在普通 PG 阶段，每次短写事务持有归属行的兼容读锁并核验 engine／epoch；切换事务取得排他锁，确保先前合法事务完成后才封住旧代次。只在事务开始前读一次普通 SELECT、不持锁也不做提交条件校验，不能证明切换与旧写入之间没有竞态。

所有旧 Writer，包括采集、恢复、Agent、结果应用、发布事实生成和管理修复路径，先部署并验证统一检查。仍可能写入而未经过栅栏的旧镜像存在时，不允许新引擎同时取得写权限。过渡阶段通过现有写入版本／权限机制阻止未知 Writer，不能只依赖 Dashboard 上的停用标记。

未来迁入 Citus 时，归属检查与频道数据写入需重新证明处于有效原子边界。把归属行留在独立控制库、再无保护地写数据分片，不等价于当前单库事务。

### 13.2 派发意图与 Workflow 启动的恢复

1. 业务事务创建稳定意图、冻结输入哈希和待启动记录，提交后才能调用 Temporal。
2. 启动适配器用确定性 Workflow ID 在事务外启动；运行中冲突与已存在情况核验业务身份，不能终止旧执行来“保证成功”。
3. 成功后记录启动回执。若启动成功但回执写入失败，重试以相同意图查验／重复启动，仍指向同一合法业务执行。
4. PG 已有终态回执时，不因 Temporal 历史过期再次执行相同业务操作；有意重抓必须创建新的合法业务代次。
5. Workflow 的首个有副作用 Activity 重新验证 engine／epoch。旧启动请求晚到或控制状态已回滚时，流程可以启动但不得取得采集与写入授权。

启动对账按明确意图与执行状态进行，不用最终一致的 Visibility 列表判断“没查到所以重新做”。业务接收／应用意图也沿同样的稳定键和回执模式恢复。

### 13.3 灰度范围的状态转换

```text
LEGACY_ACTIVE
      |
      | 停止该范围新增旧意图，已授权执行可有界收尾
      v
DRAINING
      |
      | 核验旧任务、结果、网络授权和发布事实
      | 封住旧写入，保存快照／交接账本
      v
SEALED
      |
      | 原子提升执行代次，指定 Temporal 为唯一执行引擎
      v
TEMPORAL_ACTIVE
```

这些是迁移控制状态，不替代现有业务 Run 状态。交接账本至少记录：频道／业务范围、旧 Run 与 attempt、最后应用批次与游标、未决 API／Agent 工作、待应用结果、已产生但未交付 Outbox、网络收尾证据、新意图与新代次。

DRAINING 不能只看 BullMQ waiting=0。还要查 active／delayed／重试意图、PG received 未应用结果、NATS 待确认、节点 spool、仍有效的 Rota 授权与可能恢复的旧进程。不可达节点不能被当作已安全清空，需要撤销其有效授权并验证旧写入被拒绝，保留可追溯恢复记录。

未交付的旧业务 Outbox可以继续在其原契约下交付，不能重建相同数据版本再发布一次。是否允许发布过程中迁移频道，由其版本顺序与接收回执验证，不靠队列数量推断。

### 13.4 已在途任务的处理原则

优先让有限旧执行完成后再切换；无法及时完成的任务先按现有协议停止、保存并核验检查点，再创建显式恢复意图。不能把 BullMQ 的内部 Job 状态直接复制为 Temporal 历史。

已有 whole-channel 原始结果继续用旧兼容接收器完成验收，或经专用迁移工具验证身份／哈希后导入新的接收契约。不能仅改字段名后把旧 spool 当新 Activity 结果；损坏或身份不明的载荷隔离处理。

## 十四、分阶段实施、灰度与回滚

### 14.1 阶段计划

| 阶段 | 可评审交付物 | 进入下一阶段的条件 |
| --- | --- | --- |
| P0 设计冻结与基线 | SQL／事务清单、业务不变量、版本矩阵、目标值、样本集 | 明确哪些是缺陷、风险、正确保护；团队选定试点范围 |
| P1 现有链路治理 | 共用数据契约、错误处理与查询治理、共同执行栅栏 | 旧引擎行为验证通过，所有写路径可审计 |
| P2 隔离环境原型 | Temporal＋样本 PG／对象存储、一个完整增量流程、故障测试 | SDK／历史／回执／Rota 边界证明可恢复 |
| P3 只读影子对比 | 对已有固定证据重放解析和应用计划、结果差异报告 | 不额外发起生产抓取、不写生产事实；差异有解释 |
| P4 增量小范围切换 | 按第十三节交接的明确频道集合、回滚证据 | 覆盖正常、超时、API、Agent、国家复核与节点重启 |
| P5 逐步扩大 | 按负载类型扩大，经过完整调度周期和峰值 | 无未解释数据差异；持续积压、资源及成本达标 |
| P6 Discover／全量及后处理 | 独立集群、资格反馈、批次恢复、发布契约 | 全链路失败矩阵与数据对账通过 |
| P7 NATS／旧队列退役 | 所有消费者迁移、旧凭据与载荷处置、退役记录 | 第十五节清单全满足；保留受控回滚／恢复材料 |
| P8 分片扩容 | 独立 Citus PoC、迁移设计、容量和故障报告 | 单库方案可用，分片兼容和收益已有证据，再另批生产迁移 |

阶段先后可调整非依赖的准备工作，但不能跳过共同写入栅栏和故障恢复验证。进度以交付物和证据管理，不用未经估算的固定天数保证完成。

灰度集合按频道规模、采集域、失败模式、代理区域和数据量分布选择，不仅挑最容易成功的小频道。观察窗口覆盖完整计划周期、积压回补、版本发布和至少一次受控故障演练；其时长按第一节的业务周期确定。

### 14.2 回滚步骤

1. 停止受影响范围的 Temporal 新准入，冻结新的启动意图；保持结果接收、数据库和对象存储可用。
2. 对活动执行请求取消并等待有界收尾，收集网络静默、检查点和已接收结果。即使超时也不直接开启旧引擎并发写入。
3. 以共同执行栅栏封住当前代次；校验在途短事务完成，阻止迟到的新引擎写入。保存交接账本与故障证据。
4. 核对 PG 中已经成功的事实、批次、待发布 Outbox 和业务回执；回滚执行引擎不回滚已经合法交付的数据。
5. 确认旧版本能读取当前 schema、业务版本和恢复快照；不兼容时进入暂停／向前修复，不能强行启动旧 Writer。
6. 提升代次并切回已验证的旧引擎，按持久事实补足未完成工作，避免重做整个频道。
7. 对比回滚后的业务结果、迟到写入拒绝、网络资源和重复交付，结束回滚观察后再扩大接单。

恢复代码镜像不等于恢复数据库。迁移阶段采用扩展后收缩的兼容 schema；旧字段／旧接收器的删除晚于对应回滚窗口。不能通过清空 Temporal 库、删除新业务数据、倒退 execution_epoch 或覆盖新结果实现回滚。

### 14.3 数据分片迁移是独立变更

Citus 上线另行执行：选定共置原子组 → 影子建模与回填 → 增量追平／变更捕获 → 逐频道或共置组暂停写入 → 校验游标、版本、数量、哈希及 Outbox → 切换访问层 → 保留旧数据为受控恢复来源。

不得让应用长期自行双写两个库并假设不会分叉。跨库复制的来源顺序、唯一键、DDL 变化和恢复点需要明确；旧库停止写入后再让新库成为唯一权威。回退时也必须处理新库已提交的增量，不能仅把连接串改回去。

## 十六、测试与发布验收矩阵

本节是未来需要执行的测试，不是本轮测试结果。先在隔离环境和受控数据集验证，生产压测与故障演练另行安排。既有测试入口见 [12 测试验收计划](12_测试验收与实施计划.md)，需对新旧适配器复用业务断言。

### 16.1 必须成立的业务不变量

- 同一业务批次重复提交只产生同一份合法结果，不重复增加计数、视频或发布版本。
- 旧 engine／旧 epoch 的写入被拒绝；超时与迟到结果不能覆盖新事实。
- 检查点只越过已应用内容，未完成或延期项目不能被静默跳过。
- 候选和发现来源可追溯，资格未决不被当作零合格或已结束。
- PG 已有有效结果时，回复丢失不使其回退为未执行；提交不确定要按键核验。
- 全量、增量、Agent、API fallback、国家复核、发布顺序保持既有业务口径。
- 系统故障后可从持久记录恢复；不依赖某个 Worker 内存或已丢失的消息。

### 16.2 故障与兼容测试

| 场景 | 注入位置 | 应验证的结果 |
| --- | --- | --- |
| Activity 完成回复丢失 | PG 提交后、Temporal 收到完成前 | 重试返回原批次回执，不重复写入 |
| 业务意图启动回复丢失 | Workflow 已启动、派发回执未提交 | 稳定 ID 与业务键恢复同一意图 |
| 历史过期后旧意图重放 | Workflow retention 窗口外 | PG 幂等记录仍阻止非法重复 |
| 旧节点网络隔离 | Activity 超时、新执行开始后旧节点恢复 | 旧数据库写入与旧路由授权失效 |
| 节点进程崩溃 | 页面中间、对象上传中、接收后、应用前分别测试 | 有界重放，检查点不超前，已接收结果可独立应用 |
| 对象异常 | 缺失、截断、哈希不符、multipart 未完成 | 不返回有效 RECEIVED，不推进检查点 |
| PG 故障 | 连接断开、COMMIT 回复丢失、主库切换 | 保留原异常、查询结果回执、按策略重试，无双主写入 |
| SQL 竞争 | 热点频道、重复候选、固定锁顺序冲突 | 唯一约束和条件更新有效，重试有预算 |
| 全局派发竞争 | 多调度实例同时处理同一到期意图 | 同一合法意图只获得一个有效执行归属 |
| 发现反馈 | 多来源发现同频道、资格延迟／失败 | 来源保留，分页遵守原资格反馈规则 |
| 大频道与大结果 | 极端视频数、原始包、长期分页 | 参数和历史有界、内存可控、不把内容塞入 Workflow |
| Worker 升级 | 新旧版本共存、旧历史重放、回滚 | 无决定性错误，旧执行仍可恢复 |
| Continue-As-New | 有子任务或正在处理 Signal／Update | 只在安全边界滚动，结果与在途工作不丢失 |
| 暂停与回滚 | 旧／新引擎在途写入和延迟消息 | 交接代次单调，已成功数据不倒退 |
| NATS 退役 | 隔离环境完全关闭 NATS 与旧客户端 | 所有新链路功能及故障恢复正常，旧节点无法绕过 |
| Citus 兼容 | 实际 DDL、claim、保存点、外键、触发器、锁 | 列出逐项结果，不以简单 INSERT／SELECT 代替 |
| Citus 扩容与故障 | 再平衡、worker／coordinator 切换 | 共置与约束保持，访问恢复，搬迁资源不压垮写入 |
| 存储恢复点不一致 | Temporal 与业务 PG／对象恢复到不同时间 | 按意图／回执／版本对账，不丢已承诺数据或重启过期授权 |

### 16.3 性能验证

先记录同输入、同硬件预算、同目标站请求规则下的旧链路基线，再比较 Temporal 适配后的有效完成速率、失败分类、外部请求放大、对象／SQL 写入量及成本。不能用更多机器和不同采集内容得到的数字直接宣称框架更快。

至少测试正常负载、峰值、长期运行、一个下游降速和故障后的积压回补。关注各阶段 p95／p99、数据库连接等待、事务时长、锁等待、WAL、复制延迟、对象存储延迟、事件循环／CPU 和 Temporal 历史增长。

对同一结果不允许出现无法解释的差异；测得的吞吐和延迟必须满足冻结目标，故障后积压应在目标窗口内净下降。若出现静默数据丢失、旧代次成功写入、重复业务版本或无法恢复的检查点，停止扩大灰度，不能用平均成功率抵消。

### 16.4 节点交互和连接的专项验收

| 试验 | 必须收集的证据 | 通过条件 |
| --- | --- | --- |
| 采集节点逐级增加、数据层容量固定 | C/U/P/A/D、客户端／后端连接数、队龄、有效完成速率 | SQL 并发与后端连接不越预算；压力通过有限积压和准入控制反馈 |
| 数据服务扩容／滚动升级 | 新旧进程池总量、PgBouncer 各实例后端数 | 过渡期也不突破数据库预算，不因加一副本隐式翻倍 |
| 多 origin、大结果、慢对象读取 | socket、每类请求队列、控制 API p99、内存／事件循环延迟 | 上传压力不拖到租约安全窗口之外；无无界内存增长 |
| HTTP/2／负载均衡断开长轮询 | poll 失败、重连分布、各后端负载、重复执行／业务键 | 正常恢复，无同时洪峰、旧执行越权或重复业务应用 |
| PG 慢 SQL、锁冲突、连接中断 | 借连接等待、事务占用、回执查询、连接销毁、重试次数 | 连接释放可证明；提交不确定按幂等恢复，不无限堆在池前 |
| Rota 延迟／不可用 | 剩余租期、实际停网时间、续期队列 | 授权到期前停止不合法请求；不靠延长超时掩盖失权 |
| Temporal 中断、数据入口重启、业务端变慢 | RECEIVED／APPLIED／交付差额与恢复意图 | 数据可恢复，积压受控；恢复后净排空速度满足冻结目标 |
| 同吞吐下比较不同批量 | RPC／频道、字节／频道、SQL／频道、事务 p99、历史事件量 | 选择在正确性、尾延迟与恢复成本均合格的批量 |

上线前冻结每类请求 deadline、心跳／续期安全窗口、队列条数／字节／最老年龄阈值、连接总预算、恢复目标和负载样本；未填写不能将本节视为已验收。预期过载时应受控降低准入；无限排队、无限重试或连接持续增长均不属于“高并发稳定”。

## 十七、监控、备份与灾难恢复

### 17.1 统一可观测标识

日志与追踪贯穿 channel_id、业务意图、plan_id／run_id、execution_epoch、batch_id、Workflow ID／Run ID、Activity 标识、对象哈希与发布版本。明确哪个标识用于永久业务去重，哪个只用于一次运行诊断。

监控至少覆盖：

| 层 | 关键指标 |
| --- | --- |
| Temporal | Schedule-to-Start、Activity 执行／失败／重试、Workflow Task 失败、历史大小、检索延迟 |
| 采集 | 有效频道完成率、请求数、重复抓取比例、代理／API 配额、事件循环与浏览器资源 |
| 数据应用 | RECEIVED 最老年龄、APPLIED 延迟、幂等命中、旧代次拒绝、批次大小 |
| PG／Citus | 活跃／等待连接、事务／锁、慢查询、WAL、自动清理、复制延迟、shard／coordinator 热点 |
| 对象存储 | 上传／读取失败、延迟、容量增长、冗余健康、孤儿对象、恢复时间 |
| 业务交付 | Outbox 最老年龄、拒绝分类、数据序列缺口、回执一致性 |
| 运维 | 证书过期、版本漂移、备份完成与可恢复性、磁盘余量、迟到旧节点 |

告警指向处理动作和受影响范围，例如降低某分片新准入，而不是只显示一个全局“系统繁忙”。指标名称、基数与保留预算需控制，不能把每个频道 ID 都设成长期监控标签。

### 17.2 备份恢复

Temporal 主存储、Visibility、爬虫 PG、Rota 状态和对象存储分别制定备份与恢复策略，记录 schema／镜像版本、恢复点和校验方法。副本不是备份；同宿主机多个容器不是独立故障域。

普通 PG 采用经过验证的基础备份与 WAL 恢复流程；Citus 使用兼容版本的分布式备份／恢复方案，不能任取各节点不同时间的快照就当作全局一致。Rota 的 TimescaleDB 恢复需遵守扩展的专用步骤。

跨存储没有天然统一恢复点。灾难恢复时先冻结新任务和旧节点授权，恢复数据并核验对象引用，再对照业务意图／批次回执与 Temporal 历史：业务 PG 已提交但 Workflow 未知时，Activity 重放返回原结果；Workflow 记为完成但业务备份缺少结果时，必须从可验证证据修复或明确报告数据损失，不能继续当作成功。

RPO 必须覆盖这种组合恢复风险，不能只说“Temporal 会重试所以零丢失”。恢复后重新建立业务执行权并处理旧节点，避免旧授权复活；历史中记录的旧令牌不能直接作为新授权使用。
