一、已确认的问题与证据

1. 远程增量任务出现 PostgreSQL 40P01（deadlock detected）。失败堆栈指向
   refreshVideoPublicationItemHashes，即更新 crawler.contents.publication_item_hash。
2. 已观察到的等待链：
   - 增量事务持有频道记录锁；更新内容时，外键检查需要关联历史全量 Run 的 KEY SHARE 锁。
   - 全量收尾事务持有该 Run 的 FOR UPDATE 锁，随后等待同一频道记录锁。
   - 双方循环等待，PostgreSQL 中止其中一个事务。
3. 已核查日志中的 8 个冲突频道：原始全量 Run 的首次收尾时间均早于本次增量，
   当前收尾状态均为 ready_auto。三个详细核查样本的再次收尾原因均为
   controller-finalize-source-change，针对同一个历史全量 Run。

三、实施分期

第一阶段：实施二次收尾退让机制。
保留现有收尾资格和下游发布语义，解决事务争锁、任务延期及恢复问题。

第二阶段：收窄重复收尾的业务触发条件。
按本次明确的业务规则：首次收尾允许失败恢复；首次成功后，普通增量变化走自己的

此阶段独立验证、上线和回滚，避免与并发机制混在一次变更中。

四、第一阶段详细流程

1. 识别二次收尾
   使用持久化的首次收尾证据、当前 Run、任务用途及修复身份进行判断。
   不仅依赖队列 reason，也不能把 ready_partial 直接当作首次发布已经完整完成。
   首次未成功的任务继续正常恢复；明确需要执行的二次收尾进入退让流程。

2. Controller 入队前轻量避让
   在读取大量视频内容、计算 source_revision 前，检查同频道有效的增量执行状态。
   正在执行则暂缓投递；仅排队可以短暂避让，但不能无限等待未启动的增量任务。
   队列信息用于提前避让，数据库有效执行归属用于核验，不能只凭 Job 存在判断忙碌。
   这一步存在检查后状态改变的窗口，最终互斥由写事务保证。

3. 统一同频道写事务入口
   复用 publicationChannelMutationLock.js 的频道级 PostgreSQL 事务锁键，
   增加 pg_try_advisory_xact_lock 非阻塞获取方式。
   二次收尾在每个相关写事务开始时尝试获取：
   - 成功：重新校验频道、Run、任务归属和数据版本，按统一行锁顺序执行并提交。
   - 失败：立即结束事务并释放数据库连接，转入延期处理。

   增量落库必须遵守同一个频道锁协议，覆盖本地增量、远程中心和 API 续跑等相关入口。
   获取频道锁必须发生在冲突相关行锁之前。必须审计外层事务已有的 task、Plan、
   binding、Run、attempt 等锁；不能在持有 Run 锁后再补一个频道锁。
   现有使用同一频道锁的发布、生命周期和修复入口也必须核对锁顺序。

   初始观测写入、提交前检查、最终提交是不同事务，每个事务都要遵守协议。
   第一次获取成功不代表后续仍持有锁。网络抓取、对象存储上传及可提前完成的计算
   放在持锁事务外；外部计算结果在提交前必须重新验证版本。

4. 持久化延期并释放 Worker
   顺序为：结束争用事务 -> 持久化延期意图 -> 将已有 Job 移到 delayed。
   记录频道、Run、待处理 generation、延期原因、首次等待时间、延期次数与下次尝试时间。
   状态写回使用任务归属/租约条件，避免旧执行覆盖新任务状态。
   暂缓不得推进 handled_generation，不得标记业务收尾成功。

   Worker 将退让识别为正常调度，正确传递 BullMQ Job token；释放执行名额，
   不把延期写成抓取失败或消耗业务失败重试预算。
   当前 worker.js 的通用异常处理需要显式适配，不能只抛出延期异常了事。

   数据库恢复意图与 Redis 延迟操作不是同一原子事务。必须覆盖二者之间崩溃、
   队列任务丢失、旧任务仍活跃等情形，由持久恢复记录、Job 身份和租约检查补偿，
   不得因此重复执行或丢失收尾需求。

5. 独立延期期限
   当前变化触发器会将 next_check_at 重置为 now()，单用此字段会被增量写入取消延期。
   建议增加独立 defer_until，并记录诊断所需的原因、计数及首次等待时间。
   领取任务时同时检查到期条件；新变化可以增加 requested_generation，但不能清除
   既定退让期限。Controller 变化消费、补漏扫描和 Worker 延期需保持一致。

   建议初始延期 5～15 秒并加入随机抖动；连续争用时逐步增加，最高例如 60 秒。
   这些是待压测调整的初始参数，不是已经部署的配置。

6. 恢复执行
   到期后重新检查需求是否仍有效，重新读取最新源数据及版本。
   旧 Run 或旧修复身份失效时淘汰旧任务；新 generation 的需求仍须保留。
   成功提交后只确认本次实际处理的 generation，执行期间产生的新变化不得误确认。
   观测、游标、业务数据和待发布记录继续保持必要的事务原子性、幂等性。

7. 优先级与饥饿边界
   - 增量先取得频道锁：二次收尾立即延期。
   - 二次收尾先取得频道锁：增量短暂等待它完成提交，不抢占进行中的事务。
   - 不同频道使用不同锁，保持并行。
   - 长期延期需要指标和告警；更强的公平调度可后续增加，不能自动认为非阻塞尝试
     已保证必要修复最终一定执行，也不能让修复无限饥饿。

五、锁模式与异常兜底

1. 继续统一显式行锁顺序，并覆盖外键 KEY SHARE 和提交期延迟外键检查。
2. 对只保护普通状态、不修改被引用键、也不依赖阻止外键插入来实现归属隔离的锁，
   验证后可使用 FOR NO KEY UPDATE。禁止全局替换 FOR UPDATE。
3. remoteNodes/incrementalBusinessFence.js 明确利用 Run 强锁阻止新 attempt 插入；
   此类执行隔离能力必须保留。
4. 有限事务重试可作为单独补充：仅对已审计、可安全重放的纯数据库事务，40P01 后
   完整回滚并最多重试 3 次，每次重验归属；复用已保存抓取结果。
   提交响应丢失、结果不明确的网络错误不能直接按死锁盲重试，应查询幂等结果。
