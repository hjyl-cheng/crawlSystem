# 中心服务与数据库压力实测

时间：2026-09-22 08:40–08:45 UTC（北京时间 16:40–16:45）。生产只读观测，未调整并发、数据库参数、服务或任务。使用 diagnosing-bugs 性能测量路径：连续生产采样，不施加额外抓取负载。

## 判断

数据库读盘与任务行锁等待已经出现在实时抓取链路中，会增加准备、结果应用和收尾的等待。中心 Node 主线程也接近单核上限。全量、增量、发布补偿和面板统计共享中心/数据库资源，存在相互竞争的路径。

不过本次没有做停止全量与开启全量的同负载对照，不能量化“全量使增量降低多少百分比”，也不能认定所有慢任务都是数据库造成。全量并未持续占满 10 个槽位，本次不是满负荷容量测试。

## 资源测量

主机和 cgroup 连续 120 秒差分，数据库每 10 秒采样，共 13 次；随后单独进行了 30 秒中心线程 CPU 差分。

| 指标 | 实测 | 含义 |
|---|---:|---|

PostgreSQL buffer miss 对应读取约 432 MiB/s，shared buffer hit 约 75.6%；这包含 OS cache 命中，不能将其当作物理磁盘读取。实际设备读速率应采用 cgroup 166 MiB/s。主机设备 vda 约读取 248 MiB/s，说明还有其他工作负载共享设备；设备 util 与短窗口低平均 await 不足以证明硬盘带宽已经耗尽。

当前 `shared_buffers=1GB`，此前 9 月 20 日的调整已经生效；`work_mem=4MB`、`effective_cache_size=4GB`、`effective_io_concurrency=1`。`pg_stat_statements` 未加载、`track_io_timing=off`，因此没有每条 SQL 的累计 I/O 耗时与调用次数归因。

## 数据库具体等待

13 次快照中的 active 会话样本：36 次 DataFileRead、1 次 WALSync、12 次 transactionid 锁等待、35 次 CPU/可运行、2 次 ClientRead、1 次 IPC。这是会话采样次数，不是 SQL 次数，也不是任务耗时比例。

已定位的优先路径：

1. `publication-reconciler-v1` 对 `channel_runs/channels/finalized_profiles` 的终态收敛 UPDATE，13 次采样持续可见，最长已执行约 170 秒，多数采样等待 DataFileRead。
2. 面板 Daily Clock 统计查询，包括 selected_plans/materialized 和跨表聚合，采样见约 20.6 秒，主要等待 DataFileRead。
3. 中心 `SELECT ... FROM remote_ingestion.tasks WHERE task_id=... FOR UPDATE` 反复等待 transactionid 锁，单次观测约 2.65 秒。节点接单、续约、命令及结果处理共用任务行，事务持锁与往返影响延迟。
4. 迁移指标聚合查询采样见约 5.35 秒，处于读盘等待。

因此优化不应只盯采集结果 INSERT。后台历史扫描、统计查询和任务行临界区也在与前台采集争用。

一次 outbox 全部未发布记录的只读聚合在 8 秒 statement_timeout 下被取消；没有对该查询做 EXPLAIN ANALYZE，不把这一次超时扩展成生产发布器本身一定堆积的结论。

## 抓取效率

增量：最近 10 分钟 1,033 个成功且远程任务 generation=1 的样本，从远程 task 创建到 applied：

| 阶段 | 平均 | P95 |
|---|---:|---:|
| task 创建 → 采集指令生成 | 5.52 秒 | 7.59 秒 |
| 指令生成 → 回执收到 | 6.37 秒 | 12.09 秒 |
| 回执收到 → task applied | 3.32 秒 | 6.37 秒 |
| 合计 | 15.21 秒 | 未单独统计 |

准备与应用平均合计 8.84 秒，约占上述区间 58%。它们包含数据库、中心计算与协议调度，不全是 SQL 耗时。该区间不包含排队、远程 task 创建前的准备和 applied 后的清理，且排除了失败、重试、未完成任务。

独立任务事件口径：最近 10 分钟增量 completed 事件 1,119 个，涉及 1,119 个不同 job，约 112 job/分钟；成功事件记录时长 P50 21.58 秒、P95 40.15 秒。失败事件 49 次、涉及 48 个 job。该完成量不等同于 Feature Plan 全部已成功应用。

5 次 Worker 状态采样：增量部署 82 个，实际 ready/active 62 个，另外 20 个 connected 但 allowed=0、standby。平均 11.2 个处于 collecting、50.8 个归为 processing（其中含 preparing）。状态分类只用于观察占用，不直接当作耗时比例。

全量：10 个就绪，采样时实际 active 4–6 个。近 30 分钟仅有 36 个已应用回执批次，收到后应用平均 3.61 秒、P95 6.12 秒；全量 details 阶段完成样本只有 3 个，不足以代表全量总体分布。

全量 140 个 received 未应用回执核对后：139 个属于已 failed task，1 个属于 `UPLOADS_COUNTRY_RECHECK`。这些不是 140 个活跃任务同时排队等数据库写入。全量通用队列还存在 delayed 工作和下游 finalize prioritized 积压，需按业务阶段分析。

近期中心 NATS 指标多数 rpc pending=0，偶见 1；心跳超时=0。累计 RPC timeout=849 在所查近几分钟保持不变，不能把历史累计值解释为当前新增超时。

## 推荐顺序

1. **先减少昂贵数据库扫描**：终态收敛改为状态变化驱动、有界待处理集合和低频补漏；面板统计使用短时缓存/预聚合，索引和查询计划逐项验证。不要为提速直接关闭发布、恢复功能。
2. **缩短任务行事务**：剖析连接池等待、取锁等待和持锁时长；减少重复读取及事务往返，将 JSON 解码、哈希等纯计算移出持锁区，提交前重新验证 generation/lease/business fence，保持幂等和所有权约束。
3. **剖析中心主线程**：定位调度循环、重复校验、序列化、解码等 CPU 热点。根据结果将重计算或结果应用拆到受控后台进程/worker threads。若拆分中心进程，必须维持唯一 supervisor 与任务所有权，不能直接多起相同实例争抢。
4. **隔离并行预算**：为全量与增量分别设置有界执行/结果应用并发，保留增量资源预算；只有前端调度与后端应用均有容量，扩采集 Worker 才可能提高吞吐。增加数据库连接可能放大争用。
5. **最后评估硬件与参数**：先去除无效扫描并复测，再按共享内存预算评估 shared_buffers、存储和独立数据库主机。若使用只读副本，应放面板统计等容忍延迟的查询，任务租约/所有权和关键一致性读取仍走主库。

前一轮诊断发现的 waiting_gap、详情续跑及失败状态残留是独立正确性问题，应单独修复；数据库提速不会自动消除它们。

建议在同等任务构成、同等网络条件下做 30 分钟以上的分档并发对照，记录增量有效完成量、全量有效完成量、总任务 P95、结果应用 P95、失败/重试率及发布积压。当前只能确认共享数据库等待和中心主线程压力，不能承诺具体提速倍数或给出可承载 Worker 上限。
