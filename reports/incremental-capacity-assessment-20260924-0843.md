# 增量抓取容量评估：2026-09-24 08:43 UTC

## 结论

当前扩容的首要约束是中心 Node.js 主线程及数据库交互路径，代理/TLS 失败是第二类明显损耗。55 个 worker 均在工作且有待处理任务；缺任务或大量 worker 离线不是本次样本中的主要原因。

增加 worker **可能有边际收益，但不能按 worker 数量线性推算吞吐**。中心主线程已经接近单核满载，主连接池持续排队，增加并发也会增加中心调度、事务、锁与失败处理压力。目前不建议直接从 55 扩至 75/100；优先削减中心热路径开销和网络失败耗时，再用 55→60 的受控试验验证边际收益。本次只读评估，没有修改 worker 数量、连接池、预算或生产配置，也没有实际扩容试验。

## 瓶颈证据

### 1. 中心共享路径：证据最强

- 中心主线程 CPU = **0.957 核**；进程遥测均值约 1.07 核。事件循环利用率 **98.82%**。4 核配额并不意味着单个 JavaScript 主线程可以利用 4 核完成同一串行路径。
- gateway 主连接池采样平均 **48.19** 个等待者，最大 **79**；被采样的 other 类连接获取均值 **209.90 ms**，连接持有均值 **50.50 ms**。这些是采样指标，不是所有 SQL 的完整延迟分布。
- heartbeat 池等待均值 0.0028、最大 1；result 池等待为 0。当前排队主要集中于主业务池，不能笼统归因于所有连接池都满。
- 事件循环 P95 延迟指标的样本最大值 34.57 ms，说明接近忙满与长时间卡死不是同一概念；主线程高占用仍限制并发扩展余量。

278 个成功任务样本的平均执行阶段：

| 阶段 | 秒 |
|---|---:|
| 接入：任务开始→远端任务建立 | 1.28 |
| 准备：任务建立→采集命令建立 | 3.32 |
| 采集与传输：命令建立→中心接收 | 9.88 |
| 落库：中心接收→applied | 2.51 |
| 收尾：applied→队列完成 | 3.13 |
| 执行合计 | 20.12 |

接入、准备、落库、收尾合计 **10.24 秒，占 50.89%**。这些是中心协调相关的墙钟时间，包含数据库、RPC、协议和等待，**不能说成全是中心 CPU 时间或全部可消除**。采集与传输阶段也不是纯远端网络时间。另有从 dispatched 到 started 的平均等待 21.30 秒；该等待不应重复计入占用 worker 的执行时间。

### 2. 数据库读盘和事务竞争：中心瓶颈的重要组成

- 爬虫 PostgreSQL 占用约 **3.17 核**，容器实际块 I/O 读 **53.80 MiB/s**、写 **12.29 MiB/s**。服务器 CPU busy 63.44%、iowait **8.49%**。
- pg_stat_database 缓冲区未命中读取折算 **87.06 MiB/s**，命中率 90.89%；这是 PostgreSQL 页读取口径，包含操作系统缓存，不能与物理磁盘吞吐混为一谈。
- 7 次数据库快照中的活跃会话观测：DataFileRead 9 次、transactionid 锁等待 7 次、CPU/runnable 12 次。这些是会话样本次数，不是等待时间百分比。
- 所有捕获到的事务锁等待均落在 gateway 的 `remote_ingestion.tasks ... WHERE task_id=$1 FOR UPDATE`；最长采样 query age 2.67 秒。
- 主要关系页读取包括 content_candidates 16.57、tasks 15.05、channel_execution_attempts 14.87 MiB/s。tasks 更新约 46.42 行/秒，finalize_recovery_requests 41.19 行/秒，channel_runs 24.45 行/秒；这些是全库相关表活动，尚未用调用栈逐一归因。
- 本窗口死锁计数无增长，最后快照无超过 5 秒的活跃查询；没有依据称数据库已经全面停顿，但已有实质 I/O 与锁竞争。

因此，仅增加主连接池上限可能把等待进一步推入数据库，不能作为已经验证有效的方案。

### 3. 代理/TLS 失败：持续损耗有效执行能力

稳定 30 分钟内队列失败事件共 **153**：150 次执行路由预算耗尽、2 次 upstream_transient、1 次 unknown。未观察到 BUSINESS_RUN_BUDGET_EXHAUSTED 或 STALE_LEASE 队列失败。

- 150 次执行路由预算失败全部匹配到开始事件，平均耗时 **44.99 秒**，合计 **6748 秒**；按失败结束时刻归属窗口，折合 **3.75 个持续忙碌 worker**，约占配置并发 6.8%。这不是精确截窗并发积分，也不是可全部回收的净损失，前期有效采集和跨窗口执行可能包含其中。
- 另 3 次失败耗时合计 103.93 秒。
- 网络诊断项：CONNECT 502 共 **241** 项，curl 35/TLS 类共 **203** 项，未分类 curl 56 共 1 项。诊断项可能在一次执行中多次出现，不能据此计算请求失败率。
- 队列失败对应 145 个不同 job，其中 8 个在窗口内失败 2 次。这说明仍有正常或待改进的重复尝试；**不能说所有重复失败都消失了**。本窗口没有旧的业务预算终态被误归为 system_retry 的队列证据，但没有对所有 Run 历史重新做完整终态审计。
- 新诊断支持代理隧道建立失败、TLS 类失败仍存在；无法单凭这些聚合定位到具体供应商、代理质量、TLS profile 或 relay 的唯一根因。

加 worker 不能直接提高每条路由的可靠性，也会增加路由和中心失败处理压力。

## 建议次序与可验证条件

1. **先优化中心热路径**：对任务状态推进、重复查询与 FOR UPDATE 临界区做调用级定位，减少不必要的数据库往返与重复状态写入，缩短持锁区间；分析主线程 CPU 热点后再决定批处理、缓存或进程拆分。保留既有租约、Run 终态和路由隔离规则。验收看每个成功计划的中心 CPU/SQL 成本、gateway 等待和执行 P95。
2. **并行降低网络失败成本**：按 route/proxy/profile 关联 CONNECT 502 与 curl35，验证真实采集失败后的隔离、回收及探测代表性；不以延长预算或盲目增重试掩盖失败。验收看成功计划/min、失败占用秒和失败路由复发率。
3. **完成上述优化后小步扩容试验**：先核对内存及合格代理 reserve，再在 55 与 60 worker 下各取稳定窗口，最好采用 55→60→55 对照并控制任务类型占比。比较成功业务计划/min、队列完成/min、P95、主池等待、锁/I/O 和网络失败成本。吞吐没有稳定增长、等待或失败成本恶化时，不继续加并发。该试验尚未执行。

179.20/min 是当前任务组成下的实测吞吐，既不是经过负载实验测出的系统硬上限，也不能保证增加到 60 worker 就达到按比例推算的吞吐。
