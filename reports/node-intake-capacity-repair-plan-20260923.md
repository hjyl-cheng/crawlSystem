# 节点接单与容量同步修复方案

日期：2026-09-23。状态：第一阶段三项接单修复已实施、部署并完成 30 分钟功能与恢复验收；第二阶段已完成只读评估，锁拆分/索引等性能改造尚未实施。结果与性能边界见 [上线验收报告](node-intake-capacity-repair-20260923.md)。

目标：解决“容量已经满足，点击开始接任务仍因资源同步暂缓返回 503，接单状态不切换”的问题，并让用户准确知道请求是否保存、Worker 是否已就绪。优先修复调用流程，再根据测量结果决定数据库并发优化范围。

**1. 已知事实与范围**

- 事故链路：Dashboard 开始接任务 → 中心 `capacity.ensure()` → Rota 资源同步 → 锁竞争导致同步暂缓 → 启动请求未保存。
- 05:41:40、05:42:16 UTC 两次开始请求返回 503；05:45 重试成功；05:50 节点02的 8 个 Worker 已全部连接、就绪、运行。以上是历史验收时间，不代表编写文档时重新采样。
- 同期所需名额为远端 85 + 本地配置 62 = 147，实际配置及持久容量目标为 154。名额是配置容量，不等于健康代理数、空闲名额或正在执行的任务数。
- 日志出现 `control_advisory_lock_busy`，两次失败响应长度与 `RESOURCE_SYNC_DEFERRED` 一致。原始响应正文未保留，无法确定两次失败各自的锁检查位置及持锁者。
- 代码确认容量同步、领取、续租、任务开始/完成及协调任务共用 Rota 控制锁。已有同步成功样本持锁约 9ms，准备约 525ms；单个样本不足以代表延迟分布。
- 磁盘恢复、事件补送和节点重连已完成，详见 [恢复报告](disk-recovery-20260923.md)。本次不重复执行这些恢复动作。
- 本方案第一阶段不需要数据库表迁移。现有证据不支持为解决这次 503 而重建数据库、增加名额或扩容硬件。

**2. 第一阶段：容量满足时直接返回**

修改 Rota `services/rota/core/internal/proxycontrol/capacity_target.go`，必要时将只读校验封装在相邻模块。

先执行现有鉴权、控制功能启用检查及请求参数校验，再用数据库一致快照检查：

1. 当前 workload/role 的持久容量下限已达到请求值；只靠进程配置或内存缓存满足，不能代替本应持久化的下限。
2. 当前有效目标为配置下限、持久下限、请求值三者的最大值；该目标对应的受管名额名称、编号及必需 pool/user 关联完整。
3. 名额检查遵守现有共享资源及 workload 语义，不把其他角色、异常编号或名称的记录凑成有效容量。

全部满足时，返回兼容现有格式的 `ok/role/provisioned`。此路径不调用资源同步、不争用资源同步互斥锁或全局 advisory lock、不执行 bcrypt、不重复写容量目标。健康路由仍由现有协调器维护，任务仍需通过现有执行准入。

仅凭 `count(*) >= minimum_slots` 不足以证明资源完整。目标缺失、记录不完整或确实需要扩容时，继续走现有事务路径：持久目标使用最大值更新，按需创建资源，失败整体回滚。只读检查失败应正常报错，不能把数据库查询异常解释为“容量足够”。

并发安全条件：快速路径不承诺具体空闲槽位；后续领取仍受租约和任务保护。必须验证周期资源清理尊重持久下限，且不存在可绕过该下限删除必需资源的受支持路径；若存在，应先补齐该路径的协调规则。不得以快照证明替代后续执行准入。

**3. 第一阶段：仅对明确的同步暂缓有限重试**

修改中心容量调用边界 `services/qybullmq/src/remoteNodes/deploymentCapacity.js`，按需要为 `proxyControlClient.js` 增加请求级超时/取消支持。

- 建议初始策略：总计最多 3 次尝试，间隔约 200ms、500ms，并加入少量随机抖动；参数须经集成测试验证。
- 自动重试限定为 HTTP 503 且明确错误码为 `RESOURCE_SYNC_DEFERRED`。鉴权失败、参数错误、容量上限、未知 503、断网和超时分别报错，不混成锁竞争。
- 整个容量步骤共享最多 12 秒预算，包含请求、读取响应及退避；每次请求只使用剩余时间。不能把现在的 12 秒单次超时直接乘以 3。
- 页面及 Dashboard 到中心目前均为 15 秒超时。发布前核查代理超时，并为容量步骤之后的状态事务及响应留出时间；如预算不够，调整执行接口整条链路并增加取消传播，不能只延长其中一层。集成测试必须证明外层超时不会截断正常的有限重试。
- 只设一层重试，保留底层该容量客户端 `maxAttempts:1` 或采用等价单层实现，避免嵌套放大请求数。
- 同一次容量重试复用相同的绝对目标数，不在 154 上累加 147，不重试整个部署登记/启动事务。
- 等待期间不持有中心节点事务锁或 Rota 控制锁。容量成功后仍执行现有节点状态、部署数量、版本及 `expectedRequested` 校验；并发暂停不能被迟到的开始请求覆盖。
- 暂停接任务继续独立于容量服务，Rota 故障时仍可暂停。

**4. 第一阶段：保留失败原因并准确显示状态**

当前 `deploymentCapacity.js` 的统一 catch 丢失原因；Dashboard 的容量错误文案为“网络名额自动扩容暂未完成……节点登记已保留”，不能准确表达开始接任务失败。

需要贯通中心错误对象/响应序列化、Dashboard `nodeRuntime/deploymentControlClient.js`、`serverNodesRoutes.js`、`serverNodesClient.js`：

- 保留旧顶层 `REMOTE_NETWORK_CAPACITY_UNAVAILABLE` 以兼容旧客户端，新增白名单原因字段，例如 `RESOURCE_SYNC_DEFERRED`、`CAPACITY_TIMEOUT`、`CAPACITY_SERVICE_UNAVAILABLE`、`CAPACITY_AUTH_FAILED`、`CAPACITY_INVALID_RESPONSE`；具体名称在实现时固定为测试契约。
- 日志记录关联请求标识、节点、所需/已配置容量、尝试次数、耗时及脱敏原因。页面只显示安全、可采取行动的说明，不透传数据库错误、凭据或任意上游正文。
- 开始请求进行中：显示“正在准备接单…”，同一节点禁用重复点击。同步 HTTP 接口不额外声称正在第几次重试，除非确有服务端进度数据。
- 明确同步暂缓且重试耗尽：“资源准备繁忙，本次启动未成功，请稍后重试。”页面重新读取真实接单状态。
- 请求已保存但 Worker 尚未就绪：“已开启接单，Worker 正在准备。”展示连接、就绪和运行数量；就绪但暂时没任务也属于正常状态。
- 浏览器超时、断网或响应丢失：显示“操作结果暂未确认，正在刷新状态”，通过只读状态接口核实；查不到结果时保持“状态待确认”，不能声称启动未保存，也不自动重发开始请求。
- 部署登记失败提示与开始接任务失败提示按操作区分；保留冲突、权限和容量上限的准确文案。

**5. 回归测试与验收门槛**

实现时先用隔离 PostgreSQL 和真实调用链建立失败测试；生产不注入持锁故障。

| 场景 | 必须验证的结果 |
| --- | --- |
| 持久目标/实际完整名额 154，请求 147，另一个连接持有控制锁 | 容量接口仍返回成功，不进入资源同步；运行中的任务、租约、路由、凭据不变 |
| 进程内 resourceSyncMu 已被占用，容量仍完整 | 快速路径成功，不因资源同步互斥而失败 |
| 总数够，但必需名额缺失或编号/名称不匹配 | 不误走快速路径，进入正式修复/同步流程 |
| 名额够但持久目标缺失或不足 | 正式事务持久化目标；重启不会因下限丢失缩减所需容量 |
| 控制禁用、未授权、参数无效 | 快速路径不能绕过现有校验 |
| 真正扩容，首次暂缓、后续解锁 | 有限重试成功，只保存一次启动请求；容量按最大目标增长 |
| 锁持续占用 | 尝试数及总时限受限，返回明确原因，启动请求未被该操作保存 |
| 鉴权失败、未知 503、超时、非法响应、返回容量不足 | 原因分类准确，不当成同步锁忙重试 |
| 同时开始/暂停、过期 registry 版本或部署变更 | 冲突校验保持有效，不覆盖较新的状态 |
| 重试与并发扩容、较小目标重复请求、创建途中失败 | 容量不重复累加、不降低下限；资源创建失败整体回滚 |
| 运行中任务遇扩容、服务重启 | 保留租约、路由代次、活动任务及既有凭据，新增名额可正式领取 |
| 服务端保存成功但响应丢失 | 页面刷新后显示真实状态，不虚报失败、不自动重复提交 |
| Rota 不可用时暂停；没有新任务时已就绪 | 暂停仍成功；页面不把正常空闲显示为启动失败 |

优先扩展现有测试：Rota `capacity_target_postgres_test.go`、API 容量测试和资源同步锁测试；中心 `remoteDeploymentCapacity.postgres.integration.test.js`、`remoteIntakeContention.postgres.integration.test.js`、`proxyControlClient.test.js`；Dashboard 执行路由、控制客户端和浏览器行为测试。

既有并发容量测试需核对线上 TryLock 语义：真实扩容期间可以暂缓，由调用层重试；不能为了让测试中所有并发调用立即成功而改为长期等待全局锁。核心数据库集成测试必须实际执行，环境缺失导致跳过不能算验收通过。

**6. 发布顺序、生产验收与回滚**

1. 发布前重新采样节点接单设置、连接数、容量目标/完整名额数、任务入库速率、积压年龄、续租成功率、锁等待和磁盘空间。历史的 147/154、85/85 只用作对照，不硬编码到实现或验收中。
2. 核对 Rota、中心、Dashboard 各自实际运行镜像及源码，基于各自生产版本建立隔离修复分支。Rota 记录版本为 `resource-sync-lockfix-20260922-r5`，中心记录版本为 `pachongsys-8313058-fullcrawl-fix-20260922`；部署时重新确认。保护已有 Feature ingest/Finalize 修复，不将主工作区全部改动一起发布。
3. 先构建并验证全部镜像，记录摘要、原容器规格及回滚镜像，检查只包含预期改动且无意外待执行迁移。先发布兼容旧响应的新 Dashboard，再发布中心原因透传/有限重试，最后发布 Rota 快速路径；每步验收后继续。
4. 按服务现有生命周期进行受控替换。Rota 重启前覆盖所有依赖它的本地与远端采集方，暂停新领取并等活动执行安全收尾；中心使用正常关闭和恢复机制。不得删除或强行清空活动租约来加速发布。达不到安全切换条件时保留旧实例运行并调整窗口。
5. 恢复发布前记录的接单设置，避免把备用节点开启。通过正式接口做容量幂等检查及一个受控节点的接单验收；并发开始/暂停故障测试在隔离环境完成。生产端不为测试反复切换全部节点。
6. 建议观察至少 30 分钟并覆盖正常业务负载：容量足够时命中只读路径；节点开始请求成功或返回准确原因；无重复容量增长；Worker 连接恢复；续租及任务完成持续推进；没有新增租约/路由代次错误或持续积压。与发布前相同负载窗口比较延迟和失败率，而非要求所有业务任务零失败。

回滚触发：发现容量错误放行、并发状态覆盖、重复分配、持续续租退化、Worker 无法恢复，或接口延迟/错误持续超过基线。停止后续发布，先受控停止有问题的新实例，再按相同生命周期恢复该服务上一镜像及原配置，验证实际接单状态。

回滚只回退应用版本，不回退业务数据库、不降低持久容量目标、不恢复旧数据卷覆盖新任务。Rota 回滚目标须支持持久容量下限；若只能用不支持的旧版，必须先核对并配置不低于当前持久目标的静态下限。第一阶段没有 schema 迁移，减少回滚耦合。

**7. 第二阶段：数据库并发与读取压力专项**

这部分独立评估，不作为第一阶段上线的前提，也不把所有数据库压力都归为本次锁竞争。

- Rota 控制库：按操作记录控制锁等待/持有时间的 p50/p95/p99、同步暂缓次数及原因、快速路径命中率、容量接口耗时和重试耗尽率。关联任务吞吐与续租失败，判断消除多余同步后是否仍有实际瓶颈。
- 若仍有明显等待，再提出单独变更：优先缩短事务、减少锁内重复读写；评估续租/任务操作按槽位或租约加锁的可行性。领取、全局唯一分配、资源清理和路由更新涉及跨资源一致性，不能直接删掉全局锁。拆分前明确固定加锁顺序，并验证重复领取、租约过期、任务完成、代理切换及清理并发。
- 采集业务库：另有 [读取压力快照](incremental-db-read-pressure-20260923.md)，显示迁移扫描、publication/outbox 查询及任务心跳行锁竞争。该库与 Rota 控制库的问题需分别归因；不能拿这份采集库快照证明 Rota 容量接口慢。
- 采集库先收集代表性 SQL、表规模、现有索引、执行频率和执行计划；生产先用普通 EXPLAIN，执行型测量优先放隔离环境。依据结果决定索引、扫描分页、批次/频率与事务范围优化，变更逐项对比，避免没有执行计划就添加索引或增加 Worker。
- 当前快照未启用 pg_stat_statements、track_io_timing；是否启用及是否需要重启单独评估，先使用现有统计。索引创建若获证据支持，选择适合在线业务的方式并检查磁盘余量、无效索引及回滚步骤。

**8. 防复发与完成标准**

将磁盘可用空间、inode、预计耗尽时间，以及 NATS/outbox 最老未处理年龄、数据库写入失败、接单接口暂缓率纳入监控；阈值结合实际增长速度设定。保留历史失败作为证据，以实际缺口及处理进度判断恢复，定期验证备份可恢复。

第一阶段完成须同时满足：新增回归与既有核心测试通过；精确镜像可追溯；受控发布完成；生产观察通过；失败原因可见；回滚资料齐全。仅让某一次点击成功，或仅把失败计数清零，不算修复完成。
