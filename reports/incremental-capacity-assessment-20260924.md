# 当前增量抓取瓶颈与 Worker 扩容评估

评估时间：2026-09-24 01:59–02:04 UTC，北京时间 09:59–10:04。只读采样，没有调整 worker 数、数据库连接数、CPU 配额或生产代码。

结论：当前最明确的扩容限制在共享中心：数据库客户端连接池持续排队，Node 主线程接近单核满载；任务执行还承担约 20 秒中心主导周转。55 个执行槽位基本满载，确有增加并行度的需求，但只加远端 worker 很可能将更多等待转移到中心，不能期待线性提升。数据库存在 I/O 与行锁压力，但尚无证据证明整台数据库或磁盘已经饱和。

## 增加 worker 的判断与建议

1. **不建议现在直接从 55 大幅增加到 75 或 100。** 已有 worker 不缺任务，但共享连接池已持续排队，主线程接近单核满载。新增 worker 会增加领取、心跳、查询、结果应用和收尾的压力；可能小幅增益，也可能只是增加排队与超时。此次没有做扩容对照，不能给出实测收益百分比。
2. **优先缩短中心每任务的固定成本。** 进一步计量应用池 acquire 等待、SQL 执行、事务持锁和 stop ACK；减少重复读取、轮询与序列化，缩短持锁区间。针对 Node 主线程取得安全的函数级 profile 后再决定优化点。不能移除 lease/fence、身份绑定或停止确认。
3. **连接池数量是待验证参数，不应直接翻倍。** pool=12 的事实和排队已经确认，但数据库还有行锁、I/O 等待。增加池可能缓解客户端排队，也可能把排队搬进数据库；应与事务优化分别做受控测试。
4. **排查预算耗尽和租约失效导致的失败重试。** 先追溯具体执行链路和生命周期，避免直接增大预算或绕过过期保护。恢复成功率对此前低谷的收益可能大于单纯加 worker。
5. **中心排队改善后，先试 55→60，再考虑 65。** 每档至少观察 20–30 分钟，并按 About/Video 构成和视频工作量对齐；以去重 completed/分钟、成功 Plan/分钟、失败重试率、中心池等待、主线程 CPU、阶段 P95、到期至完成延迟及远端节点资源为验收指标。若增加 worker 后完成量不升、P95 或失败率上升，应回退该档。

仅做算术参照：若完全保持当前每 worker 效率，以最近 15 分钟 84.07 个/分钟为基线，55→65 对应约 99.35 个/分钟（+18.2%）。这要求共享中心成本、任务构成、代理和远端资源不恶化；当前证据不支持把这个数字当作可实现承诺。没有采样远端节点 CPU/内存，故不能保证具体节点可承载更多槽位。

## 复核材料与方法边界

证据目录：`runtime/incremental-capacity-20260924/`。包括阶段 `measure.mjs` / `snapshot.jsonl` / `summary.json`、数据库与主机 `probe.mjs` / `db.jsonl` / `host.jsonl` / `pressure-summary.json`、线程 `threads.py` / `threads.json`、队列 `queue.mjs` / `queue.jsonl`、调度与池汇总、吞吐和失败分类查询。SQL 使用 READ ONLY 事务、8 秒 statement timeout、1 秒 lock timeout。

本次任务是容量评估而非修复指定回归，因此用现有线上阶段计时、连续统计和已有遥测作为反馈基线，未人为触发生产故障、注入临时探针或进行扩容试验。诊断确认了当前共享资源排队和近期失败开销；函数级根因、扩容弹性和完整日内容量曲线仍需后续受控测量。
