# 增量节点02开启接单无变化

核查日期：2026-09-23，时间均为 UTC。

原因已经定位到中心网络容量准备接口返回 503，开启请求在保存接单开关之前失败。不是 Worker 离线，也不是单纯的页面显示滞后。

## 证据

- 外部入口记录用户两次 POST `/api/server-nodes/0e108078-200a-4df0-9a58-a28abc97a692/execution`，分别在 05:41:40、05:42:16 返回 503。
- 同时间 Rota 的 POST `/api/v1/proxy-control/capacity/ensure` 分别于 05:41:40.751、05:42:16.213 返回 503，耗时约 4.367 秒及 2.601 毫秒。
- 首次只读检查：8 个现役 Worker 全部连接，activation_requested/enabled 均为 false；intake_controls.intake_enabled=false，接单请求没有写入新状态。
- 中心 `deploymentAdmin.setExecution` 在保存接单请求前调用 `capacity.ensure()`；容量准备失败会转换为 `REMOTE_NETWORK_CAPACITY_UNAVAILABLE`，保持原接单设置。
- Rota 对资源同步暂缓返回 503；现有访问日志没有保留那两次的响应正文，因此不将具体锁持有者或内部错误细节当作已证实结论。

## 处理与验收

根据用户已点击开启的意图，05:45 使用同一正式接口、当前 registry 版本和 expectedRequested=false 重试开启节点02。容量准备于 05:45:35 返回 200，约 530 毫秒；页面接口返回 saved=true、intakeEnabled=true、allowedCount=8。

05:50:25 再次核查：8/8 连接、8/8 就绪、8/8 运行，3 个正在采集、5 个处于处理阶段。原始开启请求返回后需要中心异步准备，不能把当次响应 ready=0 视为开启失败。

此次未重启服务、未直接修改数据库、未更改代码、未修改其他节点的接单开关。证据保存在 `runtime/node02-intake-20260923/`。


## 底层原因补充

进一步证据指向 `RESOURCE_SYNC_DEFERRED`，即资源同步遇到锁竞争而暂缓：

- 05:44:01 Rota 明确记录 `proxy control resource sync deferred`，reason=`control_advisory_lock_busy`。
- 05:45:35 同步成功，preflight 525ms、持锁 9ms、bcrypt 438ms，进程累计 deferred_total=59（不是这几分钟内的新增次数）。
- 两次 503 的响应长度均为 81 字节，与 `RESOURCE_SYNC_DEFERRED` 的既定 JSON 响应完全一致；服务禁用响应为 70 字节。结合同期控制接口正常及没有重启，资源同步暂缓与现有证据吻合。日志未保存响应正文，无法还原当次究竟是哪一个互斥锁检查失败及锁的持有者。
- 同一 6 分钟窗口，续租请求 5,642 次成功、任务开始 417 次成功、任务完成 409 次成功。并非整个 Rota 服务不可用。
- 只读容量核查：远端需求 85 + 本地固定名额 62 = 147；当前已配置 channel 名额 154，容量目标也是 154。该数字代表配置名额，不等同于所有代理当前都健康。
- Rota 和中心均没有 OOM 或额外重启；扩容后的磁盘仍有约 192GB 可用。没有证据要求继续扩容硬件来解决此问题。

调用链为：开启接单 → 强制 capacity.ensure → syncResourcesMinimum → TryLock/数据库 advisory try-lock 失败 → 503 → 开启请求未保存。

同步遇锁忙主动让出是保护正在执行任务的设计；问题在于接单开关把这一步作为每次开启的硬前置，即使已有足够配置名额仍同步，而且中心容量客户端 `maxAttempts:1`，没有对暂缓做有限重试。

建议修复方向：在可验证所需名额及持久容量下限已满足时走幂等快速路径；对明确的 RESOURCE_SYNC_DEFERRED 做有界退避重试；保留业务状态与并发修改校验，并在页面清晰显示准备中或失败原因。不要以延长持锁时间或绕过执行准入检查解决。此次仅诊断并记录方向，尚未修改这部分代码。
