## 已实现

1. `RemoteNodeStore` 在保持事务局部作用域、同步提交和原超时值的前提下，将四条设置语句合并为一条；每个相关事务减少三次数据库往返。
2. 每个 managed attempt 共享一个 binding 静止确认器。外层恢复清理和实际 Rota adapter 复用同一 binding 的成功、零在途确认；失败不缓存，并发调用共用未完成 promise。checkpoint 仍独立验证并可重试，不跨 attempt 复用权限。
3. 主池、心跳池、结果池增加固定标签的抽样 SQL/事务计时及每秒池长度采样，每 10 秒聚合报告 CPU、event loop、GC、内存和阶段耗时。未采样的连接直接使用 pg 原路径，不增加全局 AsyncLocalStorage 钩子；不记录 SQL 正文、频道 ID 或载荷。直方图分位数为桶上界，计数不能直接当成全量 SQL 次数。
4. 测试环境增加可选临时 PgBouncer 事务池和 stop 专用数据库。代码和生产发布均保留了工作区其他已有变更。

## 验证

- 修复前，真实 PostgreSQL 测试捕获设置语句为 4 次而目标为 1 次。
- 修复前，真实 managed runtime + adapter 组合测试捕获正常收尾对同 binding 多执行一次 stop；checkpoint 失败重试累计 stop 4 次。
- 修复后单元测试验证不重复停止、checkpoint 重试、失败静止结果不缓存、不同 attempt 不共用缓存、清理超时不提前完成。
- 生产同版本 Node 20.20.2、真实 Go 转发器、PostgreSQL/Redis/NATS/PgBouncer：关键集成 41 项通过、零跳过，含 SIGKILL 后原 Plan 恢复、旧 owner 隔离、API/国家切换、停止与 checkpoint。
- 抽样观测及全量执行兼容验证：37 项通过、零跳过。最终移除观测全局异步钩子后，再跑连接池接口、事务池及真实入口 6 项，全部通过。
- 微基准发现全量计时增加客户端 CPU，已改为抽样并移除额外异步上下文钩子。最终八轮 1,000 事务对照未见稳定的额外开销，但自然波动明显，不把它宣称为“观测带来提速”或精确小于 2% 的证明。

## C 批：由隔离 profile 证实的异步上下文开销

A/B 恢复后 15 分钟尚未证实整体提速：最近 5 分钟 77.4 个/分钟，成功完整样本收尾 5.30 秒、中心主导部分 18.17 秒，主池仍排队且事件循环接近满载。因此未扩大连接池或 worker。

沿主线程方向，在生产同版本 Node 20.20.2、隔离 PostgreSQL 中复现 55 个并发 Plan、12 个连接、3,300 个事务。原协调器为每个存活 Plan 启用独立 AsyncLocalStorage；Node 在异步资源创建时逐个传播这些存储。独立 CPU profile 确认 `_propagate` 是显著热点，未向线上进程注入 inspector。

候选改动只包含 `incrementalCoordinator.js` 和新模块 `incrementalTransactionScope.js`：所有 Plan 共用一个底层 AsyncLocalStorage，但每个 Plan 有独立身份，只有身份匹配才能借用自己的事务；嵌套其他 Plan 保留原上下文链。Plan 结束只关闭自身身份，不全局 disable，晚到回调不能复用已结束 Plan 的连接。

实际候选三轮交错基准：原实现平均 CPU 6,596.6 ms、耗时 6,802.7 ms；候选 CPU 4,223.1 ms、耗时 5,225.7 ms，分别减少约 36.0% 和 23.2%。这是小 SQL 合成负载，不能直接换算线上吞吐增幅。基准和 CPU profile 位于本次 runtime 的 `async-context-*` 文件。

验证包括 55 并发事务身份、嵌套不同 Plan、内层回滚后外层继续、结束后的晚到回调、真实 PostgreSQL 和 PgBouncer；真实 Go/BullMQ/NATS 的崩溃恢复及 API/国家 handoff 集成共 37 项通过、零跳过。另一路所有权、whole-channel 恢复、stop 和入口检查通过；首次 handoff 入口因测试环境变量名称填写错误拒绝运行，修正后由上述 37 项重跑通过。跨主机 WAN 诊断未启用，不列入通过项目。
