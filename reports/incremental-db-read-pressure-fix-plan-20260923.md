# 增量抓取效率修订方案

日期：2026-09-23，第二版。状态：重新审视及只读复测已完成；没有部署性能修复、创建索引或修改表结构。

## 1. 修订结论

原方案适合治理数据库后台读负载，但尚不能证明实施整套结构改造会显著提高增量抓取效率。把新增发布补偿表放在第一批、把中心主线程与任务持锁优化放到最后，优先级不够贴近增量关键路径。

新顺序：**先建立增量全过程基线，同时定位中心 CPU、持锁和往返成本；用一次可回退的后台降载对照验证数据库竞争影响；按实测收益选择最小修复。新增表和索引不作为首批前置条件。**

原第一版详细设计保留为 [条件技术选项](incremental-db-read-pressure-fix-options-20260923.md)，不是当前实施清单。

## 2. 新证据与限制

9 月 23 日 06:33–06:34 UTC（北京时间 14:33–14:34）只读复测，阶段耗时取最近 10 分钟内创建、首次 generation、已 applied 且整频道命令已收到的 535 个样本：

| 阶段 | 平均 | P95 | 含义 |
| --- | ---: | ---: | --- |
| task 创建 → command 创建 | 7.62 秒 | 11.52 秒 | 领取/协调/业务准备，包含中心与数据库等待 |
| command 创建 → command received | 16.25 秒 | 46.04 秒 | 指令领取、远端抓取、传输及中心持久接收；不能全部称为 YouTube 网络耗时 |
| command received → task applied | 6.43 秒 | 12.35 秒 | 结果采用、数据写入、领域结算及中心调度 |
| task 创建 → task applied | 30.31 秒 | 65.25 秒 | 不含 task 创建前排队、applied 后接单清理及最终 Feature 消费 |

- 中心 Node 主线程连续 30 秒占约 0.958 核，即单核 95.8%。这证明主线程繁忙，尚未证明具体 CPU 热点或事件循环延迟；增加进程 CPU 配额未必有效。
- 最近 10 分钟 youtube-channel-incremental 有 613 个不同 Job 的 completed 事件，约 61.3 个/分钟；54 个不同 Job 出现 failed。两组可能重叠，不能用 54/(613+54) 宣称精确失败率。
- completed/applied 不等于所有业务领域 complete，部分结果可能为 partial 或转交 Agent/API；真正有效完成指标须进一步对领域结果核验。
- 活跃增量传输任务为 44 leased、2 pending。Finalize 为 waiting/prioritized/failed 均 0、active 1、delayed 2，当前没有此前数千失败任务的积压。
- 9 月 22 日中心阶段平均 8.84 秒、总计 15.21 秒，只能作历史参考。恢复部署、接单节点数量、代理质量、Plan 构成和全量负载已变化，不能据此计算同负载退化比例。

底层读压证据仍有效：此前三次采样持续存在 DataFileRead、历史发布扫描超过 50 秒，见 [数据库压力快照](incremental-db-read-pressure-20260923.md)。但“后台 SQL 很慢”与“它是增量吞吐主瓶颈”是不同结论，后者需要对照。

## 3. 每项改动对增量的实际作用

| 项目 | 对增量效率的作用路径 | 当前判断 | 新优先级 |
| --- | --- | --- | --- |
| 中心 CPU 热点及任务准备/应用往返 | 直接影响下发、接收、应用及下一任务周转 | 主线程接近单核满载；函数级热点待 profile | 首批定位，按证据实施最小代码改动 |
| tasks 持锁范围 | 直接阻塞增量 poll、接收和心跳，可放大重试与槽位占用 | 有 2–3 秒锁等待和相关事务调用链证据 | 首批测量与优化 |
| 后台 onboarding/终态扫描降载 | 降低共享 I/O、缓存与 CPU 竞争，间接帮助增量 | 确认昂贵，增量收益尚未做因果对照 | 首批小范围对照，不先重构整个补偿系统 |
| 迁移/API 重复历史统计 | 减少旁路资源消耗 | 部分优化已上线；当前大读取的具体调用点未完全归因 | 仅修改确认仍在运行的热点 |
| 远端抓取、传输与中心持久接收 | 当前占平均阶段耗时约 54%，直接决定槽位周转 | 尚未拆分代理等待、抓取、上传、中心确认各自耗时 | 与中心测量同批补齐，不预先扩并发 |
| crawler outbox | 影响 Feature 新鲜度，某些结果也影响 Plan 收敛；共享 I/O 可能影响采集 | 发布器已有恢复；不能默认它阻塞下一次远端采集 | 先验证完成依赖与到期任务年龄 |
| publication outbox/自动 onboarding | 主要影响业务发布与历史导入；对抓取多为资源竞争上的间接作用 | 与增量抓取目标的直接关系较弱 | 以发布 SLO 单独验收，不用发布完成量代替增量效率 |
| 新补偿表、持久游标体系、多组索引 | 可能长期减少扫描，但增加写入、WAL、空间和维护复杂度 | 对增量的净收益未证明 | 条件项目，退出默认首批范围 |

代码核查发现的具体切入点：

- `remoteNodes/incrementalCoordinator.js` 的单次 query 包装会进入任务事务；没有外层事务时需重新取任务锁、执行业务 fence 并续 coordinator。应先统计每个 Plan 的事务/SQL 次数，寻找可合并的短操作。扩大成一个长事务可能反而使心跳和结果接收更慢。
- `remoteNodes/incrementalBusinessFence.js` 会读取并锁定 Plan、dispatch、binding、Run、attempt；这些校验是正确性约束，不能当作“冗余 SQL”直接删除或跨事务缓存。
- `remoteNodes/wholeChannelStore.js:input` 在持任务锁时调用 wholeChannelParts，逐分片请求可能重复序列化和哈希完整输入；最后结果接收会在事务内拼接/解码。它们是 CPU/持锁候选热点，不是已经证明的根因。
- `channelPlanStore.receive` 和整频道 receive 的外层 decode 已在取锁前。第一版“把解码移出锁”的笼统建议不能重复计功，须定位仍在锁内的处理。
- 完整 video receipt 的领域写入目前有意共用原子事务，确保 Observation 和领域状态一起提交。不能仅为缩短事务拆掉这个保证。

## 4. 收益应如何估计

新样本中，准备与应用合计约 14.05 秒，占总阶段耗时 46.4%，但包含 CPU、调度、数据库读写和锁等待。

举例：若两段都缩短一半，其他部分不变，30.31 秒会降至约 23.28 秒，任务该区间耗时减少约 23.2%。只有槽位周转是限制、负载同质、没有其他瓶颈时，才对应约 30% 的理论吞吐增幅。**这只是敏感性计算，不是数据库优化收益承诺。**

单独减半 6.43 秒应用阶段，总耗时仅减少约 10.6%。反过来，读盘量下降很多但中心 CPU/远端耗时不变，增量完成量仍可能不变。也可能锁竞争缓解同时改善远端确认段，所以不能把上述两个阶段作为所有数据库收益的绝对上界。

撤回第一版把“读取块减少 80%、应用 P95 降低 20%、实际 I/O 降低 30%”并列作为固定首批放行目标的做法。它们没有同负载实验支持；以后按每个具体改动的基线与自然波动设门槛。

## 5. 首批工作：无新增业务表、无默认新增索引

### 5.1 以真正增量结果建立测量闭环

指标分三层，不混为一个成功数：

1. 吞吐：每分钟唯一 Plan 的完整领域完成量，另列 partial、失败、API/Agent handoff；再报告按 about/video/task_mask、视频数、结果大小、节点及重试次数分层的工作量，避免“换成更轻任务”产生假提速。
2. 时延：排队 → task 创建 → command 创建 → 远端开始/结束 → 中心 durable receipt → applied → Worker 可再次接单；完整端到端 P50/P95。不同阶段 P95 不能相加。
3. 资源和正确性：中心主线程 CPU/事件循环延迟、连接池等待、SQL/事务/持锁耗时、数据库实际 I/O、WAL、磁盘余量、唯一应用与 stale fence 拒绝、下游新鲜度。

以独立业务主键对账，已创建但未完成任务也纳入 cohort；报告超时、失败与仍在运行，避免只统计完成样本带来的幸存者偏差。完整完成量不足时报告样本不足，不凭 queue completed 代替。

先建立 15 分钟当前基线，再做 A/B/A 或等价受控对照，各窗口至少 15–30 分钟；冻结接单数、部署版本和其他优化，记录代理/任务构成及全量负载。大尾部样本不足则延长，不能把 30 秒 CPU 快照当作完整容量测试。

### 5.2 对照一：只验证后台扫描竞争

单独把已有 `PUBLICATION_ONBOARDING_RECONCILE_INTERVAL_MS` 从 60 秒调至 300 秒，批量保持 25，正常 Finalize 后发布衔接保持执行；这是实验选项，本次未调整。

- 同时比较有效增量吞吐、准备/应用/远端确认时延、DB 读取、中心 CPU，以及 onboarding 最老待处理时间和完成量。
- 只有增量收益在重复窗口超过自然波动且补偿延迟可接受，才保留降频，并优先优化这条查询的输入集合。
- 若仅 I/O 下降而增量无改善，归类为资源节省，不再以“提高抓取效率”为理由推进新补偿表。继续检查其他直接瓶颈。
- 降频不能停止历史补漏；若单轮本来已超过新间隔或其他同类循环接管了负载，需据实际调用频率判断实验是否有效。

### 5.3 对照二：直接路径的最小改动

先短时 profile 中心，并用持锁/SQL 计时核实热点，再只选一项实现，例如：

- 对同一不可变 command/input 内容减少重复编码、解码和哈希。若使用缓存，必须按 command_id/generation/input hash 区分，设置字节上限与淘汰，并保证失效后可重建；不能缓存 lease 或业务所有权结论。
- 合并同一短事务内的重复读取或安全数据库往返，不扩大事务到网络请求、不改变 fence 顺序。
- 结果读取与纯计算分离时，提交前必须重新核验版本、generation、lease、coordinator 及 business fence。不能只凭“此前读过”就提交。

需要 worker threads 或进程拆分的改动，只有 profile 证明纯 CPU 工作占比足够且不能低成本消除时再设计，避免在未定位热点前引入额外序列化和并发所有权复杂度。

### 5.4 同时补齐远端和接收段归因

当前 16.25 秒指令到收到的区间比准备或应用都长。按任务构成拆分指令等待、代理获取/限流、YouTube 请求与重试、分片数/上传、中心持久接收确认。

发现中心接收等待则归入事务/CPU修复；发现外部抓取或代理重试占主导，则调转到对应采集路径。不降低采集完整性、跳过必需视频或缩短重试预算来制造吞吐提升。历史节点接单问题单独参照节点容量方案，实验期间不同时扩节点。

## 6. 第二批：有证据才付出结构和磁盘成本

下列门槛满足后，才重新启用 [第一版条件选项](incremental-db-read-pressure-fix-options-20260923.md)：

- 新补偿表：确认历史扫描长期构成主要竞争，查询改写/现有状态/降频不足以满足增量与发布 SLO；证明变更事件覆盖、历史补漏、跨版本回退，并给出表增长与保留策略。
- 新索引：独立库接近生产分布的 EXPLAIN (ANALYZE, BUFFERS) 与并发测试证明实际受益；估算最终索引、构建临时空间、WAL及写放大，明确复用现有索引无效的原因。一次一个，保留安全磁盘余量。
- 新持久游标：确实需要跨重启进度且现有 schema 无合适语义时才新增；不能滥用 Finalize 等其他恢复游标的业务空间。
- 迁移统计/历史 outbox 优化：以其当前执行频率、真实扫描量和与关键路径竞争为依据，不根据单次表读取排名预先承诺收益。

索引增加会影响增量写入及缓存容量，新增请求登记也会增加每次业务提交成本；验收必须测净效果。CONCURRENTLY 减少锁阻塞，不减少磁盘需求。不以清理业务失败记录或删除未发布事件作为降载手段。

## 7. 验收、回退与停止条件

每次只上线一个可回退改动；先在隔离环境跑并发、租约过期、重放、崩溃恢复、领域状态与 Observation 原子提交回归，再进入受控对照。

- **宣称提高增量效率**：同等输入下完整领域完成量提升，或固定工作量的端到端完成时间下降，幅度超过基线窗口波动并能重复；同时报告 partial、重试和超时，不能减少质量换速度。
- **仅宣称资源节省**：I/O/CPU 明显下降，但增量业务吞吐和时延无可重复改善。可以保留低风险改动，但不据此扩大结构改造。
- **立即回退**：丢失/重复业务应用、owner/fence 越权、旧 lease 复活、发布完整性回归。
- **性能回退参考**：连续两个 5 分钟窗口，同负载下完整完成量下降超过 10% 或端到端 P95 增加超过 20%；必须结合任务构成排除外部变化。这是防回归阈值，不是优化收益目标。
- **补偿保护**：以事先约定的历史积压清理期限、最老 due 年龄和新数据新鲜度作为 SLO，不要求任何短窗口队列都下降；有持续输入时队列短时增长不等于失败。
- **停止扩改**：首批优化达到实际吞吐/时延需求后停止；不为“方案完整”继续建表、加索引或拆服务。
