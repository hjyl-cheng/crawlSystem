## 确认的两个未闭环问题

1. **评论传输失败没有补回**：Ateliê Juliana Nogueira 的 `HHQNB1X0U70`（Bolsa diamante 💎）

   此处不是已确认的关闭评论，也不是昨天年龄限制空响应的问题。应做独立、有限的评论补采，
   不应把它写成 0 或为了评论重抓整个频道。

2. **About 修复被错误执行成完成态重放**：CNPqOficial (`UCXs3LHxIwbfr5_HrySsGXTA`)
   总播放量 unresolved，唯一 About 观测为 `about_metrics_partial`，只解析出 2/3 指标。
   视频的 30 个详情及 Agent 均完成，频道仍 ready_partial、未发布。
   已保存的第 2 轮修复任务包含 `publication_gap_scope=about_only`、
   `require_complete_about_metrics=true`，结果却只有 `executed_phases=[handoff]`、
   `detail_processed=0`，执行器计时 56 ms，任务显示 completed，却没有新 About 观测。
   Run 已记录第 3 轮修复意图；不是 3 次实际成功抓取 About。

   此路径未被调用。应为 About-only 修复保留专用分流或在共享执行器实现对应阶段，

## 性能瓶颈的量化证据

以下阶段占比来自 **498 个原始快照任务的最后一次成功返回**；恢复重试可能跳过已完成阶段，
因此不是所有历史尝试的完整时钟归因。总请求耗时存在并发重叠，不用它充当墙钟占比。

| 阶段 | 累计执行器计时 | 占快照总计时 |
|---|---:|---:|
| 频道 admission | 583.1 秒 | 2.43% |
| Uploads/分页 | 500.7 秒 | 2.09% |
| 视频详情 | 22,796.8 秒 | **95.09%** |
| close_fetch | 55.1 秒 | 0.23% |
| handoff | 7.5 秒 | 0.03% |
| 总计（含阶段外开销） | 23,974.1 秒 | 100% |

**主瓶颈是详情工作量。** 14,686 次已保存的详情观测，平均约 1.52 秒，
共 44,157 次详情相关请求（平均约 3 次/视频）。在 20 个 worker 下，
这些详情耗时即使理想摊平也需要约 18.6 分钟，已经占该批 22.6 分钟的大部分。
原始快照最后一次执行平均 49.0 秒，P95 73.0 秒。全部快照执行尝试累计约 24,426.6 worker 秒，
相对 20×整批时间约 90% 的占用；这是执行占用近似值，不是 CPU 利用率。

**被窗口排除的旧内容也抓了完整详情和评论。** 8,270 条详情最终因超出 90 天窗口排除，
占全部详情 56.3%，消耗约 12,455.8 秒（已保存详情计时的 55.8%）。
另有 66 条预告、4 条进行中的直播被排除。
497/498 个频道的初始 Uploads 活跃度证据含未解析发布时间，必须通过详情判龄；
不能直接把它们当休眠。164 个最终休眠频道共抓取 4,711 条详情，消耗约 7,017.7 秒。
优化点是先用 YouTubeJS player 的发布时间/类型做资格判定，只有保留内容再请求评论，
保留所有判龄与扫描完整性约束。可减少多少耗时需要实测，不能把上述 55.8% 全部算作可消除。

**Agent 凑批增加频道延迟，但不是主抓取吞吐瓶颈。** 22 个 Agent 批次覆盖 334 个活跃频道，
多数每批 20 个。抓取完成到 Agent 入队平均 39.6 秒，P95 81.2 秒；
入队后等待平均 0.003 秒，处理每批平均 13.7 秒；Agent 完成到 Run 完成平均 6.9 秒。
Controller 有 15 秒轮询，凑批与调度共同影响这段尾延迟。
应考虑带最大等待时间的小批次刷新，避免只为凑满批次而等待。

**Finalize 处理很短。** 837 个相关 Finalize Job，平均处理 0.46 秒、P95 1.02 秒；
队列等待平均 3.81 秒、P95 13.52 秒。直接增加 Finalize worker 不能解决 95% 的详情成本。

**少数重试造成长尾，不是主要总量成本。** 3 次 503、1 次连接中断的队列失败，
另有 3 次执行路由预算耗尽事件；最终全部详情已完成，无本批 API 兜底请求。
最慢几个 Run 约 12.8～16.8 分钟，含重排队/恢复，不能解释成一个请求耗时这么久。
原始快照排队平均约 9.8 分钟，是 500 个任务共享 20 个 worker 的自然排队，
不是单次网络请求延迟。

## 处理优先级

1. 修正 About-only 修复路由及成功判据，恢复 CNPqOficial，并验证批次关闭。
2. 对 1 条评论 SSL 失败做定向补采，明确可选评论的后续修复归属。
3. 再做详情阶段优化：先判龄/类型，再采保留内容的评论；用同类频道对照测量收益。
4. 缩短 Agent 凑批等待；清理已恢复频道的历史错误展示；复核 3 个未完成的外链观测。
