# 增量重复失败修复设计

状态（2026-09-24）：中心确定性修复已实施并上线，历史限定批次已补偿；用户明确授权后，远端 node01/node02 共 55 个 worker 已全部部署并恢复就绪；网络/租约根因专项仍按证据推进。发布及验收记录：`incremental-repeat-failure-fix-release-20260924.md`。以下保留原批准方案。依据：`incremental-repeat-failure-causes-20260924.md` 的生产样本与真实函数复现。

目标：可恢复错误在有效预算内恢复；耗尽预算的业务运行只结算一次；失去所有权的旧执行不能覆盖新执行；减少 SSL/代理错误造成的实际抓取失败。工作分为可立即实施的确定性缺陷修复，以及需要补足证据的网络/租约专项。

## 1. 统一失败决策，区分终止范围

将同一错误链的识别集中在共享策略入口，供中心增量处理器和本地 worker 使用。返回错误类别、终止范围、是否允许业务执行重试、是否需要路由动作，以及结构化证据。上层策略匹配完整 cause/errors 链，遍历防环。

决策优先级：失去执行所有权 → 业务总预算耗尽 → 频道/单视频终态 → 可恢复网络错误与单次执行预算 → 其他错误。旧执行遇到预算错误也不能终结替代者。

| 场景 | 行为 |
|---|---|
| 业务总预算耗尽 | 终止当前业务运行，不再申请网络 Task；保留后续独立调度资格 |
| 单次执行换路预算耗尽，总预算仍有额度 | 结束本轮，由现有队列退避机制启动下一轮 |
| SSL/代理传输失败 | 在原预算内保存检查点、静默旧请求、报告观察，由 Rota 决定换路 |
| 视频被删除/版权移除等已确认内容终态 | 在单视频范围结算，继续其他合法工作，不因该视频反复换路 |
| 已被新 generation/owner 替代 | 停止旧执行；不发布替代执行的业务失败 |
| 同一 owner 的租约确实到期 | 停止旧请求，经有界恢复接管流程继续；不直接复用失效租约 |
| 暂时无法确认所有权/结算失败 | 暂停新网络请求，重试确认或结算，不重新抓取 |

`ProxyControlRequestError` 的类名不能无条件把明确的不可重试业务错误转为 system_retry。优先识别业务码；对剩余控制请求错误明确处理 retryable 属性和兼容旧错误的规则，避免误伤原有暂时性错误。

网络、队列、业务三层预算继续各司其职。Rota 是网络预算的唯一权威；不通过新建 Business Run、重置计数或新增内部重试绕开预算。总预算耗尽终止的是本次业务，不是把频道永久禁用。

## 2. 增量预算终结作为一个完整操作

新增增量专用终结入口，复用现有事务、Observation 和绑定操作。不能简单把全量 `terminateExhaustedBusinessRun` 的队列条件放宽：增量 Job 以冻结 Plan 为身份，业务键需从 Plan 推导，并校验现有绑定；其状态归属、部分完成、Agent/API 后续工作也不同。

涉及代码：`managedWorkerJob.js`、`channelCandidateWorkerLifecycle.js`、`remoteNodes/centerIncrementalProcessor.js`、`worker.js`、`incrementalTerminalFailure.js`、`incrementalRunStore.js`、`proxyBusinessRun.js`。

操作顺序：

1. 停止本执行的新网络请求。若存在旧 binding，复用既有 stop/quiescence/retire 流程；未证明旧请求静默前不得换身份或交给新执行。
2. 在短事务中验证冻结 Plan hash、Job、dispatch generation、业务绑定以及当前执行归属。沿用现有锁序：remote task（若存在）→ channel mutation lock → Plan/dispatch → binding → Run → attempt。不得持锁调用网络服务。
3. 对本次业务写入稳定的终止原因 `business_run_budget_exhausted` 与诊断证据，终结 binding 和相应 Run 执行状态。已完成领域、已提交 Observation、已有检查点不回滚。
4. 为应失败且尚未结算的领域写入幂等失败 Observation/outbox。完整 Plan 状态沿用 feature-engine 的既有事件投影规则；不由队列层另写一套 Clock 结算逻辑。已正式交给 Agent 或 API 的工作单独校验其合法性，不能批量标失败，也不能无期限遗留。
5. 事务提交后才使 BullMQ 本次 Job 不可重试。使用不可恢复错误保留失败结果，避免把“跳过终态任务”当成成功抓取。

幂等键以业务运行、终止原因和必要的领域身份组成，不依赖额外无效重试的 attempt 次数。重复回调、提交响应丢失、worker 重启只复用同一结算结果。

跨 PostgreSQL / Redis / Rota 不假设分布式原子事务：数据库提交后队列确认丢失，下次进入只读取并重放终结；数据库提交前失败，下次只尝试完成结算。每次重新进入仍由 Rota 权威预算阻止新网络尝试。若设计中存在尚未完成的资源退休，持久化可恢复进度并由有界补偿处理，不能把未静默资源视为已释放。

## 3. 阻止已终止 Run 被再次唤醒

现有 `IncrementalRunStore.claim()` 会将普通 failed Run 恢复为 running。保留普通可恢复失败的续跑能力，但对明确预算终止标记或 terminal binding，必须在写 running 前拦截。

中心与本地 worker 均在执行准备入口识别该终态；旧 delayed Job、重复投递、进程重启都不能重新申请抓取。不能只依赖内存中的 discard 标记。

同一耗尽预算的 Business Run 不允许直接人工 resume 绕开额度。需要重新抓取时走已有合法重新调度/修复入口，明确创建新的授权执行及其预算；若现有入口不支持，返回明确不可续跑原因，不能静默重置。后续正常 Clock 调度独立处理。

## 4. SSL/代理专项：先定位，再改变恢复策略

已确认样本主要是 SSLError curl 35 与 ProxyError curl 56；这些码尚不能定位具体代理供应商、TLS 握手步骤或指纹兼容问题。

网关补充结构化且脱敏的证据：异常类别、curl code、受限长度的脱敏底层消息、实际可获得的请求阶段/耗时、session_reset、目标端点类别，以及用于内部关联的 route generation、代理匿名标识、profile revision、worker。禁止记录认证信息、Cookie、完整代理 URL；未知阶段明确标为 unknown。

详细证据只在失败时有界记录并去重；聚合指标不带 Plan/Job/代理等高基数标签。观察 30–60 分钟，分别统计请求失败率、换路成功率、故障集中度。

- 若故障集中于个别代理，核查并修复现有 Task Observation → 隔离 → 冷却 → 权威健康探测 → reserve 回归链路，不另建旁路换代理机制。
- 若多个出口在同一 profile/版本集中失败，在隔离环境做单变量 TLS/profile/session 对照，再决定会话或指纹修复；不在真实任务中盲目多试。
- 若为上游挑战，按既有挑战策略处理；版权移除等内容终态独立核对，避免误触发身份更换。

不先放大 2 次换路、9 次总尝试的现有上限，也不先增加 worker。

## 5. 租约专项：区分过期、被替代与状态已结束

保留对外 STALE_LEASE 兼容性，内部补充触发操作、拒绝原因、请求/当前 generation、owner、task 状态、服务器租约截止时间、最近续租成功时间及续租耗时。区分远端 Task 租约、网络 binding、Rota slot 与 coordinator 的不同续租链路。

恢复规则：

- 已被替代：取消旧请求，仅清理旧执行持有的资源；不能写新执行的失败记录。
- 同代租约到期：以数据库时间和原子 owner/generation 条件确认；先静默旧请求，再通过既有接管流程恢复，仍受业务预算约束。
- 续租超时但结果不确定：有界确认服务器状态；不得盲目认定续租成功，也不得立即建立第二个抓取执行。
- 结果已持久化：遵守现有 durable receipt 重放协议，不因为租约已结束重复抓取。

实现具体续租修正前，以故障注入区分事件循环延迟、数据库排队、续租响应丢失、网络中断和 generation 变化。默认 90 秒租约仅为代码默认值；先确认部署值与实际延迟，再讨论调整时长。

## 6. 历史任务、测试与发布

历史处置先输出 dry-run 清单，限定时间、队列和明确的耗尽证据。对旧 delayed/waiting Job，在重新领取入口安全终结；不批量删除或重建 Job。历史未结算状态以小批量、有游标方式补偿，逐条校验所有权和终止证据，保留审计记录。当前仍活跃的合法执行交由正常围栏/静默流程处理。

必须通过的回归：

1. 用真实 ProxyControlRequestError cause 链经过中心增量处理入口：预算终止优先于通用 system_retry。
2. 三轮各三次网络失败耗尽九次预算后，无第十次网络执行；可能存在权威预算拒绝请求，但不能再抓取。
3. 数据库提交前后崩溃、Redis 确认丢失、回调重放：只生成一次终态结算，不复活 Run。
4. 普通失败仍可续跑；已有成功领域、合法 Agent/API continuation 不受错误终结影响。
5. 旧 generation 与新 generation 并发：旧执行不能终结新执行或重复写结果。
6. SSL/Proxy/challenge/content-terminal 分类、脱敏与 Observation/换路次数吻合。
7. 租约过期、续租 ACK 丢失、结果提交竞态、持久回执重放均符合恢复规则。
8. 全量抓取原有预算终结逻辑不回归。

使用真实 PostgreSQL、Redis/BullMQ 和 Rota 预算实现的隔离集成环境验证；网络故障使用确定性注入，避免依赖真实 YouTube 波动。先将现有诊断 repro 纳入合适调用边界的回归测试。

分阶段发布：

- A：共享分类、增量幂等终结、领取拦截及测试，先解决确定的无效重试。
- B：网络与租约诊断证据；可独立发布低开销观测，再根据结果实施对应修正。
- C：有界历史补偿；完成 dry-run 和状态核对后执行。

灰度采用实际支持的部署隔离单元，确认共享分类代码的影响范围，覆盖至少 30 分钟且有足够相关失败样本后扩大。新持久化字段先保持兼容；回滚必须保留对终止标记的读取保护，不能回退到会复活 terminal Run 的旧入口。

验收目标：新增业务预算错误被判 system_retry 的次数为 0；终态业务再次启动网络执行的次数为 0；重复终态事件和跨代污染为 0；结算失败可重试且最终收敛。网络/租约阶段另验收其根因失败率和恢复成功率。吞吐按相同 about/video 任务组合比较唯一成功 Plan/分钟、P95 完成时长、失败占用 worker 时间、中心与数据库压力；减少失败事件本身不等于成功率提高。
